# frp 客户端配置管理工具 · 调研与可行性（2026-09-12）

> 用途：新增「frp 客户端配置管理」工具前的可行性调研。回答两个问题：这类工具**能到什么程度**、**有没有开源项目做过**。
> 状态：调研完成，**待用户拍板四个决策点**（见 §6）后才进入任务书阶段。

---

## 1. 结论摘要

1. **能做，而且天花板不低**：frp 官方从 v0.66–v0.68 起就在补「客户端可管理性」——`frpc verify`（配置校验）、`frpc reload`（热重载）、`frpc status`（状态）、**内置 Admin Web UI + HTTP API**，以及 v0.68 的 **Store CRUD API**（运行时增删改 proxy/visitor 且持久化）。所以这不是"给命令行套个壳"，而是有官方接口可对接。
2. **同类开源项目非常多（≥17 个 GUI）**，形态分三类：Windows 原生（`frpmgr` 最成熟）、跨平台桌面（Electron / Flutter / Avalonia / Tauri）、Web 面板（部署在服务器上）。其中 **3 个用 Tauri + Vue 3**，与 patchyBox 技术栈一致，做法可直接借鉴（不抄代码）。
3. **本仓库可行性无阻塞**：已有 spawn 外部子进程先例（`plugins/database/agent/client.rs` 的 `tokio::process::Command`、`plugins/hosts/mod.rs` 的 `std::process::Command`），**不需要 `tauri-plugin-shell`**，与项目"禁用 shell 插件"的政策兼容。
4. 唯一有分量的成本不是技术，而是**frpc 二进制从哪来**（每平台约 12MB），以及要不要做"关掉 GUI 仍常驻 + 开机自启"这种 Windows 服务级能力（见 §6）。

## 2. frp 官方提供了什么（能力天花板）

来源：frp 官方文档 `gofrp.org` 与 `fatedier/frp` releases（截至 **v0.71.0，2026-08-14**）。

| 能力 | 官方接口 | 起始版本 | 说明 |
| ---- | -------- | -------- | ---- |
| 配置校验 | `frpc verify -c frpc.toml` | 已有 | 支持 featureGates；TOML 语法错误会带行列号 |
| 热重载 | `frpc reload -c frpc.toml` | 已有 | **需开启 `webServer`**；数秒内创建/更新/删除代理；非代理类公共参数（除 `start`）无法热改 |
| 状态查询 | `frpc status -c frpc.toml` | 已有 | **需开启 `webServer`** |
| 客户端管理界面 | `webServer.addr/port/user/password`（默认 `127.0.0.1:7400`） | 已有 | 自带 Web 管理页 + HTTP API |
| **运行时动态增删改代理** | `[store] path = "..."` + `/api/store/proxies*`、`/api/store/visitors*` | **v0.68.0** | CRUD + 持久化 + 运行时 reload，**无需重启 frpc**；web dashboard 有 Store 管理页 |
| 单条代理开关 | proxy/visitor 的 `enabled` 字段 | v0.66.0 | 不必再用全局 `start` 列表 |
| 服务健康检查 | proxy 的 `healthCheck.type/path/timeoutSeconds/maxFailed/intervalSeconds` | 已有 | **由 frpc 自己发起**，不用我们在前端轮询本地端口 |
| 配置拆分加载 | `includes = ["./confd"]` | 已有 | proxy/visitor 可拆到多文件 |
| 客户端标识 | `clientID` | v0.67.0 | 服务端 dashboard 可区分多客户端 |
| 服务端侧 API | frps dashboard API v2（`/api/clients` 等，分页/详情/流量历史） | v0.70.0 | 若将来做服务端只读视图可复用 |
| 版本兼容策略 | 每个 minor 支持到后续 9 个 minor 发布；frpc 0.69 可与 frps 0.61–0.77 互通 | v0.69.0 | 混版本部署需先升 frps |

**因此工具能覆盖的三层**：

1. **配置层**（零外部依赖、最稳）：多配置（多 frpc 实例）管理、表单与源码双模式编辑、导入导出、`frpc verify` 校验。
2. **运行层**：启动/停止/重启 frpc 子进程、日志捕获与展示、崩溃/掉线状态判定。
3. **监控与动态层**（走官方 API，价值最高）：代理状态、连接数与流量、`reload` 热更新、`store` 模式下运行时增删代理、健康状态。

**做不到 / 不该做**：修改 frps 服务端配置（除非另做服务端面板，本需求是"本地 frpc"）；替代或实现穿透协议本身；跨平台统一的系统服务化（Windows 服务 / macOS launchd 需各写一套）。

## 4. 本仓库可行性（已有先例与可复用资产）

| 项 | 结论 | 依据 |
| -- | ---- | ---- |
| spawn 外部进程 | **已有先例**，不需 `tauri-plugin-shell` | `src-tauri/src/plugins/database/agent/client.rs`（`tokio::process::Command`）、`src-tauri/src/plugins/hosts/mod.rs`（`std::process::Command` 调 powershell/osascript） |
| 配置编辑 | 复用 `UiCodeEditor`（TOML/YAML 有语言支持，`minimal`/`full` 两档） | `src/core/ui/UiCodeEditor.vue` |
| 日志查看 | 复用 SSH 插件的日志弹窗样式 | `src/plugins/ssh/LiveLogDialog.vue` |
| 进程/监控视觉 | 有现成版式可参照 | `src/plugins/ssh/ProcessTab.vue`、`MonitorTab.vue` |
| 数据落盘 | 用框架 `PluginDb` 建 `frp.db` 存配置条目 | `src-tauri/src/framework/store.rs` |
| 工具级设置 | manifest `settingsSchema` 自动渲染（frpc 路径、默认配置目录等） | 框架既有能力 |
| 敏感值 | token 等走系统 keyring + vault（不落明文） | `src-tauri/src/framework/vault/` |
| sidecar 打包 | **尚无先例**，需新增 `bundle.externalBin` 与 per-platform 二进制命名 | 全仓库 grep 无 `externalBin` |
| 体积影响 | frpc 各平台压缩包约 **12MB**（v0.71.0 releases） | fatedier/frp releases |

## 5. 功能分档建议

**该做的（v1 最小可用集）**

1. 多配置（多 frpc 实例）管理：新增/复制/删除/启用，落 `frp.db`
2. 配置编辑：表单（serverAddr/token/proxy 列表）+ 源码（`UiCodeEditor` TOML）双模式
3. 生命周期：启动/停止/重启 frpc 子进程，日志实时展示
4. 配置校验：调 `frpc verify` 并把错误行列反馈到编辑器
5. 状态判定：从 frpc 日志/退出码推断（停止/连接中/已连接/错误），错误必须可见（token 错、服务端不可达）

**可选（有明确条件才做）**

| 项 | 触发条件 |
| -- | -------- |
| 运行时热改代理（`reload` / `store` CRUD API） | 用户接受 frpc 开本地 `webServer` 端口 |
| 流量与连接数监控 | 同上（数据来自 admin API） |
| 托盘常驻 + 开机自启 + 关窗保活 | 用户要求"关掉界面也要跑"，需按平台做服务/自启项 |
| frpc 二进制应用内下载与升级（SHA256 校验 + 原子替换） | 选择"不内嵌、运行时下载"方案时 |
| 定时连接（按时段自动连断） | 有明确使用场景时（MoonProxy 有此功能） |

**不建议做**

- 自研/内嵌 frp 协议实现（frp 已是成熟协议，重造无收益）
- 把 frps 服务端配置管理塞进同一个工具（本需求明确是"本地 frp 客户端"，服务端属另一个产品形态）
- 复制同类项目的全家桶（多源公共节点市场、社交化分享等与工具箱定位无关）

**排序建议**：先做「配置管理 + 校验 + 启停 + 日志/状态」这一条闭环（含 §6 决策 1 的二进制来源），其余按触发条件追加。理由：这一步就能替代"手工写 TOML + 开终端跑 frpc"，成本最低、天天用得上；而监控/托盘/定时属于增量易用性，缺了不影响可用。

## 6. 待用户拍板的四个决策点

1. **frpc 二进制来源**：① Tauri sidecar 随包内嵌（+约 12MB/平台，跨平台各带一份，符合"单 exe 便携"但安装包明显变大）；② 用户自备（工具里指定 frpc 路径，最轻，但首次使用要自己下载）；③ 应用内下载（首次使用时从上游 Release 拉取 + SHA256 校验，安装包小、但依赖网络与 GitHub 可达性）。**推荐 ② 或 ③**，① 的体积代价与 patchyBox 的单 exe 偏好冲突。
2. **是否要「关掉 GUI 仍常驻 + 开机自启」**：这是 `frpmgr` 的杀手特性，但跨平台实现成本高（Windows 服务或计划任务 + macOS launchd）。若要做，建议先只做 Windows。
3. **是否开启 frpc `webServer` 换取热改与监控**：收益是运行时增删代理、流量与连接数；代价是占一个本地端口并增加攻击面（需设 `webServer.user/password`）。
4. **配置存储形态**：单文件多 profile（本工具管理，与 frp 原生无关）还是**直接管理多个真实 `frpc.toml`**（与手写配置互通，工具只是编辑器+启动器）。**推荐后者**——用户已有的配置文件可直接纳入管理。
