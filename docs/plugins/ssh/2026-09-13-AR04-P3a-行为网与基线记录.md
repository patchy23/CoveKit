## 2. 手法与边界（对齐决策书 §2.1）

- **真实生命周期**：最小宿主组件 `defineComponent` 里调用 `useSshWorkspace()`，`mount()` / `unmount()` 真实触发 `onMounted` / `onUnmounted`。
- **mock 的是 IPC 门面，不是状态所有者**：只替换 `./ipc`（命令可编程返回、事件可手动推送、退订句柄可检查、订阅可挂起制造竞态）与框架设置读写；`useServerGroups`、Pinia store、composable 本体的状态所有权保持真实。

- **断言口径**：断言用户可感知状态（页签、连接状态、进度文案、toast）与资源责任（断开、退订、计时器），不固定无关内部调用顺序。

## 5. 观察项（不构成要求违反，本轮不改行为、也不冻结为正确）

1. **删除服务器的顺序**：`deleteProfile` 先关闭并断开该服务器名下的工作区，再请求后端删除配置；后端删除失败时提示可见（toast「删除服务器失败」）且配置仍在，但用户的活会话已被关闭。判定：不违反「删除失败不得伪装成功」（提示可见、未谎报），故不作为缺陷复现；P3c 搬移逻辑时若调整顺序，`删除失败：提示可见，配置仍在，不伪装成功` 与 `删除服务器：连带关闭其工作区并断开会话` 两条用例需同步复核。
2. **同 profile 两个占位工作区的首绑顺序**：`requestId` 绑定前，首个 `connect-stage` 事件按创建顺序绑定第一个未绑定占位（已用 `占位工作区由首个 connect-stage 事件完成绑定` 固定）。真实链路上后端事件总带 `requestId`，不影响归属；若后续改为「按 profile 预生成 requestId」，需同步改这条用例。
3. **空闲阈值来源**：`idleDisconnectMinutes` 每次定时器触发时从设置读取（`0`/非数字视为不启用），已由 `空闲断开阈值非正数时不生效` 固定。
