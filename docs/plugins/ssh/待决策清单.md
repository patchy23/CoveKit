# patchyBox SSH 工具 · 待决策清单

> 版本：v1.0（2026-08-08）  
> 状态：待用户拍板  
> 每个问题给出 2-3 个候选方案 + 推荐

---

## 1. 凭证加密方案（必决策）

**背景**：服务器密码 / SSH 私钥 / passphrase 需要安全存储，禁止明文落盘。

| 方案 | 原理 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. tauri-plugin-stronghold** | IOTA Stronghold 加密引擎，内存安全 + 持久化快照 | 跨平台、专为 Tauri 设计、内存隔离、审计日志 | 引入额外依赖（~2MB）、首次需初始化密码 | ⭐⭐⭐⭐⭐ |
| **B. 系统钥匙串（keyring）** | Windows Credential Manager / macOS Keychain / Linux Secret Service | 零依赖、系统级安全、用户无感知 | 各平台 API 差异大、私钥大文件可能超限 | ⭐⭐⭐ |
| **C. 加密文件（AES-GCM + 主密码）** | 本地文件用主密码加密，主密码内存驻留 | 完全可控、无外部依赖 | 主密码管理麻烦、忘记无法恢复 | ⭐⭐ |

**推荐：A（stronghold）**  
理由：patchyBox 技术决策已预留 stronghold（AGENTS.md 开放问题 #5 默认 stronghold）；SSH 私钥通常 2-4KB，keyring 可能超限；stronghold 的内存隔离特性适合多服务器凭证场景。

**遗留问题**：stronghold 初始化密码是用户设置还是自动生成？（自动生成更安全，但用户换机无法迁移）

## 2. 终端组件选型（必决策）

**背景**：SSH 终端需要支持 ANSI 转义序列、滚动缓冲、resize、复制粘贴。

| 方案 | 原理 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. xterm.js** | 成熟 Web 终端模拟器（21k★），Canvas/WebGL 渲染 | 功能最全、社区活跃、Tabby/electerm 同款、支持插件（搜索/链接/图片） | 包体积 ~300KB、需处理与 Vue 的集成 | ⭐⭐⭐⭐⭐ |
| **B. 自研终端渲染** | 用 `<pre>` + 正则解析 ANSI 序列 | 零依赖、体积小 | 工作量大、兼容性差（特殊序列/性能/滚动）、维护成本高 | ⭐ |
| **C. 简化终端（LineNumberTextarea 只读）** | 只展示输出，输入走下方输入框 | 最简单、复用现有组件 | 非真正交互式终端、无法支持 vim/top 等 TUI 程序 | ⭐⭐ |

**推荐：A（xterm.js）**  
理由：SSH 终端的核心价值是「真正的交互式 shell」，vim/htop/top 等 TUI 程序必须完整 ANSI 支持；xterm.js 是事实标准，patchyBox 作为桌面端可直接通过 Tauri IPC 与 Rust SSH 库双向通信，无需 WebSocket。

**集成方式**：`npm install @xterm/xterm @xterm/addon-fit @xterm/addon-web-links`，封装为 `src/core/ui/Terminal.vue`。

## 3. 监控刷新机制

**背景**：资源监控需要实时数据，但 SSH 连接是长连接，频繁 `exec` 有开销。

| 方案 | 原理 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. 轮询（exec 命令）** | 前端定时器 → `ssh_monitor_get` → Rust exec `top/free/df` 解析 | 实现简单、无额外依赖 | 每次 exec 有 fork 开销、数据不实时 | ⭐⭐⭐⭐ |
| **B. 长连接推送（SSH 通道 + 循环）** | Rust 建立 SSH 通道循环执行命令，通过事件推送到前端 | 数据更实时、减少 exec 开销 | 实现复杂、需管理多个后台任务 | ⭐⭐⭐ |
| **C. agent 模式** | 服务器上运行轻量 agent，通过 HTTP/metrics 暴露 | 性能最好、数据最全 | 需在服务器安装额外软件，违背「纯 SSH」定位 | ⭐ |

**推荐：A（轮询）**  
理由：第一批先用轮询（3s 间隔），满足「够用」；P2 再评估是否升级为 B。轮询命令用 `top -bn1`、`free -b`、`df -B1`、`cat /proc/net/dev` 组合，一次 exec 完成。

## 4. 契约分批边界

**背景**：任务书建议分 3 批，但第 2 批（凭证）与第 1 批（连接）有依赖关系。

| 方案 | 分批方式 | 优点 | 缺点 |
|------|----------|------|------|
| **A. 按任务书：1=连接+终端+文件，2=凭证+编辑，3=监控+服务+进程+docker** | 凭证在第 2 批才实现 | 第 1 批命令数少（~14 条），快速验证终端体验 | 第 1 批连接时密码只能内存传递，无法保存服务器配置 |
| **B. 合并 1+2：连接+凭证+终端+文件+编辑** | 凭证与连接一起实现 | 服务器配置可保存，用户体验完整 | 第 1 批命令数多（~20 条），开发周期长 |
| **C. 凭证提前到第 1 批，编辑延后** | 1=连接+凭证+终端+文件，2=编辑，3=监控+... | 凭证与连接强绑定，逻辑自洽 | 编辑功能延后，文件管理器只能查看不能改 |

**推荐：B（合并 1+2）**  
理由：凭证管理是 SSH 工具的「地基」，没有保存服务器配置的能力，每次连接都输密码体验太差；且 stronghold 集成本身有学习成本，宜早不宜迟。远程编辑可延后到第 2 批。

## 5. 远程编辑技术方案

**背景**：远程文件编辑需要「下载 → 编辑 → 上传」流程。

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 临时文件 + CodeMirror** | 下载到 `%TEMP%/patchybox-ssh/<hash>`，CodeMirror 编辑，保存时上传 | 编辑体验好（语法高亮/搜索/替换）、复用现有 CodeViewer 技术栈 | 需管理临时文件生命周期 |
| **B. 直接流式编辑（不下载完整文件）** | 只下载文件片段，编辑时增量同步 | 大文件友好 | 实现复杂、冲突处理难 |
| **C. 调用系统编辑器** | 下载后调起 VS Code / Notepad++ 编辑，监听文件变化上传 | 用户用熟悉编辑器 | 依赖外部软件、跨平台差异大 |

**推荐：A（临时文件 + CodeMirror）**  
理由：与 patchyBox 现有技术栈一致（CodeViewer 已用 CodeMirror 6）；临时文件用连接 sessionId + 文件路径 hash 命名，断开时清理。

## 6. 文件上传下载并发与进度

**背景**：大文件传输需要进度反馈，多文件需要队列。

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 单文件同步传输** | 一次传一个文件，阻塞 UI | 实现最简单 | 大文件时 UI 卡死、无法取消 |
| **B. 单文件异步 + 进度事件** | 后台任务传输，IPC 事件推送进度 | 进度可见、可取消 | 实现中等 |
| **C. 多文件队列 + 并发** | 队列管理，同时传 2-3 个文件 | 效率最高 | 实现复杂、需处理并发错误 |

**推荐：B（单文件异步 + 进度事件）**  
理由：第一批先做好单文件体验；多文件队列 P2 再议。Tauri 事件机制（`app.emit`）可直接推送进度到前端。

---

## 7. 终端多路复用（一个连接多个终端）

**背景**：用户可能想在同一服务器开多个终端。

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 一个连接一个终端** | 每开终端新建 SSH 连接 | 实现简单、隔离性好 | 连接数多、服务器压力大 |
| **B. 一个连接多个终端通道** | SSH 连接复用，每终端一个 channel | 连接数少、符合 SSH 协议设计 | 实现稍复杂、需管理 channel 生命周期 |

**推荐：B（连接复用 + 多通道）**  
理由：SSH 协议原生支持多通道；patchyBox 的 `ServerConnection` 模型已预留 `sessionId → connection` 映射，终端只是 connection 上的多个 channel。

---

## 8. 断线重连策略

**背景**：网络波动时自动重连提升体验。

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 手动重连** | 断开后 toast 提示，用户点击重连 | 实现简单、用户可控 | 体验差、频繁断线时繁琐 |
| **B. 自动重连（指数退避）** | 断开后自动尝试，间隔 1s/2s/4s/8s，上限 5 次 | 体验好、无需干预 | 需处理重连时终端状态恢复 |
| **C. 心跳检测 + 自动重连** | 定时发送 SSH keepalive，失败即触发重连 | 检测更及时 | 实现最复杂 |

**推荐：B（自动重连，指数退避）**  
理由：第一批实现基础自动重连；心跳检测 P2 再议。重连成功后自动恢复终端（重新打开 shell channel），文件管理等页签提示「连接已恢复」。
