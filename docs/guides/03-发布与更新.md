# 03 · 发布与更新

## 发布模式

### CoveKit 命名与旧安装接续

产品名和仓库名为 `CoveKit`，工程包名为 `covekit`，应用标识为 `com.patchyx.covekit`；GitHub 所有者仍为 `patchy23`，与域名 `patchyx.com` 不要求同名。

新标识首次启动且尚无 `settings.json` 时，接续旧标识 `com.patchy23.patchybox` 的自举配置，并把旧默认数据根显式写成存储位置；已有自定义根原样保留。旧目录与配置不移动、不删除，新配置存在时不覆盖。若希望数据目录也使用新名称，通过设置中的存储位置迁移入口处理，不手工删除仍在使用的旧目录。不要同时运行共享同一数据根的旧、新版本。

新建凭证使用新 keyring service；只有新 service 的同空间条目明确不存在才只读回落到旧 service。拒绝访问、损坏等错误不当作缺省处理；读取兼容不重生成密钥、不改动旧条目。`.pbdata` 容器魔数与加密 AAD 保持兼容。新建暂存目录统一使用 `.covekit-staging-`；旧前缀集中定义在 `brand_compat`，仅处理升级前的残留和中断计划。同一迁移计划同时存在新旧暂存目录时停止并保留现场。默认导出文件名前缀使用 `covekit-`。

安装标识与可执行文件名均已改变，发布前须在 Windows/macOS 验证安装、更新、数据接续和凭证解锁；仅修改源码或 Rust 格式检查不能代替这些验证。

普通开发读取 `src-tauri/tauri.conf.json`，不要求更新签名私钥。正式发布由维护者在本地生成不入库的 `src-tauri/tauri.release.conf.json`，构建、校验并手动上传 GitHub Releases。推送标签不触发远程检查或自动发布。

更新器固定读取：

`https://github.com/patchy23/CoveKit/releases/latest/download/latest.json`

## 构建平台与环境

应用只发布 Windows NSIS 和 macOS DMG，安装包在各自目标系统构建。发布终端按需配置环境变量：

- `TAURI_UPDATER_PUBLIC_KEY`：更新签名公钥，用于生成发布配置。
- `TAURI_SIGNING_PRIVATE_KEY`：更新签名私钥，绝不入库。
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：私钥口令；无口令时留空。

macOS 代码签名和公证按本机构建方式配置签名身份、证书与公证凭据；Windows Authenticode 使用可用的代码签名证书。更新签名不等同于操作系统代码签名。无需配置 GitHub Actions variables 或 secrets。

## 密钥和安全

首次发布前生成更新密钥对，在安全位置保存私钥和备份，仅在发布终端提供给构建工具。丢失私钥后，已安装的应用无法验证新更新。不要在仓库、日志、聊天或发布产物中传播私钥。

## 发布步骤

1. 确认 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 与发布标签版本一致，运行 `python scripts/check_versions.py <发布标签>` 校验。
2. 按[验证矩阵](02-验证矩阵.md)完成检查，将 `CHANGELOG.md` 中准备发布的条目归入目标版本。
3. 在各目标系统设置发布环境变量，运行 `pnpm release:config` 和 `python scripts/check_release_config.py`；校验失败时停止发布。
4. Windows 执行 `pnpm tauri build --config src-tauri/tauri.release.conf.json --bundles nsis`；macOS 执行 `pnpm tauri build --config src-tauri/tauri.release.conf.json --bundles dmg`。
5. 创建并推送同版本标签，手动创建 GitHub Release 草稿。上传安装包、更新产物与对应 `.sig`，根据真实产物整理更新器需要的 `latest.json`，核对版本、平台、下载地址与签名；构建不会自动创建或上传该清单。
6. 在 Windows/macOS 实机验证安装、升级、数据接续和凭证解锁，核对代码签名及 macOS 公证。确认 `latest.json` 引用的文件完整后，发布正式版本，并验证固定更新地址能够返回本版本清单。
