# 03 · 发布与更新

## 发布模式

### CoveKit 命名与旧安装接续

产品名和仓库名为 `CoveKit`，工程包名为 `covekit`，应用标识为 `com.patchyx.covekit`；GitHub 所有者仍为 `patchy23`，与域名 `patchyx.com` 不要求同名。

新标识首次启动且尚无 `settings.json` 时，接续旧标识 `com.patchy23.patchybox` 的自举配置，并把旧默认数据根显式写成存储位置；已有自定义根原样保留。旧目录与配置不移动、不删除，新配置存在时不覆盖。若希望数据目录也使用新名称，通过设置中的存储位置迁移入口处理，不手工删除仍在使用的旧目录。不要同时运行共享同一数据根的旧、新版本。

新建凭证使用新 keyring service；只有新 service 的同空间条目明确不存在才只读回落到旧 service。拒绝访问、损坏等错误不当作缺省处理；读取兼容不重生成密钥、不改动旧条目。`.pbdata` 容器魔数与加密 AAD 保持兼容。新建暂存目录统一使用 `.covekit-staging-`；旧前缀集中定义在 `brand_compat`，仅处理升级前的残留和中断计划。同一迁移计划同时存在新旧暂存目录时停止并保留现场。默认导出文件名前缀使用 `covekit-`。

安装标识与可执行文件名均已改变，发布前须在 Windows/macOS 验证安装、更新、数据接续和凭证解锁；仅修改源码或 Rust 格式检查不能代替这些验证。

## Alpha 发布范围

首个公开测试版本为 `0.1.0-alpha.1`。同时提供 Windows x64 NSIS、macOS Apple Silicon ARM64 DMG 和 Intel x64 DMG，不提供 Linux 包。Alpha 不启用应用内更新，不生成更新签名包或 `latest.json`；新版本从 GitHub Releases 手动下载。

Windows 暂不配置 Authenticode；macOS 使用 ad-hoc 签名，不需要开发者证书，但未获 Apple 公证，也不代表发行者身份已验证。构建成功不等于实机验收通过，平台状态见[平台能力矩阵](../product/07-平台能力矩阵.md)。

## 自动打包与草稿

仅推送 `v*` tag 触发 [Release 工作流](../../.github/workflows/release.yml)，日常分支 push 和 PR 不触发。工作流核对 tag 与四处版本号，分别构建三个目标；全部成功后才汇总安装包和 SHA-256 清单，创建标记为 Pre-release 的草稿。当前流程仅接受 Alpha tag，正式版本须先确定签名与更新策略。

不需要签名 secrets，上传使用 GitHub 自带的 `GITHUB_TOKEN`；仓库须允许 Actions 执行，发布任务需要 `contents: write`。重跑可以替换同名草稿附件，遇到已公开版本则拒绝覆盖。不会自动公开草稿。

## 安装说明

- Windows：下载 x64 安装程序。未配置发布者签名，系统可能显示未知发布者或 SmartScreen 提示；确认下载来源与校验值后再决定安装。
- macOS：按芯片选择 ARM64 或 x64 DMG，打开后将 CoveKit 拖入应用程序。未公证应用可能被 Gatekeeper 阻止；确认来源后按系统“隐私与安全性”中的提示处理，不需要全局关闭系统安全检查。系统拒绝继续时保留提示并反馈，不承诺所有系统版本均可绕过。
- SHA-256：Windows PowerShell 使用 `Get-FileHash <安装包> -Algorithm SHA256`，macOS 使用 `shasum -a 256 <安装包>`，与附件 `SHA256SUMS.txt` 比对。

依据：[Tauri ad-hoc 签名](https://v2.tauri.app/distribute/sign/macos/)、[Apple 安全打开应用说明](https://support.apple.com/102445)。

## 发布步骤

1. 同步 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 的 CoveKit 条目及 `src-tauri/tauri.conf.json` 版本；运行 `python scripts/check_versions.py v0.1.0-alpha.1`。
2. 按[验证矩阵](02-验证矩阵.md)执行发布前检查，整理 `CHANGELOG.md` 和工作流引用的[Alpha 发布说明](../../.github/RELEASE_NOTES.md)。不把未执行检查写成通过。
3. 提交准备好的变更，再创建并推送对应 tag；仅本地创建 tag 不会触发工作流。发布准备不代表已经授权推送。
4. 等待三个构建任务成功，下载草稿安装包，在对应系统核对安装、启动、退出、凭证、SSH 与文件传输、数据导入导出等关键链路。未覆盖项在发布说明中明确列出。
5. 检查三个安装包、SHA-256 清单、预发布标记、已知问题、第三方许可及资源授权后，手动公开草稿。发布正文只说明用户可用的功能、安装方式与具体限制，不放内部待办或验收要求。

本地排查构建时，Windows 使用 `pnpm tauri build --target x86_64-pc-windows-msvc --bundles nsis`；macOS 使用 `pnpm tauri build --target aarch64-apple-darwin --bundles dmg` 或 `--target x86_64-apple-darwin`。完整构建由维护者执行，当前不使用 `pnpm release:config` 的更新签名覆盖配置。
