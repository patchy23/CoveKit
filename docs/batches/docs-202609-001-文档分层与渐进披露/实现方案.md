# 文档分层与渐进披露（怎么做）

## 设计原则（harness 思路）

> 文档边界 = 上下文边界。判据是**「什么时候会需要它」**，不是「内容多长就切多短」。

| 原则 | 落地 |
| --- | --- |
| 按读取时机切分 | 一次任务里总是一起读的留在同一份；条件性内容拆出去 |
| 渐进式披露 | 每份文档头部「何时读 / 讲什么 / 多大」；索引只说有什么、多大、何时读 |
| 单一事实源 | 拆出去的内容原处不留副本，只留指针 |
| 内容去它该在的域 | 插件专属模式归 `docs/plugins/<id>/`，不堆在 `standards/` |
| 稳定锚点 | 保留原二级标题文字，便于 `read_file` offset/limit 精读与全文检索 |
| 机器守卫 | 体量预算 + 死链 + 台账覆盖，三项都由脚本把关 |

### 4. 摘要块

每份保留文档在标题下插入统一格式：

```
> **何时读**：…
> **本文讲什么**：…
> **体量**：约 N 千字符（超过 1 万的应用 `read_file` 的 offset/limit 分节读）
```

### 5. 引用同步

改动前先全仓 grep 旧路径与被搬走的章节标题，逐一改写；改完跑死链扫描 + 四个检查器。

## 风险与回退

| 风险 | 应对 |
| --- | --- |
| 内容在切割中丢失 | 切完**逐节比对字符数**，总量守恒才继续；有差异立即定位 |
| 引用漏改造成死链 | 全仓扫描 `docs/` 与根 md 的所有 markdown 链接；检查器独立把关 |
| 拆分后反而更难找 | 总纲/红线篇保留导航表；`docs/README.md` §按需追加 同步到新文件名 |
| 有人仍在引用旧章节 | 原二级标题文字不变，全文检索仍能命中 |
