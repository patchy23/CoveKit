# 文档分层与渐进披露（做什么）

## 背景

实测：仓库 75 份 md 约 50 万字符。新会话开工必读链路 4 万字符（已收口到 24,656），
但**按需追加**这一环仍有硬伤——UI 任务必读的 `11-插件UI开发约定.md` 单份 36,026 字符，
产品需求 `07-产品需求.md` 单份 40,716 字符 / 1723 行。中文 1 字约合 1 token，
打开其中一份就用掉上下文四分之一到三分之一。

根因两条：

1. **文档边界与上下文边界不重合**——把"每次都要读的红线"和"只在用到某组件时才读的
   API 备忘"、"所有工具的产品需求"和"某个工具的需求"塞进同一个文件，读者只能整份吞
2. **缺渐进式披露**——文档没有让读者"先看骨架再决定深入哪里"的入口

## 范围

| 对象 | 现状 | 目标 |
| --- | --- | --- |
| `docs/standards/07-产品需求.md` | 40,716 字符 / 1723 行 | 总纲 + 按工具域分册，每册只在做该工具时读 |
| `docs/standards/11-插件UI开发约定.md` | 36,026 字符 | 红线与契约留本文；组件 API 备忘独立；插件专属模式归 `docs/plugins/<id>/`；UI 验证专题独立 |
| `TODO.md` | 17,832 字符 | 四段"✅ 已完成"（6,874 字符）移入对应批次目录，本文只留待办与裁决 |

## 非范围（明确不做）

- 不改任何**规范内容本身**：只做搬移、切分与导航，正文一字不改
- 不改 `docs/batches/` 下的历史任务书（记录当时事实，改写历史无意义）
- 不删任何信息：拆出去的内容必须在新位置完整存在

## 产出

1. `07-产品需求.md` 拆为总纲 + 4 份工具域分册
2. `11-插件UI开发约定.md` 拆为红线篇 + 组件 API 备忘，插件专属模式归入 `docs/plugins/<id>/`
3. `TODO.md` 瘦身，历史段进批次目录
4. 每份保留文档头部加「何时读 / 本文讲什么 / 体量」摘要块（渐进披露入口）
5. 全局引用同步改写，死链 0
6. `docs/README.md` / `AGENTS.md` 文档地图 / `docs/进度台账.md` 同步更新
