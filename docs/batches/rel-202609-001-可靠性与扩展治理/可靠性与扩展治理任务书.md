## 1. 判断与目标

### 1.1 按当前定位判断框架是否足够

依据 `docs/standards/07-产品需求.md` §2，项目是**本地优先、低占用、服务开发者与个人服务器维护者的桌面工作台**，重点是 SSH、网络排障、接口调试和数据处理，而不是工具数量或企业平台规模。

当前框架方向可以继续使用：Tauri + Vue、插件目录隔离、惰性加载、公共 UI、命令注册表、PluginDb、Vault、分区存储都有实际价值。不建议重写，不引入动态插件运行时、通用 ORM、微内核或工作流编排器。云账户后期实现，本期通过本地导入导出的数据空间、稳定身份、版本化逻辑数据和适配接口预留接入基础。

主要问题是几个公共能力的**失败路径与生命周期没有闭环**：存储迁移可能切分读写位置，凭证保护与声明不符，设置可能显示成功但未生效，页签关闭/更新重启没有共同的资源退出协议。这些问题会随着连接型工具增加而放大。

建议投入顺序：先冻结本地数据空间/传输契约 → 数据与密钥安全 → 双平台可用与设置一致性 → 工作区生命周期与可诊断性 → 本地导入导出闭环 → 可选复用扩展。

### 1.2 必须保留的边界

- 保留插件独立目录和独立本地数据库，框架不能直接依赖业务表结构。
- 保留 Vault 引用与手工输入的用户路径；统一底层安全能力不等于强迫每次临时连接创建可见凭证条目。
- 保留“存储位置重启生效、旧目录保留”的既定决策；修正实现，不改成热迁移。
- 保留关闭主窗进入托盘的默认行为；区分隐藏、关闭工具、退出应用和更新重启。
- 不重新启动 TODO 中明确搁置/不做的事项，包括 SSH 日志自动轮转压缩、FRP 关闭界面后后台常驻与多跳 SSH。云账户/同步已由用户确认为后期规划，本期不运行云端功能，但落实数据接口预留。
- 不把文档中的预留字段当成已经实现的能力，也不为用不到的扩展先造框架。

### 1.3 优先级与证据级别

| 标记 | 定义 |
| --- | --- |
| P0 | 数据完整性或凭证保护存在明确缺口，应先修；相关高风险操作在修完前不得被描述为可靠 |
| P1 | 双平台交付、核心行为、资源收尾与维护性问题，下一整改批必须覆盖 |
| P2 | 有明确消费方的轻量扩展，基础可靠性修完后再做 |

| 条件风险 | 代码缺保护，但损害需要并发、故障或特定数据才能触发 |
| 建议 | 产品能力缺口，不能作为当前 bug 计数 |

## 4. 必修任务详细定义

### T01 · 固定本次运行的存储根，改为下次启动迁移（P0）

**目标行为**：选择新位置后显示“等待重启”；继续操作时，所有数据仍写当前根。真正重启后，在任何插件数据库、Vault、日志写入者初始化前执行迁移，成功后才激活新根。

**改动范围**：`framework/paths.rs`、`framework/storage/`、`lib.rs`、`StorageSettingsCard.vue`、框架 IPC 契约。

**实施要求**：

1. 启动一次解析并注入 `StorageRuntime`，所有 paths 函数只读取 `activeRoot`，不再每次从 settings 计算或探测可写性。与 T15 的 `activeSpaceId/generationId` 一并冻结解析上下文，整根迁移包含非活动空间，不能遗漏新空间布局。
2. 设置保存迁移计划 `pendingMigration`，包含 id、source、target、布局版本、阶段；自举配置继续固定在原 app_data_dir。`storageRoot`、layoutVersion 不允许走通用 settings_set 任意修改。
3. 当前迁移按钮文案改为“确认并安排重启迁移”，不得还声称复制已完成。提供“稍后重启”和“取消待执行计划”。重启必须经过 T10 的未保存/运行中任务协商。
4. 下次启动用维护阶段执行复制与验证，再提交 active root；迁移前不初始化业务资源。若初始化可能早于 setup，调整装配顺序并用测试证明。
5. 已配置盘不可用时进入可见恢复状态，不静默到默认目录新建一套数据库。允许用户重试或明确选择新数据环境；不得自动把空环境标为迁移成功。
6. 失败后保留源、计划和错误详情；只有已确认源可用时才允许继续打开原环境。磁盘重新出现不能导致同进程自动换根。

**验收**：安排迁移后再新增 SSH 配置并写 Vault，重启后两者都存在；重启前 `storage_info.activeRoot` 不变；拔盘显示恢复页；直接 IPC 修改保留 key 被拒；连续两次迁移请求只有一个被接纳；取消计划不修改任何业务文件。

### T02 · 迁移预检、暂存与一致性校验（P0）

**目标**：迁移失败既不损坏源，也不破坏目标原有数据；停止把“文件数/总大小相同”当完整性证明。

**实施要求**：

1. 全局只能有一个迁移，锁在 Rust 服务层。路径验证覆盖绝对路径、规范化同一目录、大小写别名、源/目标祖先关系；未存在目标先规范化最近存在祖先再验证。
2. v1 对复制树中的 symlink/junction/reparse point 明确拒绝并指出路径；不要跟随链接。读目录项失败必须报错，不用 flatten 静默漏项。
3. 非空目标默认拒绝；恢复默认位置若已有旧数据，同样展示冲突，不自动覆盖/合并。用户可先选择新空目录。未来合并单独设计，不能藏在迁移逻辑里。
4. 每次任务使用带随机 id 的暂存目录和 `create_new` 写入探针；不得覆盖用户现有 `.patchybox-write-probe`。只清理由本次任务创建且路径验证通过的文件。
5. 离线复制生成逐文件清单：相对路径、字节数、内容摘要；检查缺失/多余/同长异内容。SQLite 使用一致性备份或完整离线处理；不能仅复制 `.db` 而遗忘 journal/WAL。SQLite 官方明确给出了在线备份 API，不能用裸文件复制替代运行中快照：[SQLite Backup API](https://www.sqlite.org/backup.html)。
6. 验证数据库完整性及逻辑记录；验证 Vault 可用性时不得生成新主密钥。新根提交须可恢复，配置保存失败仍能回原环境。进度按文件/分块更新并节流，不只每个分区发一次。
7. 允许空数据环境变更位置；可选不迁移可重建 cache，但必须在 UI 和清单中说明。源目录继续保留，禁止迁移成功后自动删除。

**验收矩阵**：同目录不同写法、源内目标、目标内源、链接循环、非空目标、同名不同内容、目标断盘/空间不足、目录项权限错误、取消、配置保存失败、零文件、数万小文件、大文件；每种失败都校验源内容摘要不变，目标原有内容不变，重试可成功。

### T03 · 旧布局按数据集合可恢复迁移（P0）

**重点**：同时修正已到 layoutVersion=2 但部分文件未迁移的用户，不能仅修首次迁移路径。

1. 枚举完整旧布局矩阵：DB 与伴随文件、Vault 密文/降级 key/备份、credentials 目录与 key、SSH 旧凭据、`db-secrets.enc` 与 `db-master.key`、known_hosts、缓存。实际文件名由现有插件读取代码确认。
2. 把密文与其密钥、DB 与恢复文件作为迁移集合；使用暂存和逐项状态，校验成功才提交集合。失败保留可读旧位置。
3. 整体 layoutVersion 只在所有必需项完成后推进；已标完成的历史状态增加修复迁移，不改已发布迁移的含义。
4. 不把“目标存在”视为“目标完整”；旧/新同时存在时做比对并提供冲突处理，不能优先采用半截目标或自动覆盖。
5. Vault 与 credentials 的读取必须获得同一已选定布局的路径，不能 key 在旧根、密文在新根各自寻找。
6. 插件旧凭据转换必须全量读入、全量写入、解密回读确认后再标完成；修复数据库旧凭据循环写首项后目标存在导致下一次跳过剩余项的风险。无法解析的旧快照保留归档并提示，不自动删除。

**验收**：构造每种旧版本目录夹具；模拟单项 rename/复制失败、只有 bak、只有 tmp、新旧共存、迁移中断后再次启动、版本号已为2但根下留旧文件。验证所有旧记录、密码、主机信任记录可继续使用，失败不被记为完成。

### T04 · 系统密钥库真实接入与降级透明化（P0）

**证据补充**：本机 `cargo tree --manifest-path src-tauri/Cargo.toml -e features -i keyring --offline` 只显示 keyring 默认 feature。锁定 3.6.3 的 `src/lib.rs` 在 Windows 缺 windows-native、macOS 缺 apple-native 时导出 mock 为 default；不是“系统凭据管理器偶发丢写”所能解释的配置。

1. 用目标平台依赖 feature 启用 Windows/macOS 原生后端；Linux CI 是否需原生后端按测试目标明确，不把 mock 当正式安全实现。核对 lockfile 和各 target feature tree。
2. 增加跨进程读写测试：使用测试专用 service/account，进程 A 写随机测试 key，进程 B 新建 Entry 读取；不可使用真实生产 service/account。单进程内存桩测试不能证明持久化。
3. 旧 fallback key 是迁移输入：先解密验证既有 Vault，再写系统库并跨 Entry 回读。原生 key 与 fallback 不一致时必须基于当前密文判断并报告冲突，禁止简单“keyring 优先”掩盖正确旧 key。
4. 删除 `{other:?}` 对秘密材料的日志输出，仅记录错误类别/存在性/长度是否正确；补测试返回不匹配测试 key，断言日志中无原始字节、十六进制/base64 key。
5. 暴露保护状态 `system-keyring / file-fallback / unavailable`，设置页持续显示原因和恢复入口。fallback 文件施加当前用户权限（Windows ACL、macOS 文件权限分别实现和验证），明确密钥与密文共同复制不具备抗离线解密能力。
6. 沿用既有 fallback 兼容策略，但不能静默声称系统级保护；若要彻底取消 fallback 或引入主密码，应另行确认产品决策，不夹带在 feature 修复中。

**验收**：两平台重启应用可解锁；keyring 不可用/恢复、旧 fallback、双 key 冲突、密文存在而无 key、只剩备份等分支有明确结果；任何失败不生成覆盖既有密文的新 key，不自动删除可恢复旧 key。

### T05 · 合并凭证文件安全原语，补齐崩溃恢复（P0）

**范围**：`framework/credentials.rs`、`framework/vault/store.rs`、数据库凭据适配层。两种业务数据格式不要求本批统一。

1. 抽公共 `framework/secure_store/`（名称可调整）：加解密、主密钥来源、原子写/备份恢复、文件权限。Vault 负责凭证条目模型，namespace credentials 负责兼容 KV 格式。
2. 恢复 bak 必须早于把 NotFound 当空数据；主文件存在但坏、bak 可解密时，不得直接删除 bak。以完整性与认证结果决定采用哪个版本。
3. 存在密文、备份或未完成事务而 key 不在时返回 locked/error，不得生成新 key；正常首次空环境才生成。
4. 临时文件用唯一名称，写完刷盘；明确文件替换各故障点及恢复规则。避免笼统声称多次 rename 是完整事务。旧文件归档/清理由可证明提交结果驱动。
5. 数据库 namespace 当前确有消费方，不得作为“重复 Vault”直接删除；先加兼容读取，再迁移/复用原语。手工密码仍可保存，不强制修改用户工作流。

**验收**：在 tmp 写入前后、主文件转 bak 后、新文件替换后、清理 bak 前注入故障；重启后只能读完整旧版或新版，不能空表覆盖。并发保存不同 id 都保留；key 丢失、密文篡改报错且原文件摘要不变。

### T06 · PluginDb 迁移事务化与版本保护（P1）

1. 每条 migration 的 SQL 与 user_version 更新放同一事务，失败回滚。串行执行迁移，明确锁等待上限和错误。
2. 删除“遇 duplicate column 就整条 migration 成功”的兜底。针对已发布的半执行历史，做版本定向的 schema 检查和修复步骤；不要简单删兼容逻辑导致老库无法启动，也不要按分号切 SQL。
3. user_version 大于应用支持值时拒绝写入并提示需新版，保留文件；非法负版本显式拒绝。
4. 连接 busy timeout 等策略集中设置；foreign_keys/WAL 是否启用先检查现有 schema 和读写场景，不能为了现代化统一开启导致兼容破坏。
5. 提供供迁移/备份调用的一致性快照接口；保留业务 SQL 原始能力，不引入 ORM。

**验收**：第二条 SQL 故意失败不留下第一条修改；版本号写失败回滚；已有列但缺后续表的历史夹具正确修复；新版本库拒绝降级写；重复启动幂等；所有现有插件迁移数组升级到最新均成功。

### T07 · 设置读写、系统副作用与 schema 统一（P1）

1. Rust 设置按字段校验，枚举/数字边界/结构错误返回可展示错误。通用 key API 禁止存储根与迁移版本等内部字段；修复 get/set 层级不一致。
2. 设置更新整体串行或带 revision 的原子 patch，不能各自 get app → set app 覆盖其他更新；工具字段改为 owner/key 粒度更新，不每次发送陈旧 tools 全对象。
3. 全局快捷键先校验，再尝试切换；失败保留/恢复原快捷键，持久化记录与实际状态一致。自启失败返回失败，不保存虚假的开启状态；补启动时配置与系统实际状态核对。
4. 前端显式检测 Tauri 环境：浏览器预览才用 localStorage；桌面 IPC 失败展示并回滚/保留待保存状态，不写另一份配置伪装成功。快速修改按序保存，不能旧请求后返回覆盖新值。
5. storage cache 以文件名缓存 Promise，合并并发 load，失败清缓存可重试；校验 JSON shape，对损坏数据隔离备份后允许恢复，不能直接覆盖。
6. AppSettings 唯一源置于 contracts；默认值每次生成新对象；清理无消费的 recentTools 镜像并保留真实 recent。主题 system 注册媒体变化订阅并释放，不能仅初始化时匹配一次。
7. SettingsField 用判别联合表达类型/default/options/min/max；secret 不允许普通 settings 明文存储。近期无消费方可先禁止该类型并给出迁移说明；未来实现必须走受控凭证引用/安全存储，密码外观不是加密。

**验收**：快捷键非法/占用保留旧键；自启拒绝权限不显示成功；settings.json 无权限/损坏可见；并发更改两个工具字段不互相丢失；两个文件同名 key 不串库；数字 NaN/越界拒绝；预览模式可正常运行；系统暗色变化即时跟随。

### T08 · Windows/macOS 装配、资源访问与发布门禁（P1，交付阻塞）

1. Windows 专属 WebView 调用添加条件调用或非 Windows 明确 no-op；不能通过移除 macOS 目标规避。异常输出采用 T11 的诊断方式。
2. asset scope 跟随本次 `activeRoot`，只授权需要播放的 cache/tts 文件或目录；不得放宽到任意磁盘、整个 data/vault 分区。新路径、中文/空格路径和重启迁移后都实测播放；vault、settings、其他文件仍不可通过 asset URL 访问。
3. 审查已使用的原生窗口 API 与 capability 对应关系，例如 setTheme；失败不能静默隐藏。权限按实际消费方删减，不仅凭 default 名字认定过宽或安全。
4. 开发/普通安装包/正式签名发布的更新可用性明确显示；普通构建没有有效更新配置时显示不可用，不把占位 key 当可用。正式 release 已有覆盖配置，保留并校验。

**验收**：Windows 与 macOS 构建成功、冷启动无 panic、托盘显示/隐藏正常、原生密钥库生效；TTS 默认及自定义根播放成功；无效签名更新拒绝安装；正式更新在测试发布通道验证，不发布测试包到真实 latest。

### T09 · 插件自报凭证引用，删除前状态可信（P1）

1. 框架定义只读 `CredentialReferenceProvider`，由各插件 register 提供查询能力；DNS/SSH（以及实际有 Vault 引用的其他插件）分别查自己的存储，框架不写业务 SQL。
2. 返回引用 owner、对象 id/名称、计数和扫描状态；查询失败返回 unknown/error，不能假装 0。批量扫描避免每个凭证各开一次库。
3. 删除保持现有用户可确认强制删除语义：后端收到显式强制/确认信息并重新核对当前引用；引用变化时重新提示，不依赖过期前端计数。扫描与删除竞态按共享协调/版本机制定义，不声称跨多个库天然原子。
4. 后端持久化迁移完成后移除 localStorage 引用镜像与其测试，先确认无调用并兼容旧数据；不能把陈旧镜像继续当事实源。

**验收**：不开 SSH 页面也能看到引用；DNS/SSH 多个配置引用同一凭证计数准确；库不可读显示未知；删除确认期间新增引用触发复核；插件扫描失败不允许无提示当无引用删除；已删除引用在连接时给出改绑入口。

### T10 · 工作区生命周期、关闭协商与资源释放（P1）

**原则**：现有插件有自己的卸载清理（例如 SSH cleanupAll），并非全部泄漏；缺的是框架能等待、阻止、报告清理结果的共同入口。

1. 引入轻量 ToolContext，提供工具 active/hidden、关闭原因、dispose 注册、未保存/运行中状态。工具切换、设置页覆盖、窗口隐藏分别传递状态；连接不因失焦自动断开。
2. 关闭按钮、Ctrl/Cmd+W、溢出菜单、全部关闭统一走异步 requestClose；未保存草稿弹确认/保存入口，运行中操作明确停止策略。不能保留直接改 openTabs 的绕过路径。
3. 退出/更新安装/重启共用准备关闭入口；托盘退出也须进入该路径。正常退出有总时间上限、逐 owner 结果，失败可重试或由用户显式强退；强杀无法保证恢复要如实注明。
4. SSH、HTTP/WS、数据库、FRP 各接入自己的资源清理，先定义关闭工具是否停止进程。FRP 遵守 v1 不在关闭工具后常驻的边界；隐藏主窗口与关闭工具不能混淆。
5. 公共作用域化事件订阅：卸载早于 listen resolve 时，resolve 后立即 unlisten；Promise.all 部分成功后失败也清理；定时器不在已 disposed 后创建。
6. 工具外包局部错误边界、异步加载状态与重试/关闭入口，单工具加载失败不导致整工作台失用；重试重建错误实例，不清空其他页签。
7. 隐藏时降低监控/可视更新频率，恢复时取最新状态；不暂停协议心跳、不无提示中止用户下载。所有缓冲都有上限。

**验收**：所有关闭入口行为一致；编辑未保存关闭可取消；退出时长任务可取消退出；快速开关页面100次订阅/定时器回到基线；隐藏再显示连接仍正常；单工具抛错其它工具可用；FRP 关闭工具后无该工具应停止的进程残留；macOS 键盘冲突按平台实测。

- 默认导入新本地数据空间，数据库、凭证、偏好实际隔离；可选合并当前空间，先预览再按类型保留本地/采用导入/保留两份，单槽数据不能伪装支持两份。
- 稳定 UID、revision、来源映射与类型化依赖保证重复导入幂等；配置复制时重映射凭证/分组引用，不自动绑定同名秘密。
- 复用维护锁、暂存 generation、持久提交日志和重启激活，保证跨多个库/Vault/偏好文件可恢复；未选数据必须保留。
- 云账户未来用于跨地点同步，当前落地真实被本地传输消费的数据/密钥适配接口，不建设登录、服务器或自动上传。
- 旧 `.pbvault` 兼容导入；现有持久化 owner 全部按专项矩阵覆盖，不能只做 SSH/Vault demo 就宣告完成。

### T16 · 工作区资源预算与缓存管理（P2）

- 先测空闲启动、单 SSH、多工具切换、隐藏10分钟、反复开关页签的 CPU/内存/句柄/订阅数；记录机器、构建模式与连接条件，再冻结回归阈值，不编造当前性能成绩。
- 框架提供可查询缓存占用与按 owner 清理入口；各插件报告 in-use 文件，清理不碰 data/vault 或活跃播放/驱动。
- 工作区可持久化工具 id/顺序等非敏感 UI 状态，不自动恢复 SSH/FRP/数据库连接，不把编辑器明文与密钥放进默认恢复快照。
- 无状态工具可按需释放；有未保存数据/活跃连接不自动淘汰。不要直接用 KeepAlive LRU 解决所有内存问题。
- 日志/缓存预算应基于测量调整；本项不扩大已明确不做的 SSH 日志轮转功能。

### 暂不建议建设

动态下载第三方插件、通用后台任务调度器、自动工作流、跨插件共享数据库、全局网络客户端强制统一、企业权限、LSP、通用进程托管平台。

原因：当前是内置受信工具集合，以上会增加维护与安全边界，不能直接解决已查到的数据、设置和退出问题。未来有两个以上真实消费方再评估公共抽象。

云账户不在此排除清单内：它是已确认后期功能，本期按 T15 预留数据身份、隔离、变更和密钥接口，账号绑定与实际同步后期实现。

## 6. 最小契约草案与兼容约束

以下用于冻结语义，实施 agent 可调整类型名；改变行为必须同步本文与测试，不得先实现再让前端猜。

| 能力 | 建议契约 | 必须保证 |
| --- | --- | --- |
| 存储信息 | activeRoot、configuredRoot、pendingMigration、availability、partitions 的值/错误状态 | 生效根与待生效根分开，统计失败不是0 |
| 迁移计划 | id、source、target、phase、error；plan/cancel/status | plan 不提前写业务文件，cancel 不能删源 |
| 任务进度 | taskId、owner、phase、processedBytes、totalBytes可空、sequence | 可按 id 查询最新快照，丢事件可恢复 |
| 设置更新 | patch、expectedRevision；返回值含 revision 与实际生效值 | 内部 key 不开放，失败不伪装成功 |
| 凭证保护 | backend、availability、fallbackReason（无秘密） | 不能把 mock 标为 system-keyring |
| 引用扫描 | references、scanStatus、revision | unknown 与0不同，强删显式 |
| 关闭上下文 | reason=tab/exit/restart/update，prepareClose、dispose | 所有入口统一，异步完成可等待，有时间上限 |
| 通用错误 | code、message、requestId、retryable可选 | 无秘密，旧 String 错误先适配，不自动重试写操作 |
| 数据空间/传输 | spaceId、generationId、entityUid、revision、inspectId/planId | 空间与账户不同；计划可失效，引用须映射；详见 T15 专项 |

兼容要求：

1. 框架/插件 contracts 各自唯一声明；旧接口保留过渡包装或在同一个提交同步所有消费方。
2. 事件订阅与快照查询同时存在，不能只依赖瞬时事件；进度不保存用户内容。
3. 新增内部状态版本化、原子保存；读未知较新版本时只读/拒绝，不能覆盖。
4. 所有 schema migration 只追加，修复旧数据用追加迁移或明确兼容修复器。
5. 修改 keyring service/app identifier 会影响旧凭证访问，未经单独需求禁止修改。
