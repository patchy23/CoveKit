## 2. C0：默认空间 uid 化（实施计划）

### 2.1 现状核对（只读）

| 事实 | 位置 | 后果 |
| --- | --- | --- |
| 默认空间 id 是字面量 `"default"` | `framework/context.rs:23` | **每台机器同名**，「全局唯一」不成立 |
| 默认空间是 `LegacyFlat` 布局：数据直接在 `<设备根>/{data,vault}`，不在 `spaces/default/` 下 | `framework/context.rs:30,37`、`framework/space/mod.rs:160` | 没有可改名的空间目录，uid 化是**身份层**的事 |
| 默认空间的密钥库走历史 service `com.patchy23.patchybox`（无后缀兼容位，注释明写「未经单独需求禁止改动」） | `framework/secure_store/key/mod.rs:19` | uid 化**不动密钥库**，否则既有凭证不可读 |
| 空间切换 = 写 `activeSpaceId` 自举 + `restart_required: true` | `framework/data_transfer/commands.rs:259-289`、`framework/space/mod.rs:128-153` | 活动空间记录在设备自举配置里 |
| 导出包 manifest 的 `sourceSpaceId` 直接写 `"default"` | `framework/data_transfer/commands.rs:307`、`import.rs:475`（夹具）等 | 两台机器的默认空间包**来源 id 相同**，L3 映射键会误判同源 |
| 前端没有 `"default"` 字面量假设 | `src/` 全局检索为空 | uid 化只需动后端 |

### 2.2 目标与分层

**第 1 层（本批做）：身份 uid 化，不动数据目录与密钥库。**

- 设备自举新增 `defaultSpaceUid`：首次启动生成 UUIDv4；升级安装（已有 `activeSpaceId` 而无 uid）补生成并写入；一旦生成**永不变更**。
- 默认空间的「身份」= 该 uid；字面量 `"default"` 降级为**历史别名**，只用于读取旧自举/旧索引的兼容。
- 导出 manifest 的 `sourceSpaceId`、L3 映射键 `(来源 uid, 数据集, 记录 id)` 一律用 uid。
- 「是否默认空间」改为角色判定（`is_default`），不再比较 id 字面量。

**第 2 层（单独裁决，本批不做）：布局统一。**

- 把 LegacyFlat 数据搬进 `spaces/<uid>/generations/1/`，解除 L1「不搬动真实数据」红线。
- 收益：少一个特例；代价：升级搬迁要在启动维护窗口做，失败要回退，是真正的风险面。
- 建议：**先不做**。同步（§4）与合并导入都不依赖目录形状；等 uid 身份跑稳再议。

### 2.3 实施步骤（文件 → 改动）

| 文件 | 改动 |
| --- | --- |
| `framework/space/mod.rs` | 自举新增 `KEY_DEFAULT_SPACE_UID`；`resolve_active` 在缺失时生成并写入（首启与升级同一入口）；`SpaceResolution` 增 `space_uid`；`is_default` 判定兼容「uid 与历史别名」两种表示 |
| `framework/context.rs` | `DEFAULT_SPACE_ID` 保留为历史别名常量并注释「只用于兼容读取，新写入一律用 uid」 |
| `framework/data_transfer/commands.rs` 等 | 导出时 `sourceSpaceId` 取 uid；uid 缺失（写入失败）时**拒绝导出**并给明确错误，不拿 `"default"` 发包 |
| `framework/space/index.rs` | 索引读取兼容「键为 uid 或历史别名」；`SpaceRecord` 结构与展示名不动 |
| `framework/secure_store/key/mod.rs` | 仅注释更新：「默认空间 uid 化后仍沿用历史 service，属刻意兼容」 |
| 测试 | 首启生成、升级补生成、已生成不覆盖（幂等）、导出 manifest 的 sourceSpaceId = uid、默认空间判等在两种表示下一致 |

### 2.4 不变量与回滚

- uid 生成即永久；生成或写入失败**不阻断启动**（沿用现有「写失败不阻断但必须可见」口径），但导出/同步在 uid 缺失时拒绝。
- 本层不动数据目录、不动密钥库、不动记录内容：回滚 = 撤代码，数据无感。

## 3. C 裁决固化（回写 L3 方案）

- **uid 跟数据走**：包是来源 uid 的快照；导入后数据归属**当前 uid**。
- **不能直接导入 uid**：包内 `sourceSpaceId` 只做留档与同源识别，永远不作为导入目标。
- **两种导入模式**：
  - **合并**：按 L3 方案的冲突三选语义合进当前空间（未选数据不丢）。
  - **覆盖**：包内容**整体替换**当前空间——目标空间内容 = 包内容，不经冲突判定；强确认 + 二次口令 + 写保护与代际机制同合并；旧内容按「保留上一代」兜底，不提供图形回退入口。
- 以上已回写 L3 方案 §1.1 与 §14.4。

## 4. A 方案：同一 uid 多端同步（延迟可接受）

### 4.1 核心判断：同步 = 自动化的「导出包 + 合并导入」

不发明新的同步协议：对端的快照就是一个 `.pbdata` 包，拉下来走 **L3 合并引擎**（同一套冲突三选、幂等映射、代际提交）；本端改动打包上传。这带来三个免费性质：

- **服务端零知识**：线上一律密文包（AES-256-GCM），服务端只见 uid、设备、时间戳、摘要这些元数据；
- **冲突语义唯一**：手动导入与自动同步共用同一套判定，不存在两套行为；
- **离线天然可用**：同步只是多一个传输层，断网时本地全部功能不受影响（§8.2 的离线口径不破）。

### 4.2 语义与边界（延迟同步的代价必须显式接受）

- **删除不同步**（任务书 §5.5：v1 快照导入不应用删除）：同步合并只做「新增 + 冲突决策」，删除只在本地生效。要在所有设备清掉一条记录，只能走「覆盖」模式整体上传替换（对应 §3 的覆盖导入），文档必须写明。
- 延迟窗口内两台设备都改了同一条记录 → 冲突进「待决策」队列，提示用户选「保留本地/采用远端」，**不静默覆盖**（沿用 L3 默认「保留本地」）。
- 「不能太久」的实现：启动时拉取合并一次 + 变更后防抖上传（建议 60s 防抖）+ 手动「立即同步」入口。

### 4.3 服务端形态（三选）

| 选项 | 内容 | 取舍 |
| --- | --- | --- |
| ① 自建最小服务（**推荐**） | 在已有的腾讯云服务器（152.136.231.68）上跑一个窄服务：账号/设备注册 + 包存储 + 摘要列表，数据全密文 | 零知识、完全可控、无供应商锁定；用户已有机器，边际成本≈0 |
| ② 对象存储直存（COS） | 无服务端逻辑，包直接存桶 | 少一层服务，但账号/设备注册仍需一个最小后端，省不掉 |
| ③ 第三方同步盘 | 用户自己把包放进网盘目录 | 等于现在的手工导出，没有自动性，不满足「不能太久」 |

### 4.4 阶段切分

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| A1（本方向第一步） | 手动/定时快照上传 + 对端启动时拉取合并 | L3 合并引擎、C0 uid 化、服务端① |
| A2（将来） | 记录级修订与 tombstone、增量同步 | 记录级稳定 UID/修订（L1 曾移出归 L3），属下一层架构 |

### 4.5 裁决项

- **A-D1 服务端形态**：建议 ① 自建最小服务。
- **A-D2 同步触发**：建议 启动拉取 + 60s 防抖上传 + 手动立即同步。
- **A-D3 冲突默认**：建议「保留本地 + 新增直接落」，冲突进队列提示决策。

## 5. B 方案：切换账号 = 切换空间（不重启）

### 5.1 现状

切换空间只做两件事：写 `activeSpaceId` 自举 + 返回 `restart_required: true`（`commands.rs:259-289`），前端走 relaunch。必须重启的原因：

- **后端**：`DataContext` 在启动时固定一次（空间 id 与代际的解析见 `context.rs`）；插件的 DB 句柄、SSH 连接池、隧道/FRP 进程都绑定当前空间。
- **前端**：各 store（ssh/vault/settings/favorites/tasks/tools）持有空间作用域的已加载数据；打开中的页签与路由。

### 5.2 软重启路径（推荐）

进程不退出，按序做六步，任何一步失败**回退到自动 relaunch**（现有「切换并重启」路径保留）：

1. **断连**：断开所有打开的资源——SSH 连接/终端/隧道、FRP 进程、数据库连接，走既有「切换清理」协调入口（与应用退出清理同一套，只是不退出）；
2. **冻结**：取维护互斥，前端进入「切换中」遮罩，写保护挂上；
3. **重建上下文**：后端重新解析 `activeSpaceId` + 代际，重建 `DataContext` 与空间作用域句柄；
4. **重置前端**：按「空间作用域 store 清单」逐项 reset，重路由到首页；
5. **缓存更新**：监控定时器、目录树、凭证列表随 uid 失效重建——store reset 后重新拉取自然覆盖（这就是「切换后自动更新缓存数据」）；
6. **解冻**：写保护解除，报告「已切换到空间 X」。

### 5.3 风险与受控方式

- 最大的风险是**漏重置**：某个 store 忘了 reset → 界面串了旧空间的数据。处置：空间作用域 store 清单**入本文档受控**，并加一条前端行为测试「切换后所有清单内 store 的 uid 指纹与目标空间一致」。
- 打开中的连接被断开是硬体验损失，但切换空间本来就是「换一套数据」，断连是正确语义；UI 上给确认（「切换将断开 N 个连接」）。

### 5.4 注册路径

注册发生在**本地默认空间**（默认 uid）下：注册时把当前默认 uid 绑定到新账号；此后登录其他账号 = 切换到该账号 uid 的空间（本机没有该 uid 的空间则新建一个承载空间，数据由 §4 同步拉取）。「登出」= 切回默认 uid。

### 5.5 裁决项

- **B-D1 切换方式**：建议软重启 + 失败回退自动 relaunch。
- **B-D2 空间作用域清单**：建议清单入文档受控 + 行为测试断言（防漏重置）。

## 6. D 方案：凭证可用性（参考同类项目）

### 6.1 同类项目通行做法（2026-09-16 查证）

| 项目 | 做法 | 启示 |
| --- | --- | --- |
| VS Code Settings Sync | 秘密不进同步：引用（设置项）同步，秘密存系统密钥库，到新机提示重录；冲突给 Accept Local/Remote 并保留本地备份 | 「引用走、秘密留、到端补录」是主流默认 |
| JetBrains Backup and Sync | 密码默认不同步：密码存 OS 密钥库，或 KeePass 格式库（c.kdbx + 主密码） | 密码走「主密码加密的库」 |
| Chrome Sync | 密码**永远加密**同步；可选自定义口令 = 端到端（服务端零知识）；口令重置 = 云端数据作废；密码身份用业务键（来源域 + 用户名字段拼 unique tag），不用内部 id | 「口令即加密材料」「身份用业务键」 |
| 1Password / Bitwarden | 凭证随库走，整库端到端加密 | 「携密走」的前提是 E2E |
| WinSCP / FileZilla 导出 | 只导配置不导密码，到端重输 | 「不导密码」是行业常态，不是缺陷 |

### 6.2 归纳出的两条正交选择

- 秘密**带不带**：默认不带（VS Code/JetBrains 式，到端补录）；勾选带（Chrome/1Password 式，口令 E2E 打包——L2 已有「携带凭证」能力）。
- 凭证的**身份用业务键**（名称 + 用户名/主机，Chrome unique tag 思路），不用内部 id——这正是 L3 三级判定里的业务键命中。

### 6.3 我们的方案（默认 + 可选 + 补救）

- **路径 1（默认）**：导入后凭证保留元数据（名称/类型/用户名），标「待补录」；引用它的档案显示「凭证待补录」徽标；在档案上或凭证列表就地补录一次，写入当前 uid 密钥域，全部引用立即恢复可用。
- **路径 2（可选，导出时勾选）**：携密导出 → 导入即用目标空间密钥重加密落库，零补录（现有能力，只是默认不勾）。
- **路径 3（补救，本方案的关键新增）**：合并导入时对**没随包带出的凭证引用**做业务键匹配，预览里给「采用本地同名凭证」的显式入口——勾选即把档案的凭证引用重定向到本地凭证；不勾则保持待补录。**不自动绑定**（L2 已定），但把「无法使用」变成「一次点击」。
  - 导入报告列出 N 条待补录；凭证列表页支持筛选「待补录」并逐条补录。
- **不做**：跨 uid 共享凭证（D 裁决）；`known_hosts` 不进包（已有裁决）。

### 6.4 裁决项

- **D-D1 是否提供「采用本地同名凭证」入口**：建议提供、默认不勾（显式动作才重定向引用）。
- **D-D2 待补录入口位置**：建议两处都做（凭证列表筛选 + 档案内联徽标就地补录）。
