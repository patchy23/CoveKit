## 1. 本批交付与明确不做

### 1.1 交付

| # | 交付物 | 验收口径 |
| --- | --- | --- |
| 1 | 合并导入：数据包 → **当前空间**（与隔离导入并列的第二种模式） | 冲突逐条预览与处置；未选中的本地数据一条不掉 |
| 2 | 冲突判定与三选处置：保留本地 / 采用导入 / 保留两份 | 同名不同 UID、同 UID 不同来源都进冲突列表，不自动覆盖 |
| 3 | UID 与引用重映射：按映射重写引用，必要时分配新 UID | 保留两份的档案引用新凭证或明确复用的本地凭证，不出现指向被覆盖对象的悬空引用 |
| 4 | 导入映射（`sourceLineage`）与幂等：重复导入同一包不重复创建 | 再导入只出「已识别（相同，跳过）」与「待决策（不同）」；显式「作为新副本」才新增 |
| 5 | 代际（generation）提交与回滚：克隆当前代 → 应用 → 校验 → 切指针 | 注入故障不部分提交；各步强杀后可恢复到完整的旧代或新代，无混合库 |
| 6 | 空间写保护：提交窗口与「待激活」期间拒绝写入并给出可见提示 | 提交期间插件写入得到明确错误文案，不静默丢弃 |
| 7 | 前端导入向导「合并到当前空间」模式：冲突决策、影响面、报告与重启 | 预览显式显示目标空间名、冲突计数、被影响的本地对象 |

三条直接影响设计的结论：

1. **合并导入必须自己造「代际」**：当前空间已有数据，隔离导入那套「目标目录此前不存在 → rename 即原子」的等价性不成立。要克隆当前代 + 指针切换 + 启动清理（§6）。
2. **必须新增真正的写保护**：`maintenance_guard` 只做互斥，拦不住运行中的插件写入；没有写保护就有「克隆之后本地又改了、一切到新代就丢」的分裂风险（§6.3）。
3. **契约扩展可以不改命令名**：任务书 §9 早已把 `data_import_plan` 的「目标/模式、冲突决策」与 `data_import_commit` 的 `expectedRevision` 写进冻结契约，本批是**补齐已冻结名下的参数**，不动 `PUBLISHED` 冻结表（§8）。

## 3. 待裁决项（D1–D8）

| # | 决策 | 建议 | 理由与代价 |
| --- | --- | --- | --- |
| D1 | 提交后如何激活新代 | **写活动指针 + 要求重启**（沿用 §13.4「重启生效」） | 运行中的实例按旧代路径写盘；热切换会让内存态与磁盘分叉，重启是最小可信边界。代价：导入后要重启一次 |
| D2 | 是否允许「稍后重启」 | **允许，但维持写保护**：写入被拒 + 界面常驻条幅「导入已应用，重启后生效」 | 任务书 §7 第 6 条允许稍后重启，前提正是维持写保护；否则期间的写入会落到即将被弃用的旧代 |
| D3 | 写保护做在哪一层 | **框架写入口 + 空间级标记**，统一校验 `PluginDb` 事务写、Vault 保存、偏好/设置保存三处 | 适配器与插件都绕不过这三个入口；只加互斥拦不住运行中的写入。代价：三处写路径各加一次校验与文案 |
| D4 | 冲突默认处置 | **按任务书 §5.4 表格默认，可逐条改**：SSH 档案/分组/隧道/书签/凭证默认「保留本地」；收藏与最近使用默认并集 | 默认值决定用户什么都不点时发生什么——宁可不覆盖本地，也不静默替换用户的现有配置 |
| D5 | 「保留两份」的依赖链范围 | **复制整条被选中的依赖链**：档案与其引用的凭证/分组/隧道/书签各自获得新 UID；凭证若选「保留本地」，则新档案引用**本地**凭证 | 任务书 §5 第 3 条已定；禁止出现「复制了档案却仍指向被覆盖的旧凭证」 |
| D6 | 记录级映射（`sourceLineage`）落点 | **空间级文件 `spaces/<id>/import-map.json`**，原子替换，不随代际切换 | 放代际目录会被每次提交复制一份并产生版本歧义；放设备级索引会让索引膨胀。文件缺失即视为空表，零迁移 |
| D7 | `expectedRevision` 的定义 | **目标空间当前代的目录摘要**（复用 `storage::scan` 的清单 + 文件摘要），提交前重算，不一致即拒绝并要求重新预览 | 任务书 §7 第 2 条要求「重核目标 revision」；文件摘要就是「本地是否变化」的可验证定义 |
| D8 | 是否新增命令 | **不新增命令名**，只补参数：plan 加 `mode`/`conflicts`，commit 加 `expectedRevision` | 冻结表改名会挂契约测试；§9 已把这两个参数写进冻结契约 |

补充两条不构成裁决、但要记录的口径：

- 上一代（旧 generation）**保留到下一次成功提交**，之后由启动维护清理；更早的代际一律清理（用磁盘换可预期性）。
- 合并**从不删除**本地记录：任务书 §5.5 已定「缺记录不表示远端删除」，本批不实现任何删除应用。

## 4. 合并导入语义

### 4.1 冲突的三级判定（谁和谁算「同一个东西」）

| 级 | 判据 | 结论 |
| --- | --- | --- |
| ① 映射命中 | `import-map.json` 中有 `(sourceSpaceId, dataset, sourceId) → targetId` | 同一来源再次导入：内容相同 → 「已识别（跳过）」；不同 → 「待决策」 |
| ② 主键命中 | 目标空间已存在同 `id` 记录 | 同 id 不同来源：比内容 → 相同「已识别」，不同「待决策」 |
| ③ 业务键命中 | owner 自定的业务标识（档案/分组按名称、书签按「档案 + 路径」、凭证按名称 + 用户名） | 同名不同 id：进冲突列表，默认「保留本地」 |

判定在**适配器**内完成（业务键只有 owner 知道），框架负责提供映射表、目标空间上下文与统一 UID 分配，并校验不变量。

### 4.2 每类默认处置（任务书 §5.4 落到本批数据集）

| 数据集 | 新增 | 已识别且相同 | 冲突（不同） | 备注 |
| --- | --- | --- | --- | --- |
| `ssh.profiles` | 直接写入 | 跳过 | 保留本地（默认）／采用导入／保留两份 | 「采用导入」只替换该记录的字段，不清空整表 |
| `ssh.groups` | 直接写入 | 跳过 | 同上 | 分组改名不隐式重绑定档案 |
| `ssh.tunnels`、`ssh.bookmarks` | 跟随所属档案写入 | 跳过 | 同上 | 依 L2 D4：随档案带出，不单独勾选 |
| `vault.credentials` | 直接写入（用目标空间密钥重新加密） | 跳过 | 保留本地（默认）／采用导入／保留两份 | 「采用导入」须先展示影响面（§4.4） |
| `core.favorites` | 有序去重并集，保留本地顺序，新项追加 | — | — | 不用导入顺序覆盖本地顺序 |
| `core.recent_tools` | 保留本地顺序，导入项追加并按上限截断 | — | — | 不把跨设备时间戳当可信排序 |

「待补全」判定沿用 L2：包内档案引用了没随包带来的凭证 → 写入后仍标待补全，**不自动绑定**同名本地凭证。

### 4.3 UID 分配与引用重映射

分两阶段，顺序不可颠倒（任务书 §5 第 3 条）：

1. **先分配全部目标 id**：计划阶段为每条记录定出 `targetId`（沿用本地 id／采用导入仍用本地 id／保留两份则新 UUIDv4），汇总成 `IdMap`。
2. **再按映射写引用**：`apply_to_staging` 必须经 `IdMap` 重写所有引用字段，写完读回自查（L2 已定的契约）。

框架层校验的不变量（任一不成立即整批失败）：

- 写入后不存在指向「本次未写入、本地也不存在」对象的引用；
- `KeepBoth` 记录的依赖链成员在本次也必须是 `Insert`/`KeepBoth`；
- 同一批里多条档案引用同一来源凭证时**共享一份**导入凭证，不复制 N 份（任务书 §5 第 4 条）。

### 4.4 影响面（共享凭证替换）

选「采用导入」替换某凭证前，必须算出**当前空间所有引用该凭证的记录**并展示（任务书 §5 第 5 条）：影响面由适配器对本地记录调 `enumerate_references` 得到，框架汇总计数交给界面，用户确认后该决策才允许进入提交。替换共享凭证会改变多个本地档案的连接行为，这是必须被看见的动作。

### 4.5 幂等与「可能恢复已删项」

- 映射命中但本地已不存在的记录（本地删过）：默认**不复活**，标「可能恢复已删项」，在预览里单列，用户显式选择才写入（任务书 §5.5）。
- 显式「作为新副本导入」：分配新 `targetId`，映射新增一条记录，与既有目标并存。
- 同一包重复导入的默认结论：内容全同 → 报告「本次无新增」；有差异 → 只对差异项出决策，相同项不再打扰。

## 5. 导入映射（sourceLineage）

### 5.1 结构与落点

文件：`<设备根>/spaces/<空间 id>/import-map.json`（空间级、不随代际切换、原子替换写入）。

```
{
  "version": 1,
  "entries": [
    {
      "sourceSpaceId": "<来源空间 id>",
      "dataset": "ssh.profiles",
      "sourceId": "<来源记录 id>",
      "targetId": "<本空间记录 id>",
      "packageIds": ["<包 id>"],
      "lastSeenAt": "<RFC3339>"
    }
  ]
}
```

- 只记「来源 → 目标」的对应与最近见到它的包，**不记内容摘要**：内容比较由适配器按业务字段做，摘要会随字段演进失效。
- 键唯一性：`(sourceSpaceId, dataset, sourceId)` 唯一；一条来源记录可被多次导入成多个目标（多行、用 `packageIds` 区分批次）。
- 写入时机：**写代际指针之前、同一写保护窗口内**，先写 `.import-map.json.tmp` 再原子替换。
- 自愈性：映射是「上次导入的意图记录」。映射写入后若提交失败、或文件被外部改坏，命中映射但目标不存在的条目在下次预览会落到「可能恢复已删项／新增」，不会造成错误覆盖。
- 兼容：文件缺失、`version` 不认识、条目字段非法 → 视为**空映射**并重新判定，不阻断导入（映射是幂等依据，不是正确性的唯一来源）。

### 5.2 与设备级索引的分工

设备级 `spaces` 索引里的 `importedFrom` 继续只做「该包导入过／导入到哪个空间」的提示与留档；记录级事实以空间内 `import-map.json` 为准。

## 6. 代际（generation）提交、写保护与回滚

### 6.1 目录与指针

现状：空间内容根 = `<设备根>/spaces/<id>/generations/<n>`，`n` 由启动解析给出且恒为 1。本批引入：

- **活动代指针**：设备级 `SpaceRecord` 增加 `activeGeneration: u64`，**缺失视为 1**——旧安装零迁移，无需任何数据动作。
- 代际目录只增不改：新代永远写进 `generations/<n+1>` 的新目录，**不原地修改当前代**。
- 启动解析（`framework/space/mod.rs` + `context.rs::init`）仍是唯一的代际来源；写指针只在本批的提交链路与空间切换里发生，不开第二处入口。

### 6.2 提交顺序（合并导入）

1. 取 `maintenance_guard`（与根迁移、空间切换、既有导入互斥）；
2. 重核 `expectedRevision`：目标空间当前代的目录摘要与 plan 时不一致 → 拒绝，要求重新预览（D7）；文件摘要不一致同样拒绝（L2 已有）；
3. 置**写保护**（§6.3），窗口从此刻持续到第 10 步结束；
4. 克隆当前代 → `spaces/.patchybox-staging-<planId>/generations/<n+1>`（逐文件复制，内容与 `generations/<n>` 一致）；
5. 逐数据集 `apply_to_staging`（携带 `IdMap` 与冲突决策），写入后读回自查；
6. 校验：条数对账 + §4.3 的三条不变量；
7. 写 `import-map.json`（先写 `.tmp` 再原子替换）；
8. 写 `pending-activation.json`（记录 `{ fromGeneration: n, toGeneration: n+1, planId }`）；
9. `rename` 暂存代目录 → `spaces/<id>/generations/<n+1>`；
10. 写 `activeGeneration = n+1`，清暂存目录，释放 `maintenance_guard`（**写保护维持到重启**，§6.5）；
11. 产出报告：新增／替换／跳过／待补全／可能恢复已删项的条数与「需重启」。

第 1–10 步任何失败：删暂存目录、`activeGeneration` 不动、当前代原样 → 等价于本次导入没发生。第 9、10 步顺序固定「先代目录、后指针」：指针未写时代目录无人引用，指针写了代目录必然已存在，不存在「指到半个空间」的中间态。

### 6.3 写保护（本批新增能力）

- 实现：`framework/context.rs` 增加进程内写保护状态（`WriteBarrier`）+ 空间级持久标记 `<设备根>/spaces/<id>/pending-activation.json`（已应用但未激活的代）。
- 校验点（D3）：`PluginDb` 事务写入口、Vault 保存、偏好/设置保存三处。被拒时返回明确文案「数据维护中，导入完成后需重启」，**不得**静默丢弃，也不得写进旧代。
- 为什么必须有：克隆发生在第 4 步，若插件在第 4–10 步之间写盘，这些写落在旧代；一切到新代就等于丢失。写保护把这段窗口焊死。
- 提示：写保护期间界面顶部常驻条幅（正在应用导入／需重启），附「立即重启」入口。

### 6.4 回滚与「回滚后继续操作」的边界

- 指针写入前失败 → 删暂存，当前空间零变化，这就是本批的「回滚」。
- 指针写入后**不自动回退**：数据已是完整新代，回退等于用旧快照覆盖用户之后的新修改（任务书 §7 第 8 条明确禁止无提示覆盖）。上一代保留到下次成功提交，仅作故障兜底与人工排查，不提供图形回退入口。

### 6.5 崩溃恢复与「稍后重启」

- 启动维护阶段（沿用既有清理入口）：
  - 扫 `spaces/` 下的 `.patchybox-staging-*`：无引用即删（L2 口径）；
  - `pending-activation.json` 存在且目标代目录已就位而指针未写 → **补写指针**（提交被打断在最后一步）；两者都已就位 → 只清标记；
  - 代际清理：每个空间只保留**当前代 + 上一代**，更早的删除；
  - 索引里的 `activeGeneration` 指向不存在的代目录 → 报错并拒绝加载该空间（fail-fast，不猜）。
- 「稍后重启」（D2）：提交完成即写指针，运行中的实例仍在旧代路径上，由写保护挡住写入、界面条幅提示重启；重启后标记清除、写保护解除、新代生效。

## 11. 风险与处置

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 克隆成本随空间体积线性增长（将来 DB 插件有大 SQLite 文件） | 提交变慢、写保护窗口变长 | 先按实际规模记录耗时并写进验证矩阵；超过可接受阈值再考虑「只复制将被修改的数据集」 |
| 写保护窗口内用户操作被拒 | 体感像卡死 | 条幅说明 + 明确错误文案；窗口目标 2 秒内（当前数据量级） |
| 用户不重启且绕过写保护 | 内存态与磁盘代际分叉 | 写保护三处写入口；启动维护按 `pending-activation.json` 纠正并清标记；不提供 CLI 写口 |
| `import-map.json` 被外部改坏 | 幂等失效 | 命中映射但目标不存在的条目退化为「新增/可能恢复已删项」（§5.1 自愈） |
| 保留两份堆积重复凭证 | 空间变乱、重复条目 | 预览显示「将新增 N 条凭证」，报告可查 |
| 旧安装迁移 | 升级即坏 | `activeGeneration` 缺失默认 1、新增文件缺失视为空、不改动既有 `generations/1` 内容 |
| 目标代目录已存在时 rename 失败 | 提交中止 | 新代号单调递增（n+1）且提交前先校验目录不存在 |
