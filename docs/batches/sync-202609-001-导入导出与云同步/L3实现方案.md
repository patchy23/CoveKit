## 1. 本批交付与明确不做

### 1.1 交付

| # | 交付物 | 验收口径 |

三条直接影响设计的结论（2026-09-16 按用户裁决修正）：

1. **合并导入不需要克隆目录、不需要代际**：SSH 等 owner 的数据在 SQLite 内，单个 `IMMEDIATE` 事务即原子（崩溃自动回滚）；偏好类是单文件原子替换；凭证不进包。「跨存储原子」的剩余窗口由导入映射的幂等自愈与导入前快照承接（§6）。原「代际克隆 + 指针切换 + 重启激活」设计被用户否决（「不能重启应用」）。
2. **写保护收缩为「提交窗口内写禁用」**：`maintenance_guard` 只是互斥；提交窗口（亚秒级）内前后端各加一层禁用即可，不延伸到任何「待重启」状态。
3. **契约扩展不改命令名**：任务书 §9 已把 `data_import_plan` 的「目标/模式、冲突决策」与 `data_import_commit` 的 `expectedRevision` 写进冻结契约，本批是**补齐已冻结名下的参数**，不动 `PUBLISHED` 冻结表（§8）。

## 4. 合并导入语义

### 4.1 冲突的三级判定（谁和谁算「同一个东西」）

| 级 | 判据 | 结论 |
| --- | --- | --- |
| ① 映射命中 | `import-map.json` 中有 `(sourceSpaceId, dataset, sourceId) → targetId` | 同一来源再次导入：内容相同 → 「已识别（跳过）」；不同 → 「待决策」 |
| ② 主键命中 | 目标空间已存在同 `id` 记录 | 同 id 不同来源：比内容 → 相同「已识别」，不同「待决策」 |
| ③ 业务键命中 | owner 自定的业务标识（档案/分组按名称、书签按「档案 + 路径」、凭证按名称 + 用户名） | 同名不同 id：进冲突列表，默认「保留本地」 |

判定在**适配器**内完成（业务键只有 owner 知道），框架负责提供映射表、目标空间上下文与统一 UID 分配，并校验不变量。

### 4.2 每类默认处置（任务书 §5.4 落到本批数据集）

| 数据集 | 新增 | 已识别且相同 | 冲突（不同） | 备注 |
| --- | --- | --- | --- | --- |
| `ssh.profiles` | 直接写入 | 跳过 | 保留本地（默认）／采用导入／保留两份 | 「采用导入」只替换该记录的字段，不清空整表 |
| `ssh.groups` | 直接写入 | 跳过 | 同上 | 分组改名不隐式重绑定档案 |
| `ssh.tunnels`、`ssh.bookmarks` | 跟随所属档案写入 | 跳过 | 同上 | 依 L2 D4：随档案带出，不单独勾选 |
| `vault.credentials` | **不进包**（2026-09-16 裁决：跨 uid 不导凭证） | — | — | 档案引用未随包的凭证 → 待补录，或显式「采用本地同名凭证」（§4.4） |
| `core.favorites` | 有序去重并集，保留本地顺序，新项追加 | — | — | 不用导入顺序覆盖本地顺序 |
| `core.recent_tools` | 保留本地顺序，导入项追加并按上限截断 | — | — | 不把跨设备时间戳当可信排序 |

「待补全」判定沿用 L2：包内档案引用了没随包带来的凭证 → 写入后仍标待补全，**不自动绑定**同名本地凭证。

### 4.3 UID 分配与引用重映射

分两阶段，顺序不可颠倒（任务书 §5 第 3 条）：

1. **先分配全部目标 id**：计划阶段为每条记录定出 `targetId`（沿用本地 id／采用导入仍用本地 id／保留两份则新 UUIDv4），汇总成 `IdMap`。
2. **再按映射写引用**：`apply_to_staging` 必须经 `IdMap` 重写所有引用字段，写完读回自查（L2 已定的契约）。

框架层校验的不变量（任一不成立即整批失败）：

- 写入后不存在指向「本次未写入、本地也不存在」对象的引用；
- `KeepBoth` 记录的依赖链成员在本次也必须是 `Insert`/`KeepBoth`；
- 同一批里多条档案显式采用同一本地同名凭证时**共享该本地凭证**，不产生副本（任务书 §5 第 4 条的同源共享语义）。

### 4.4 凭证引用处置（凭证不进包后的两种结局）

凭证不随包导入（2026-09-16 裁决），因此合并导入不再出现「凭证替换」。导入档案的凭证引用只有两种结局：

- **待补录**（默认）：保留引用的元数据（凭证名称/类型/用户名），标「凭证待补录」，就地补录一次即恢复；
- **采用本地同名凭证**（显式勾选）：按业务键（名称 + 用户名/主机）匹配本地凭证，勾选后档案的引用重定向到该本地凭证；预览时展示影响面——「本地凭证 X 将被 N 条导入档案引用」（由适配器对本地记录调 `enumerate_references` 汇总），**不自动绑定**。

### 4.5 幂等与「可能恢复已删项」

- 映射命中但本地已不存在的记录（本地删过）：默认**不复活**，标「可能恢复已删项」，在预览里单列，用户显式选择才写入（任务书 §5.5）。
- 显式「作为新副本导入」：分配新 `targetId`，映射新增一条记录，与既有目标并存。
- 同一包重复导入的默认结论：内容全同 → 报告「本次无新增」；有差异 → 只对差异项出决策，相同项不再打扰。

## 5. 导入映射（sourceLineage）

### 5.1 结构与落点

文件：`<设备根>/spaces/<空间 uid>/import-map.json`（空间根下、原子替换写入）。

```
{
  "version": 1,
  "entries": [
    {
      "sourceSpaceId": "<来源空间 id>",
      "dataset": "ssh.profiles",
      "sourceId": "<来源记录 id>",
      "targetId": "<本空间记录 id>",
      "packageIds": ["<包 id>"],
      "lastSeenAt": "<RFC3339>"
    }
  ]
}
```

- 只记「来源 → 目标」的对应与最近见到它的包，**不记内容摘要**：内容比较由适配器按业务字段做，摘要会随字段演进失效。
- 键唯一性：`(sourceSpaceId, dataset, sourceId)` 唯一；一条来源记录可被多次导入成多个目标（多行、用 `packageIds` 区分批次）。
- 写入时机：**同一提交窗口内**（事务落定之前），先写 `.import-map.json.tmp` 再原子替换。
- 自愈性：映射是「上次导入的意图记录」。映射写入后若提交失败、或文件被外部改坏，命中映射但目标不存在的条目在下次预览会落到「可能恢复已删项／新增」，不会造成错误覆盖。
- 兼容：文件缺失、`version` 不认识、条目字段非法 → 视为**空映射**并重新判定，不阻断导入（映射是幂等依据，不是正确性的唯一来源）。

### 5.2 与设备级索引的分工

设备级 `spaces` 索引里的 `importedFrom` 继续只做「该包导入过／导入到哪个空间」的提示与留档；记录级事实以空间内 `import-map.json` 为准。

## 6. 原地事务提交、快照与刷新（2026-09-16 重写）

> 本节取代原「代际克隆 + 指针切换 + 重启激活」设计。理由：SSH 等 owner 的数据在 SQLite 内，单事务即原子；偏好类是单文件原子替换；凭证不进包。整目录克隆 + 指针 + 重启是为「跨存储原子提交」付的过重代价，且重启被用户明确否决（「导入都是往当前的数据目录下面导，重新加载数据到内存就行」）。

### 6.1 提交顺序（原地）

1. 取 `maintenance_guard`，前端禁用相关写入口；
2. 重核 `expectedRevision`：当前空间**将被修改的存储**的摘要与 plan 时比对，不一致 → 拒绝并要求重新预览（D7）；
3. 拍**导入前快照**：把将被修改的存储（ssh.db、preferences.json、import-map.json）复制到 `<设备根>/backups/import-<时间戳>/`（保留最近 3 份，旧的由启动维护清理）；
4. 逐数据集写入：SQLite 数据集在**单个 `IMMEDIATE` 事务**内完成全部写入（`rusqlite::Transaction` 直接复用现有 `&Connection` 层函数）；文件类（preferences.json、import-map.json）先写 `.tmp` 再原子 rename；
5. 校验：条数对账 + §4.3 不变量，**在事务内、提交前**完成，失败即回滚；
6. 提交事务 + 文件 rename 落定；产出报告（新增／替换／跳过／待补录计数）。

任何失败：事务回滚 + 删除 `.tmp` 残留 → 每个存储要么完整旧要么完整新；跨数据集的「部分落定」窗口由 import-map 幂等自愈（重导时已提交的显示「已识别」，未提交的重新判定）。

### 6.2 不重启：提交后如何生效

- **后端零改动**：路径没变（原地写），后端不落空间数据缓存（逐调用读库）；打开中的 SSH 连接继续使用已协商的参数（业界常态，WinSCP/MobaXterm 同此）。
- **前端定点刷新**：提交成功后发 `space-data-changed`（携带受影响数据集清单），各插件 store 订阅并重拉；向导关闭后所在页面即为新数据。
- 兜底：漏订阅的插件在重新进入页面时自然重拉；「串旧数据」的窗口收敛为「已打开且未订阅的页面」，用前端行为测试断言清单内 store 全部响应事件。

### 6.3 写保护（收缩后）

只在**提交窗口内**（通常亚秒级）：前端禁用保存类按钮 + 后端写入口校验「导入提交中」即拒。窗口结束即解除；不存在「待激活」状态。

### 6.4 回滚与后悔

- 崩溃：事务回滚，存储级完整；重导自愈（§4.5）。
- 用户后悔（导入的内容不想要）：设置-数据管理提供「还原到导入前快照」，恢复被修改的存储；快照只保留最近 3 份。
- 没有「上一代」目录概念，不做自动回退。

### 6.5 启动维护（收缩后）

- 扫 `spaces/` 下的 `.patchybox-staging-*`：无引用即删（隔离导入仍用 staging，不变）；
- 快照目录清理：只留最近 3 份；
- 无指针、无待激活标记。

### 7.2 契约扩展（7 个方法名不变）

- `ImportContext` 增：`mode`（`NewSpace`/`Merge`）、`lineage`（来源 → 目标映射）、`conflicts`（用户决策）。

## 10. 测试与验收

### 10.1 自动化（Rust 定向 + 故障注入）

| 面 | 用例 |
| --- | --- |
| 映射表 | 读写往返、原子替换、文件缺失/损坏 → 空表、多条来源映射同一目标 |
| 事务提交 | 事务内任一写入失败 → 整库回滚、无半提交可读态；条数对账与不变量校验在事务内、提交前完成 |
| 快照与还原 | 快照与被修改存储逐字节一致；还原后可读；只保留最近 3 份；跨数据集部分落定（DB 已提交、文件未写）→ 重导时前者「已识别」、后者重新判定 |
| 计划 | 三级冲突判定各一组；默认处置表逐类；`IdMap` 无悬空引用；多条档案采用同一本地凭证只产生一份引用；`KeepBoth` 依赖闭包完整 |

| 幂等 | 同包两次导入第二次「无新增」；本地删除后重复导入不复活；显式「作为新副本」新增映射记录 |
| 命令层 | `merge` 模式缺 `expectedRevision` 拒绝；摘要不一致拒绝并提示重新预览；提交阶段 `cancel` 被拒 |
| 前端 | `mergePreview` 纯函数（默认决策、计数、可提交性）、向导模式分支与失败留步（行为用例）、i18n 键对齐 |

## 11. 风险与处置

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 提交事务持锁期间写入被暂拒 | 体感卡顿 | 窗口亚秒级 + 明确文案；`IMMEDIATE` 事务 |

| 老安装迁移（uid 化 + 平铺） | 升级即坏 | uid 方案 §3：fail-fast + 现场保留 + 密钥回读校验 |
