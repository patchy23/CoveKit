结论三条，直接影响设计：

1. **§7.2 的 generation 机制不存在**。L2 的隔离导入必须靠「目标空间此前不存在」这一点取得等价的原子性，而不是靠 generation 切换（见 §6.2）。
2. **空间只能读不能建**，而 L1 已按 2026-09-15 用户裁决收窄为「不做空间新建/切换/重命名/删除、不做界面与索引」（见[进度台账](../../进度台账.md) sync 行）。L2 的隔离导入必然要创建目标空间目录，这是本方案与既有裁决**唯一冲突点**，原列 D5，已于 2026-09-16 批准最小创建与切换入口，见当前接续状态；激活路径只能走「切换并重启」（§13.4 冻结：重启生效，不做热切换）。
3. **凭证容器先例已存在**。包容器复用 `export.rs` 的 KDF/容器写法，不新造第二套加密协议（§6.1 要求「不能自行拼接未经评审的分块加密协议」）。

## 4. 包格式 v1（`.pbdata`）

### 4.1 布局

```
magic(8B "PBDATA1\0") ‖ containerVersion(u16 LE) ‖ kdfAlgo(u8) ‖ mCost(u32 LE) ‖ tCost(u32 LE)
‖ pCost(u8) ‖ salt(16B) ‖ nonce(12B) ‖ cipherLen(u64 LE) ‖ ciphertext
```

- `ciphertext = AES-256-GCM(key = Argon2id(password, salt, m, t, p), plaintext = manifest JSON)`；**AAD = 头部字节**，改头部即认证失败（满足 §6.1「AEAD 认证格式版本及关键头字段」）。
- 明文头只含算法参数与随机量；工具名、服务器名、目录、记录清单、来源标识**全部**在密文 manifest 内（§6.1）。
- 不压缩、不打包文件、不存物理路径；记录体是逻辑 JSON。

### 4.2 manifest（密文内）

| 字段 | 说明 |
| --- | --- |
| `packageId` | UUIDv4，导出生成，用于「该包是否导入过」提示 |
| `sourceSpaceId` / `sourceSpaceName` | 来源空间（不可信，仅展示与留档） |
| `createdAt` / `appVersion` / `platform` | 仅展示 |
| `datasets[]` | `{ name, schemaVersion, policy, recordCount, sha256, records? }`，`policy ∈ portable/device-local/secret/sensitive-content/history` |
| `dependencies[]` | `{ kind, fromId, toId }`（如档案 → 凭证），导入侧据此判「待补全」 |
| `excluded[]` | 用户在预览里显式排除的类别/记录 |

### 4.3 资源上限与文件操作

- 明文 ≤ 32 MiB、单记录 ≤ 2 MiB、记录数 ≤ 50 000、JSON 深度 ≤ 64；超限**导出前**提示缩小选择，导入侧有界拒绝，不静默截断（§6.2）。
- 导入侧校验 KDF 白名单：`m ∈ [8 MiB, 256 MiB]`、`t ∈ [1,10]`、`p ∈ [1,4]`、salt 16B、nonce 12B、`cipherLen` 与文件长度一致；越界立即拒绝。
- 写包：唯一临时文件 → 刷盘 → 原子替换；覆盖已有文件先经确认，失败保留原文件。
- 解密、解析、生成全在 Rust 侧完成；秘密与完整明文不进 JS，密码不落设置文件、不进日志。

## 6. 隔离导入落地

### 6.1 新空间

- 空间 id = 小写 UUIDv4（`space::is_valid_space_id` 已按其校验）；目录 `<deviceRoot>/spaces/<id>/generations/1/{data,vault,preferences.json}`，日志与缓存落 `<deviceRoot>/{logs,cache}/<id>`（构造 `StorageLocation::partitioned` 后建目录，不手拼路径）。
- 凭证用**新空间自己的**主密钥重新加密（新空间 keyring 服务名独立，L1 已实现），源机器 keyring 不参与解密（§13.5）。
- 设备级自举新增 `spaces` 键：`{ name, createdAt, importedFrom: { packageId, sourceSpaceId, sourceSpaceName, importedAt, counts } }`；无该键的旧安装按「只有 default 空间」呈现。
- 导入留档即 `sourceLineage`（§13.2）：记来源空间 id 与原主键，本批目标主键与源相同，映射结构先就位，L3 重映射时复用。

### 6.2 原子性与失败处理

因为**目标空间此前不存在**，本批不需要 generation 机制即可满足「不混合」：先把数据写进 `<deviceRoot>/spaces/.patchybox-staging-<planId>`，全部校验通过后**一次 rename** 成名下空间目录，最后写索引。任一步失败即删暂存目录，当前空间数据零接触（§7.2 第 3 条「未选数据不丢」自动成立：默认空间整份不参与）。

- 崩溃恢复：索引写入前崩溃 → 残留 `.patchybox-staging-*`，启动维护阶段按「只删本应用命名且无人引用」清理；索引写入后崩溃 → 空间已完整（rename 原子），索引即已存在。
- 二次导入同一 `packageId`：按 `spaces` 索引命中即提示「已于 <时间> 导入到空间 <名>」，需用户显式选择才新建第二个空间（正式去重语义归 L3）。
- 导入**不**触发登录、联网、SSH 连接、SQL 执行、系统配置修改或外部程序（§6.2）；包内 source/account/device 标签一律当不可信数据。
- 「切换并重启」走 `data_space_switch`：维护互斥 + 写活动指针 + 提示重启；重启后由启动解析生效（§13.4）。

- 适配器契约从 §13.6 的 6 个方法最终为 7 个（`describe_datasets` / `export_records` / `validate_records` / `enumerate_references` / `plan_import` / `apply_to_staging` + `owner`）：新增的 `describe_datasets` 合并了「列数据集」与「列可勾选条目」，避免预览与目录两处各算一遍。
- 凭证适配器的「写入后读回自查」放在 `apply_to_staging` 内部，而不是再加一个 `verify_staging` 方法：少一个可被忘记调用的契约面。
