## 1. 现状与缺陷（带证据）

| 项 | 现状 | 位置 |
| --- | --- | --- |
| 后端关闭协调 | prepare（可拒绝）/ dispose（5s 总超时、panic 兜底）已建 | `framework/lifecycle.rs` |
| 已注册钩子的 owner | **只有 2 个**：frp、http_ws | `plugins/frp/mod.rs:479`、`plugins/http_ws/mod.rs:55` |
| 页签关闭 | 纯前端裁决，后端收不到 `tab` | `stores/ui.ts:108` → `toolContext.ts:199` |
| 前端协调器 | 与 Rust 同形的第二套（5000ms 超时、dirty/running 兜底），互不知情 | `core/lifecycle/toolContext.ts` |
| epoch 晚到判定 | `is_current` / `note_stale_dropped` 均带 `#[allow(dead_code)]`，无消费方 | `framework/context.rs:148`、`:159` |

两个真缺陷（本次必须修）：

1. **退出顺序错**：`appClose.ts` 先 `disposeAllTools()` 再 `requestAppExit`，后端 prepare 被拒绝时用户按「取消」，前端已把工具全清完（只有 frp/http_ws 会拒绝，故平时不炸）。前端 owner 的 prepare 在退出路径上**从未被询问**：退出时「有未保存内容」是静默丢弃。
2. **契约与实现不匹配**：契约 `app_request_exit: { reason: string }`（扁平），Rust 侧形参名为 `request: Option<ExitRequest>`；前端传 `{ reason }` 无法落到该形参，`reason` 恒为缺省 `exit`。`requestAppExit('update')` 会静默降级为 `exit`。

## 2. 三项定论（用户授权按推荐执行）

| 项 | 定论 |
| --- | --- |
| 谁权威 | **Rust 唯一裁决点**：`lifecycle` 合成裁决；前端 owner 只上报自己的拒绝原因，不自行决定关闭 |
| dispose 边界 | **只在裁决通过后执行**，且两段分清：退出路径的进程级清理仍只由 `RunEvent::Exit` 执行（唯一清理点，不重复清）；页签关闭由 `app_commit_close` 内做工具级清理 |
| 单 tab 作用域 | owner 显式声明 `scopes`：默认 `EXIT_ONLY`（未声明不随页签关闭清理）；`tab` 作用域还要 `tool` 归属匹配才被询问。**本轮只有 frp 与 http_ws 声明 `TAB_AND_EXIT`**（依据见 §5） |

作用域默认值取「少清」而非「多清」：页签关闭误清全局资源（连接、进程）比晚清更难恢复。

## 3. 唯一裁决链（两段命令）

```
页面关闭（页签/退出）
  → 前端 owner 询问（只问不清理，得到 blockers）
  → app_request_close { reason, toolId?, blockers[], force? }   ← 只裁决，绝不退出
       lifecycle::prepare_close(reason, tool)  过滤：tab 只问 tab 作用域 + 同 tool 的 owner
       裁决 = 后端 blockers + 前端上报 blockers（任一侧拒绝即 proceed=false）
  → proceed=false：返回 blockers（退出原因额外 surface_veto 唤窗口 + 事件）
  → proceed=true ：前端 dispose（工具级）→ app_commit_close { reason, toolId? }
       退出族：app.exit(0)，后端清理走 RunEvent::Exit（唯一清理点）
       页签  ：dispose 该 tool 作用域的 owner（没有就一个都不清）
```

不变式：

- 两个命令都不含「先清理再裁决」的路径，**裁决未通过时任何一侧都不清理**；
- prepare 与 dispose 用同一个 `selected()` 过滤函数，询问面与清理面不可能不一致；
- `reason=tab` 必须带 `toolId`，缺失直接报错，不回落成「问全部 owner」。

## 4. W1 · 收敛唯一协商链

Rust：

- `lifecycle.rs`：`CloseScopes{tab,exit}`、`ModuleLifecycle{tool,scopes}` + `exit_only()/for_tool()` 构造器、`selected()`、`prepare_close_with(app, reason, tool)`、`dispose_with_timeout(app, reason, tool, timeout)`、`compose_decision(forced, frontend_blockers, outcome)`；`DisposeOutcome.ran` 改为 `owners: Vec<&'static str>`（诊断可见跑了谁）。
- `exit.rs`：新增 `app_request_close`（只裁决）与 `app_commit_close`（提交：退出族 `app.exit(0)`，页签族做工具级清理）；删除 `app_request_exit`（被两段取代，避免两套语义并存）；`ExitDecision` 由 `lifecycle::CloseDecision{proceed,forced,blockers,failures}` 取代。
- `lib.rs`：`RunEvent::ExitRequested` 用 `CloseDecision`；`RunEvent::Exit` 日志补打印实际清理的 owner 列表。
- 装配：`framework/mod.rs` 命令清单 + `manifest_contract_tests.rs` 期望表同步（否则契约测试失败）。

前端：

- `contracts.ts`：`app_request_close` / `app_commit_close` 入参出参；`ExitDecision` → `CloseDecision{proceed,forced,blockers,failures}`。
- `toolContext.ts`：新增 `collectToolBlockers()`；`negotiateToolClose()` 改为「前端询问 → 后端裁决 → 通过才清理 → 提交」的完整链，被拒绝时返回两侧合并的 blockers。
- `appClose.ts`：`requestAppExit` 改为同一两段链（收集全部工具 blockers → 裁决 → 清理 → 提交），返回 `CloseDecision`。
- `ui.ts` / `AppExitDialog.vue`：`started` → `proceed`；弹窗 blockers 现在含前端（未保存/运行中）与后端两侧原因。

## 5. W2 · 补齐注册面与作用域声明

| owner | 进程级资源（证据） | 本轮登记 | 作用域 |
| --- | --- | --- | --- |
| frp | frpc 子进程（`frp/runtime.rs:413 shutdown_all`） | 已登记，改用构造器 + `with_tab_scope()` | EXIT+TAB |
| http_ws | WS 会话注册表（`http_ws/ws.rs:198 close_all_sessions`） | 已登记，改用构造器 + `with_tab_scope()` | EXIT+TAB |
| ssh | 会话表 `SshState`、终端表 `TerminalState`、传输取消表 `TransferState` | **新增 dispose**（断开全部会话/终端、取消传输） | EXIT_ONLY |
| database | 连接表 `DbState`、取消表 `DbCancelState`、agent 子进程 `AgentRuntimeState` | **新增 dispose**（关闭全部连接与 agent 子进程） | EXIT_ONLY |
| dns | 只有 `DnsState(Mutex<Option<PluginDb>>)`，无会话/进程 | 不登记 | — |
| hosts | 无进程级资源（纯文件读写） | 不登记 | — |
| tts | 无进程级资源（无状态表） | 不登记 | — |

不登记的三个 owner 在代码注释里写明「无进程级资源，接入无从谈起」，避免后人误判为漏接。

**frp / http_ws 声明 `TAB_AND_EXIT` 的依据**：两个插件的前端 owner（`src/plugins/frp/toolLifecycle.ts`、`src/plugins/http-ws/toolLifecycle.ts`）已经写明「关闭工具页签会停止 frpc 进程 / 关闭全部 WS 会话」并实现了对应的前端清理——后端跟着一起关，是把两侧口径对齐（此前页签关闭只由前端停，后端只在退出时停，两侧不一致）。关页签时前端 owner 的 prepare 会先询问（有 frpc 在跑时提示「关闭后会被停止」），不是静默动作。

**ssh / database 保持 `EXIT_ONLY`**：页签关闭的释放已由前端 owner 按连接粒度完成（`ssh_disconnect` / `dbc_disconnect`），而后端只能按「整个工具」清一遍（会话按会话 id、连接按连接 id，映射都在前端），再清一次会误伤同一工具下其它页签仍在用的连接。

dns / hosts / tts 无进程级资源，登记与否都不改变行为，故不登记（后端没有需要释放的东西）。作用域模型与断言已就位，后续要启用只需在登记处加 `with_tab_scope()`。

## 6. W3 · epoch 接入

- `tasks.rs`：`TaskHandle` 记录登记时的 `epoch: Option<u64>`（上下文未初始化时为 None，测试与极早调用不误判）；`progress` / `succeed` / `fail` 在写入前判 `context::is_current(epoch)`，晚到则丢弃并 `note_stale_dropped()`。
- `context.rs`：删掉 `is_current` / `note_stale_dropped` 的 `#[allow(dead_code)]`，注释改为「消费方：`tasks` 长任务出口」。
- 如实说明：当前 `DataContext` 是 `OnceLock`、单空间单次启动，epoch 在进程存活期内不变，判定结果恒真；接入的价值是空间切换（E 批 L1）落地后**消费方不用再改**，且丢弃路径与计数已被用例覆盖。

## 9. 边界与已知限制

- **托盘菜单退出与 OS 退出**（`framework::exit::decide_exit`）现在与页面发起走同一条裁决：托盘退出不再直接 `app.exit(0)`（原来会绕过 prepare，未保存内容与进行中的任务都拦不住）；两者都没有同步询问页面的通道，因此只按后端 blockers 裁决，页面内「未保存内容」在这条路径上仍可能被丢弃——被拒绝时唤窗口并抛事件，页面给出重试 / 强制退出 / 取消。这是本轮明确的边界，不是遗漏。
- 页签关闭的 `force`（用户点「放弃并关闭」）传到后端后跳过 prepare，但清理照做、失败照报。
- 强制退出（`app_force_exit`）保持原语义：进程级标记 + 跳过拦截 + 清理照做。
