# patchyBox 架构与工程规范独立评审

> 评审日期：2026-09-12；代码基线：`1c9fcf79e5ace9e0c6cf641e2109a8eb83cadbc0`。
>
> **本次评审架构和规则本身是否合理，不是检查代码是否遵守 AGENTS。** 代码用于验证规则的实际效果，AGENTS、docs/03、docs/05 都是被评审对象，不预设它们正确。
>
> 本文是技术判断与修订建议，尚未替换生效中的规范，也未实施重构。与前两份任务书的关系：可靠性任务书处理具体风险；导入导出任务书定义产品功能；本文决定它们应采用什么边界和工程规则。
>
> 后续方案已确定：[架构重构与工程规范调整任务书](2026-09-12-架构重构与工程规范调整任务书.md)。执行时以其中 AR01–AR07 为准；本文保留评审依据，不再作为多候选路线执行。

## 1. 总体结论

**保留 Tauri + Vue 和模块化单体，不推倒重写；优先重构状态所有权、持久化上下文与公共 UI 的依赖边界；工程规范从“文件形态与数量”转向“正确性、职责、可验证的行为”。**

当前项目适合的是一组随应用发布、可信、编译期集成的功能模块。称为“插件”可以，但它们不是具有独立版本、第三方加载和权限隔离的插件平台。为尚不存在的外部插件兼容性设定“框架永远零改动”会阻碍必要演进。

最值得投入的不是统一所有目录名字或换底层技术，而是明确三件事：

1. 谁拥有某份状态，谁有权修改，何时释放。
2. UI、应用服务、业务模块、平台/存储适配之间的依赖方向。
3. 用户配置和凭证的身份、空间、版本、恢复边界，与设备运行状态分离。

云账户已是后期明确规划，本地分类导入导出为近期必做。两者足以证明数据空间和稳定身份有必要；还不足以证明现在要建设通用同步引擎、分布式事务、插件市场或事件溯源系统。

## 2. 值得保留的设计

| 设计 | 判断及保留条件 |
| --- | --- |
| Tauri + Rust 系统能力 + Vue UI | 符合桌面工具箱定位；当前问题没有构成换框架的理由。低占用仍需测量，技术栈本身不是性能保证 |
| 模块化单体、工具惰性打开 | 部署和调试成本适中；保留内置模块注册，避免改造成微服务/动态插件加载器 |
| 业务模块不直接依赖彼此实现 | 能降低联动修改与隐式共享；受控联动通过应用层协调，不是永久禁止业务协作 |
| 公共 UI 与唯一编辑器基座 | 有明确的一致性和维护价值；应区分无业务控件与接入凭证等应用服务的复合组件 |
| PluginDb 提供路径、迁移与连接骨架 | 有实际多个消费方；补齐事务和上下文即可，不需要 ORM 或每个表套泛型 repository |
| 数据库 native driver / agent / dialect 分离 | `drivers` 处理传输，`dialect` 处理 SQL 语义，有合理边界；无需为了抽象统一而换回 sqlx 或把所有驱动强制套一个巨大 trait |
| 凭证集中保护、列表走摘要、按引用使用 | 正确方向；手工输入与保存路径可以共存，底层密钥/文件安全应统一 |
| 平台专用实现被封装 | Windows COM、macOS keyring 等本来就需要平台代码；应要求产品双平台而不是要求每个依赖跨平台 |
| 追加数据库迁移、旧数据兼容、提交前验证 | 必須保留；但“duplicate column 整条跳过”不等于幂等，测试通过也不能代替真实恢复验证 |

## 3. 需要重构的架构边界

以下按收益与前置关系排列。问题是职责和状态边界，不是超过某条行数线。

### A1 · 工作区状态过度集中，拆分尚未完成闭环（高优先级）

**证据**：`src/plugins/database/useDatabase.ts` 1416 物理行，包含连接、元数据树、查询页签、DDL、结果处理、历史与收藏；`src/plugins/ssh/useSshWorkspace.ts` 723 行。`ssh/useSshProfiles.ts` 声称因“300 行红线”拆出，但全仓检索仅见其定义，入口 `ssh/index.vue` 仍使用 useSshWorkspace；两边有重复的 profile 加载与旧配置导入，错误处理已不同。

**判断**：文件变短不等于复杂度减少，复制出新模块但不替换旧路径反而产生两个潜在事实源。不能把所有逻辑移进 useXxx 后就算完成 UI/逻辑分离。

**建议**：

- Database 按 connection/session、query tabs、catalog/tree、saved/history 划分所有者；顶层 composable 只协调，不把所有可写 ref 交给所有子模块。
- SSH 将 profiles/groups、connection workspaces、host-key confirmation queue、lifecycle 分开。每个状态只创建一次，通过明确参数或窄接口组合；不要每个 composable 各自初始化 profiles。
- 决定接入 useSshProfiles 还是删除未使用版本，以行为一致性和完整迁移为标准；保留 importLegacyOnce 中现有失败反馈等较新行为。
- 以“迁移后旧实现删除、实际入口消费新模块、关键行为回归”为验收，禁止仅移动代码或保留两套路径。

**验证**：同一配置修改只有一个状态源；并发连接/关闭与页签状态一致；旧配置迁移只有一个实现；连接取消、晚到响应、组件卸载等状态机有测试。无需先把整个 Pinia 体系重写。

### A2 · core/ui 混入应用服务，公共入口形成依赖环（高优先级）

**证据**：`core/ui/index.ts` 导出 CredentialPicker → CredentialPicker 导入 `core/vault/CredentialForm.vue` → CredentialForm 从 `@/core/ui` 导入控件，形成模块依赖环。CredentialPicker 自己调用 Vault IPC；`core/ui/useClipboard.ts` 依赖应用 ui store。

**判断**：“所有可复用东西都进 core/ui”过于粗糙。按钮、编辑器等呈现能力与带账户/凭证/通知语义的应用组件不是同一层。依赖环目前未证明造成运行时错误，但已增加独立测试与后续空间切换的耦合。

**建议**：

- `core/ui` 保留没有业务服务依赖的控件/编辑器；CredentialPicker/Form 放同一 `core/vault/ui` 或应用复合组件入口，依赖方向只向基础 UI。
- clipboard 平台操作与“复制后怎么提示”拆层：底层返回结果，应用 helper 决定通知。避免基础 UI 反向引用 stores。
- 公共入口允许按能力分组，如 `@/core/ui`、`@/core/vault`；不得让业务组件为了“唯一入口”进基础组件 barrel。
- 暂留兼容 re-export 后逐步切消费方，最终去除环。不因此一次性改所有相对 import。

**验证**：基础 UI 能在无 Pinia、无 Vault IPC 的测试环境挂载；静态依赖图无该环；凭证选择行为保持。包体/启动收益需实测，不把 barrel 存在本身判为性能 bug。

### A3 · “前后端一一对应”不是合理的硬边界（高优先级规范修订，代码低风险渐进）

**证据**：前端 http-ws 既调用 `http_request/ws_*`，也调用后端 `api_save/api_list/api_delete`；后端有 api 模块，前端没有 api 工具目录。格式工具、组件实验室等不需要后端。

**判断**：业务能力的 owner 应清楚，但前后端目录数量相等不产生价值。“无独立前端目录即删除后端模块”甚至会误删实际被 http-ws 消费的 api 持久化能力。

**建议**：

- 以用户能力确定 feature owner；纯前端工具无需空 Rust 目录。
- api 请求收藏与 http-ws 是否同一 owner 应在架构图明确。本项目建议逐步归入 HTTP/WS 能力域的 persistence 子模块；原 `api_*` 命令名可保留，避免把物理移动变成契约破坏。
- 若暂不合并物理目录，也可声明“多个后端模块属于同一能力”的受控映射，不能为了规范齐整建立假 UI。
- 删除依据是调用图、注册入口、动态加载与数据迁移职责均无消费者，而不是只查同名目录。

### A4 · 应用状态、设备状态、数据状态缺少明确契约（最高前置收益）

**证据**：Pinia settings、core/storage、Rust settings、paths 分别读写持久化；FRP 可直接读取 settings.json；Vault 与 namespace credentials 分开取根。上一份可靠性任务书已说明具体失败路径。

**判断**：接本地空间和未来云账户前，最有价值的是一份稳定 `DataContext` 与唯一数据访问边界。仅增加 spaceId 字段却让各模块继续随时读取全局配置，仍会串环境。

**建议**：

- Rust 管真实持久化数据与版本，前端 store 管缓存/显示状态；写入经命令或应用服务，不让两端各自成为 settings 写入权威。
- 设备级与空间级配置由 schema 声明并经同一服务分流；业务模块接上下文而非自己猜文件位置。
- PluginDb 继续使用惰性连接，但在一个工具生命周期内上下文固定；epoch/generation 变化经明确重启/释放，不是每次读盘临时改目标。
- 不要求所有服务都改成 trait。路径、时钟、key store、故障注入等确有多实现/测试需求的边界再做可替换接口。

**对应已有工作**：可靠性 T01/T07、数据导入导出 L0/L1；不要另起第三套“全局配置中心”。

### A5 · 资源生命周期应独立于页面，避免做成通用万能任务平台（高优先级）

**判断依据**：长连接、子进程、迁移/更新任务具有不同寿命，当前主要依靠组件挂载/卸载和模块自建清理逻辑。仅用 v-show/KeepAlive 管页面，无法定义退出前应等待什么。

**建议**：应用层拥有少量统一协议：prepareClose、dispose、任务快照和维护互斥。SSH/DB/FRP 仍各自拥有协议与业务状态机；框架不统一它们的连接实现、不定制巨大 Session 基类。

活跃任务同时绑定 tool instance 与 DataContext；空间切换清理完资源才换上下文。生命周期测试聚焦取消、释放、晚到事件、重入，而不是测试 onUnmounted 是否被调用一次。

**对应**：T10/T11 与本地导入提交。应共享一个关闭/维护协调入口，不因不同任务书创建多个协调器。

### A6 · 原生命令装配仍重复，但不值得引入运行时服务容器（中优先级）

**证据**：lib.rs register 链、plugins/mod.rs 路由分支、validate_routing 的 owner 名称列表、各 generate_handler 与中文注册列表多处维护。

**建议**：选择一个编译期描述入口生成 owner 装配/校验，或小型宏配契约测试；元数据冻结后查表，不需要可热插拔注册表和依赖注入框架。

“新增工具一行”可以作为简化装配目标，但不应承诺新增系统能力无需权限/生命周期/迁移变更。总 handler 的 setter 陷阱值得保留为 Tauri 专项说明，不应让整套架构被这个 API 细节主导。

### A7 · 数据库驱动层分派和管理能力需要控制规模（中优先级）

**证据**：`database/drivers/mod.rs` 726 行，承担连接、会话、探测与分派；dialect 已含大量可选管理能力。枚举 DbSession 与多驱动分派本身合理。

**建议**：把 session registry/lifecycle、connect/disconnect、probe 与 driver 操作分开。保留封闭枚举或现有 trait，只有确实减少分支重复时再抽能力接口；不机械把每个 match 变 dyn trait。数据库产品边界已经冻结，别借架构重构增加新方言或更多 DBA 功能。

### A8 · 对刚制定的导入导出方案也要控制架构成本（实施前约束）

独立空间、稳定 UID、逻辑导出、类型化引用与全包加密有明确收益，保留。generation 暂存+指针切换是针对跨库/Vault/偏好一致性的方案，不要继续扩展成全应用每次写入的版本系统。

- generation 只服务导入/恢复/迁移提交；普通记录编辑仍走原数据库事务。
- 数据空间当前仅一个活动实例、重启切换，无需给所有表加 space_id 或引入多租户 ORM。
- 云端预留接口必须由本地传输实际消费；不先造 EventBus、CRDT、永久 outbox、云 provider 注册平台。
- 分阶段完成 SSH+Vault 链路后复用到其余 owner，完成标准仍覆盖专项任务书全部范围；阶段性 demo 不等于可以长期只支持一个插件。
- 32MiB 包上限、具体目录名等是待实测设计参数，不该提升为 AGENTS 永久铁律。

## 4. AGENTS 与配套规范逐项判断

下表的“改”指建议调整规范，不表示放松数据安全、兼容与验证责任。

| 现有要求 | 判断 | 建议替代 |
| --- | --- | --- |
| 组件<300行、Rust>400行必须拆、目录>8/15文件必须下沉 | **改：机械硬门槛** | 行数作为评审信号；按职责/修改原因/状态所有权拆分。分别统计生产逻辑、模板、测试/声明；较长声明表可说明保留，复杂短文件也应重构 |
| `useXxx.ts` 是纯函数 | **改：概念错误** | useXxx 用于 Vue 响应式/生命周期逻辑；纯计算按 format/parse/reduce 等命名。分别测试纯函数和状态/副作用 |
| 每个 useXxx 必须有同名单测 | **改：以文件形态代替测试价值** | 非平凡状态、并发、失败与迁移行为必须有测试，可由对应集成测试覆盖；薄映射无需为同名文件造断言 |
| 前后端插件目录一一对应 | **改：边界选错** | 以业务 owner 为边界，允许纯前端与一对多后端模块；明确映射和调用关系 |
| 框架升级不破坏插件、只增不改、框架零改动 | **改：对内置模块过度承诺** | 已发布数据格式与用户行为向后兼容；内置模块可原子协同重构。只有公开扩展契约才需独立兼容版本 |
| 无实际前端引用的插件必须删除 | **保留意图，改判定** | 无实际消费方的死功能删除；检查 IPC 调用、动态入口、启动/恢复职责，不按前端同名目录判断 |
| 所有公共能力下沉 core/ui、core/ipc | **改：公共层会变杂物层** | 按呈现、应用服务、传输基础分层；只有确有复用价值的能力共享，领域模型不塞 ui |
| IPC 出入参只在 contracts.ts 出现一次 | **保留去重，改文件限制** | 每个 owner 的传输 DTO 有单一权威，可用 contracts/ 按域分文件并导出；不要强迫内部状态/表单模型也用 IPC DTO |
| 每个插件一个数据库文件 | **保留为默认，不是绝对** | 每数据空间/持久化 owner 默认一库；纯计算无需库，密文/外部文件例外须说明生命周期；不做跨 owner SQL |
| duplicate column 幂等跳过 | **删除** | 迁移事务化，旧半迁移按已知版本与实际 schema 修复，不能跳过整段 SQL |
| 禁单平台绑定技术选型 | **改：产品支持≠依赖都跨平台** | 公共契约覆盖 Win/mac；平台适配器可使用原生库，按 target 编译与测试，unsupported 必须可见 |
| State 一律 std::sync::Mutex，不用 tokio Mutex | **改：不能按类型名选锁** | 短同步内存临界区用 std 锁；确需跨 await 独占的 I/O 用异步锁或任务所有者+消息；同步锁不得跨 await |
| clone后只读禁止、3个clone停下来、优先Arc | **改：过度关注语法数量** | 按数据规模、频率、所有权与持锁成本判断；小值快照可 clone，Arc 也有分配/原子计数/共享复杂度，不是默认更优 |
| `unwrap_or*` 只可展示字段 | **改：Option 缺省与错误被混为一谈** | 允许业务已定义的默认值；IO/解析/密钥失败不能伪装成功。审查 Result 错误处理与缺省语义，而非方法名 |
| 每函数/结构体/字段都写用途注释 | **改：容易制造复述和噪音** | 强制公共契约、安全/生命周期、单位/可空性/敏感性等非显然语义；私有显然函数和测试看可读性，不要求重复名字 |
| unsafe 零容忍/必要时可用 | **统一现有矛盾** | 采用已批准的窄适配器+紧邻 SAFETY 规则；保留必要性审查、线程/生命周期论证，不鼓励用 unsafe 绕所有权 |
| 一律 eprintln，println 会污染打包产物 | **改：理由不准确、能力不足** | 区分协议 stdout 与诊断通道；日志统一级别、脱敏与有界保存。stdout 会污染子进程协议/控制台，不会因此改写安装包文件 |
| 所有用户操作 toast/错误行 | **改：反馈不等于弹提示** | 显式操作必须可感知结果；状态变化、加载/保存指示也算反馈。取消和预期缺失不弹错误；真实失败有持久错误入口 |
| 每次改动全量门禁、pnpm format全仓写入 | **改为按风险验证，发布全量** | 文档/样式/前端/后端/权限装配分别规定验证；CI统一format:check，开发者格式化本次文件，减少并行污染 |
| 依赖要求近一年有提交、禁单平台包、能不用就不用 | **改：指标不能代替风险判断** | 看安全维护、兼容与复杂度；成熟低变动库未必差。比较依赖成本与自研协议/加密/解包成本，平台包可封装 |
| 复杂开发前提交基线 | **澄清执行语义** | 记录起始 HEAD，提交自己已有完整改动；工作区干净不做空提交，有他人改动不暂存 |

Vue 官方将 composable 定义为封装可复用**有状态逻辑**的函数，不能要求其本质上纯函数：[Vue Composables](https://vuejs.org/guide/reusability/composables.html)。Tokio 也按是否需跨 await 持锁与 I/O 共享场景区分同步/异步 Mutex，并讨论任务加消息的替代方式：[Tokio Mutex](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html)。这些资料支持上述技术边界，具体目录和阈值仍是本项目的工程选择。

### 4.1 不建议放松的底线

- 用户输入/网络/文件错误不能 panic，不能假成功或默认清空；注册冲突等编程不变量允许启动 fail-fast。
- 密码/私钥/token 不能进入普通设置、日志或错误；需要导出的秘密只进受保护容器。
- 同步锁不跨 await；后台任务有所有者、取消与回收路径。
- 修改持久化必须给出兼容、幂等和中断恢复验证；禁止借“重构”更改已发布迁移。
- 业务模块不直接读写其他模块内部数据；跨功能协作经明确应用协议。
- 公共控件与编辑器统一；安全相关配置变更与平台入口需要冷启动/平台验证。
- 只暂存本会话文件、提交信息描述具体行为、默认不 push；这些是有效协作约定，不属于需要删除的坏规范。

## 5. 规范检查器本身需要降噪与修复

### 5.1 本轮实际执行结果

`check_rust_rules.py` 通过：panic计数0、clone仅报告285；`check_docs.py` 通过：扫描95个 Rust 文件。**这些结果不证明架构合理，也不证明所有函数/字段已被覆盖。**

在内存与系统临时目录运行了三个最小探针，未改生产代码：

| 探针 | 实际结果 | 含义 |
| --- | --- | --- |
| `#[cfg(test)] mod tests {}` 后放一个含 unwrap 的生产函数 | strip_test_code 返回空列表 | 目前按首个 cfg(test) 截断整个后半文件，可能漏检后续生产代码 |
| 注释 `// Avoid .unwrap() here` | PANIC_PATTERN 匹配 true | 注释也会影响 panic 数；同样的词法问题需要检查字符串/宏 |
| `impl Example { fn undocumented(&self) {} }`（函数缩进） | check_file 返回空问题列表 | 正则只看行首特定形式，未覆盖 impl 中普通方法，却打印“全覆盖” |

另有规则与实现不一致：docs/05 §10 说 panic/clone 都是棘轮，脚本实际 clone 只报告，baseline JSON 也只有 panic。建议保持 clone 为测量线索，并修正文档，不把总数量升级为失败条件。

### 5.2 建议做法

1. 先决定规则语义，再修检查器，避免用更复杂的解析器强制错误规范。
2. 利用编译器、Clippy、TypeScript、ESLint 已有能力；Python 文本扫描只做明确边界的补充检查，输出“候选/已扫描范围”，别宣称语义全覆盖。
3. 必须对检查器自身加入注释/字符串、impl方法、多行属性、cfg测试夹杂、宏等夹具测试。若可靠解析成本过高，缩小强制规则范围而不是假装能解析 Rust。
4. 架构依赖检查解析 import/模块关系并识别 public入口，不只用目录路径数值判违规；暂不引入大套治理平台。
5. 例外清单绑定具体位置/原因/复核条件；不能用一句通用 expect 文案让任何位置都绕过审查。合法例外不需要每次重新申请，但新增例外需说明。

## 6. 建议的目标结构与依赖方向

不要求一次物理搬家；先按下列职责审查依赖，再在相关功能改动时移动。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 组装根（main/App/lib/bootstrap） | 注册服务与工具、绑定平台实现、启动/退出 | 插件业务SQL和具体连接流程 |
| 应用服务（workspace/settings/data/vault） | 用户操作协调、空间上下文、引用与任务/关闭协议 | SSH/DB协议细节、基础UI样式 |
| 工具能力域（plugins） | 自己的业务状态、逻辑数据、适配器、传输映射 | 跨工具读表、自己决定全局数据根 |
| 共享呈现（core/ui） | Ui控件、编辑器、交互原语 | Vault IPC、全局Pinia状态、账号/存储决策 |
| 平台/基础设施 | Tauri、keyring、文件与数据库实现 | 业务冲突策略、用户流程 |

不是所有层都需要独立 crate/package，也不是每个函数都要接口。应用服务通过能力契约调用工具，工具只实现约定能力；共享呈现不反向依赖应用服务。目录 `core` 不代表其中所有代码必须框架无关：Vue控件当然可以依赖Vue，只需避免业务依赖倒置。

## 7. AGENTS 建议替换条文（草案，尚未生效）

以下可以在规范修订任务中替换相应段落；不建议直接覆盖整个 AGENTS 而丢失用户已有提交/环境约定。

### 架构规则草案

> 项目采用内置功能模块的模块化单体。模块以业务能力 owner 为边界，允许纯前端工具及一个能力对应多个后端实现模块。禁止访问其他业务模块的内部状态/表；跨工具协作由框架应用服务通过明确契约协调。新增能力可修改组装根、权限和生命周期注册，不承诺框架源码零改动。

> 持久化路径、数据空间和密钥解析由框架上下文提供；模块不得自行重算当前环境。每 owner 默认使用独立 PluginDb；数据库迁移只追加并事务执行，不能因 duplicate column 跳过整段。传输 DTO 每 owner 有唯一权威定义，允许按能力分文件；内部状态模型无需强制复用传输 DTO。

### 规模与测试草案

> 文件规模是评审信号，不是拆分目标。Vue文件约300行、Rust生产实现约400行或目录难以导航时，检查职责和状态所有权；测试、模板、声明表分别考虑。多职责、大量互传可写状态、重复实现必须重构，单一清晰职责可写明原因保留。禁止通过复制实现、挪入巨型use文件或过度转发来满足行数。

> useXxx 封装Vue状态与副作用，纯计算独立命名。测试覆盖非平凡规则、并发、失败、迁移与资源释放，不按文件名配额。重构验收包含实际入口接入、旧实现删除和用户行为回归。

### 错误与平台草案

> 明确操作必须有可感知结果；取消、可选缺省与真正失败区分。错误不能伪装为默认成功，秘密不得进入日志。短同步临界区用同步锁，跨await独占IO按需用异步锁或消息所有者；所有任务有生命周期。

> 产品保持Windows/macOS支持，平台适配器允许原生依赖和受审查unsafe；公共契约一致，unsupported明确可见，相关平台编译/启动验证不省略。

### 文档与验证草案

> AGENTS只保留常青边界、协作约定与文档入口；TODO记录状态，设计决策按主题单一事实源。文档记录现行实现与目标方案的区别，历史方案不与现行规则并列。

> 验证随风险扩大：纯文档检查引用/格式；前端逻辑跑相关测试、lint/typecheck/build；Rust逻辑跑相关测试、fmt/clippy；路径/凭证/迁移加故障恢复；依赖/权限/注册加双平台构建与冷启动。发布和跨层合入运行全量门禁；本地格式化只覆盖本次文件，CI用只读检查。
