## 1. 确定的调整方案

### 1.1 保留

- Tauri 2 + Rust、Vue 3 + TypeScript + Pinia、现有构建链与 Windows/macOS 目标。
- 内置功能模块随应用整体发布的模块化单体，不建立动态第三方插件平台。
- 公共 Ui 控件、CodeMirror 6 唯一编辑器基座、现有设计 tokens。
- PluginDb 本地数据库骨架、Vault 引用与手工输入路径、数据库 native/agent/dialect 分工。
- 已发布数据兼容、追加迁移、敏感数据保护、明确的任务取消/释放责任。
- 用户约定的中文文档/注释、Conventional Commits、明确署名、只提交本任务文件、默认不 push。

### 1.2 本次决定改变

| 决策 | 最终方案 |
| --- | --- |
| 业务边界 | 以业务能力 owner 为边界；允许纯前端工具及一个能力对应多个实现模块，不要求前后端目录一一对应 |
| 规模规范 | 300/400行、8/15文件改为评审触发信号，不作为自动失败条件；按职责和状态所有权判断是否拆分 |
| Vue逻辑 | useXxx 管响应式状态/生命周期；纯计算独立命名；按行为风险测试，不要求每个use文件配同名单测 |
| 基础UI | `core/ui` 不依赖 Vault/Pinia/业务IPC；凭证复合组件迁到 `core/vault/ui`，通过 `@/core/vault` 使用 |
| SSH状态 | 完成 profiles/groups、connections、host-key队列、lifecycle 的实际拆分；接入并修正现有 useSshProfiles，不保留两套profile实现 |
| Database状态 | 分为 connection、query workspace、catalog、saved/history 四个状态所有者；顶层只协调 |
| 持久化 | Rust为桌面持久化权威；前端为缓存/展示；启动固定 DataContext，设备设置与空间设置声明式分流 |
| 生命周期 | 一个应用关闭/维护协调入口；插件保留自己的业务状态机，不建统一 Session 基类 |
| HTTP/API | 后端 api 收藏持久化归入 http_ws/persistence；保留 api_* 命令和 api.db 文件，不为改目录迁移用户数据 |
| 装配 | 编译期模块描述生成注册和路由；命令清单与handler由模块描述约束；不建立运行时DI容器 |
| 检查器 | Rust源语法检查改用钉版本的 syn AST 测试工具；两个Python脚本保留兼容入口；不声称语义全覆盖 |
| 验证 | 按变更风险分层，本地只格式化本次文件；发布/跨层最终集成保留全量门禁 |

### 1.3 本任务明确不扩展

不换技术栈、数据库驱动或编辑器；不新增数据库方言、SSH/FRP业务功能；不建设账户服务器、网络同步、CRDT、通用事件溯源、插件市场、多租户ORM或通用任务调度器。云账户仍为已确认的后期规划，本地导入导出仍为近期必做，按专项任务书实施。

## 3. 目标职责与公开入口

### 3.1 前端

| 位置 | 最终责任与约束 |
| --- | --- |
| `main.ts` / `App.vue` | 应用组装与初始化；不放插件领域逻辑 |
| `core/ui/` | 基础控件、编辑器、纯交互原语；允许Vue/Reka依赖，不允许stores/vault/features/plugins和业务IPC依赖 |
| `core/vault/` | 凭证应用能力、DTO适配、复合UI；公开index导出Picker/Form与必要类型 |
| `core/platform/` | 剪贴板/窗口等平台操作与环境判断；返回结果，不直接toast；不依赖应用store |
| `core/feedback/` | 应用级通知辅助入口，供业务调用；可适配现有ui store，后续随T11收敛 |
| `core/ipc/` | 通用调用与框架契约；不导入插件业务类型 |
| `features/workspace/` | 工具页签、关闭协商、活动状态与错误边界 |
| `stores/` | 现有全局显示/缓存状态；不强制整体搬家，不存各插件全部连接状态 |
| `plugins/<owner>/` | 领域UI、状态、数据契约和IPC适配；通过公开框架能力协作 |

`core/ui/windowCtl.ts` 与依赖ui store的复制helper一并分类迁移。基础UI内部用相对具体组件路径，避免经自身barrel回流。跨层不允许用类型导入绕过明确的领域边界；DTO需要共享时归属公开契约。

### 3.2 Rust

- `lib.rs`：平台插件装配、应用构建、启动/退出委托；业务模块由静态模块清单组装。
- `framework`：DataContext、settings、secure_store/vault、PluginDb、维护/关闭、命令元数据等应用公共能力。
- `plugins/<owner>`：自己的业务状态与存储/传输适配，框架不写业务表SQL。
- 不新拆多个生产crate，不要求所有结构都实现trait；测试替身只出现在确有外部效应的边界。

## 5. AR02 · 重做可靠的规范与依赖检查

### 5.1 确定工具方案

使用 **Rust测试工具 + syn 2 AST** 检查自有Rust源文件。当前Cargo.toml没有 `[dev-dependencies]`，本批首次新增此段；`syn` 的 full/visit 与 `proc-macro2` 的 span-locations 作为直接dev依赖。执行时选定经验证的具体版本，在Cargo.toml使用 `=x.y.z` 精确约束，并更新Cargo.lock；仅有lockfile不等于manifest钉版本。记录原有传递依赖、增加的直接依赖/包/feature及编译成本，不声称首次引入syn包本身。不新增生产运行依赖，不自研完整Rust语法解析器。

测试工具放 `src-tauri/tests/source_rules.rs`，辅助实现与夹具放测试子目录。**check_docs.py的文档扫描实现并入同一syn工具，保留第二个Python薄wrapper**，删除两个脚本内的旧正则扫描逻辑。约定测试入口 `scan_rust_rules` 与 `scan_docs`，夹具测试与这两个入口同属source_rules target。

- `python scripts/check_rust_rules.py` 委托 `cargo test --manifest-path src-tauri/Cargo.toml --locked --no-default-features --test source_rules scan_rust_rules -- --exact --nocapture`。
- `python scripts/check_docs.py src-tauri/src` 委托相同target的 `scan_docs -- --exact --nocapture`，保留目录参数并通过明确的环境参数传递规范化绝对路径；默认目录由仓库根解析，不依赖调用cwd。非法参数、扫描失败、Cargo失败均非零退出。
- wrapper验收必须确认过滤器实际运行1个扫描测试，不能把零测试的成功退出当通过；CI跑整个target，覆盖两类扫描与全部夹具。

### 5.1.1 CI 的确定命令

修改 `.github/workflows/ci.yml`：保留并明确下面两个独立步骤，移除原先两个Python扫描步骤，避免重复扫描：

```sh
cargo test --manifest-path src-tauri/Cargo.toml --locked --no-default-features --lib
cargo test --manifest-path src-tauri/Cargo.toml --locked --no-default-features --test source_rules -- --nocapture
```

第一步只跑库单测，不能覆盖 `tests/source_rules.rs`；第二步显式选择该集成测试target。此命令不会选中 `ssh_live`；现有 `clippy --all-targets` 或全量 `cargo test` 仍会编译它，`#[ignore]` 只避免执行，不能避免编译。CI不得添加 `--ignored`。两种wrapper在工具变更验收中分别调用验证，不再作为日常CI独立扫描步骤。

当前Cargo.toml也没有 `[features]`，`--no-default-features` 目前不关闭任何本包默认feature，更不等于关闭依赖的默认feature；保留该参数仅为命令兼容，不据此宣称精简构建。

AST负责源级结构；Clippy负责编译后的已启用代码诊断。宏展开、cfg组合与别名解析不可能仅靠syn完整证明，报告必须列未覆盖范围，不能继续输出“全库语义全覆盖”。未知复杂条件下的生产候选不能默默按测试代码跳过。

### 5.2 硬检查与提示

- 硬检查：运行期直接unwrap/expect/panic/unreachable候选、禁止的生命周期逃逸调用、unsafe缺紧邻SAFETY、定义范围内缺失的公共/IPC语义文档、明确的层级依赖越界。
- `assert!` 等不在现有PANIC_PATTERN中的潜在panic入口纳入清单审查；集合索引等由Clippy和代码评审补充。新增发现必须分类，不能直接抬高总数基线。
- 仅按属性AST的字面结构排除直接 `#[cfg(test)]` 子树，继续遍历后面的生产项。这不是cfg求值器：`cfg(all(test, feature = ...))`、`cfg(not(test))`、`cfg_attr` 等组合不作真假推断，保守扫描并列入未覆盖清单；用夹具证明不会静默漏过其中的生产候选。识别impl方法、嵌套模块、多行属性、raw字符串，注释和字符串不当代码检查。
- 启动注册冲突、可证静态不变量等例外绑定相对路径+符号+调用类别+原因，不以同一句expect文本全局放行。移动符号同步更新记录，失效例外报错。
- clone/文件规模仅报告，不拦截，不因读数字高就批量改Arc或拆文件。
- 文档检查严格限定：模块职责；pub/pub(crate) API职责；IPC/持久化DTO的非显然字段语义；关键安全/资源契约。测试辅助与私有直观方法不强制；注释质量人工审查，工具不声称证明语义正确。

### 5.3 前端依赖守卫

复用已安装TypeScript编译器API解析TS及Vue SFC脚本块（Vue编译器来自现有工具链），解析静态import/export、字面量动态import与alias。不新增大型治理依赖。

硬规则：core/ui不依赖stores/features/plugins/vault或应用IPC；不同插件不import彼此内部；应用复合组件不得由core/ui重新导出；公共域入口无已发现的运行依赖环。非字面量动态路径列为未解析并要求明确登记，不默默忽略。

**必需夹具**：测试模块后生产函数、impl方法、多行属性、注释中的unwrap、raw string中的unsafe、合法和非法SAFETY、同文案不同符号expect、宏未展开提示、有效与陈旧例外、alias/相对import、barrel依赖环、合法type export。夹具测试必须先证实现有误判场景再验证修复。

**验收**：已有脚本命令仍可用且退出码真实传递；报告包含规则数、源范围、例外和未解析项。不得删除检查器只留“人工检查”，也不得用规则调整掩盖新发现的真实错误。

## 8. AR05 · Database 前端及驱动职责重构

### 8.1 前端明确分工

- `connection/useDatabaseConnections.ts`：连接定义、连接/断开、当前选择与请求epoch。
- `workspace/useQueryWorkspace.ts`：query tabs、每tab SQL/dirty/result/request状态、运行/取消与结果分页投影。
- `catalog/useDatabaseCatalog.ts`：数据库/schema/对象树缓存、加载状态、补全元数据；缓存key包含connection与上下文，不读另一连接的树。
- `library/useQueryLibrary.ts`：历史/收藏的读取与保存；不拥有查询执行生命周期。
- 根 `useDatabase.ts`：应用级操作协调/兼容门面；不得继续保存上述域的重复ref或重新实现相同行为。

DDL/管理操作暂置catalog域的显式command函数，通过query执行端口请求执行并失效相关缓存；不把任意执行能力藏在tree读取函数中。不增加新DDL功能。

模块之间传readonly快照、computed视图与command函数，禁止为了方便把巨大的workspace对象双向传入。现有纯函数filterTreeItems/extractExecSql等迁域并保持测试。

### 8.2 Rust驱动层明确拆分

`database/drivers/mod.rs` 仅声明/重导出；现有DbSession/DbState/CancelHandle迁 `session.rs`，连接/关闭迁 `connection.rs`，版本/时延探测迁 `probe.rs`，查询/取消分派放 `execution.rs`。mysql/postgres/redis/sqlite和agent/dialect边界保持。

保留封闭DbSession枚举，不把每个match改为dyn trait，不改驱动、SQL语义或可用方言清单。公开crate内路径可经mod重导出保持，门面必须只有转发而不是重复实现。

**验收**：多连接、多查询页签各自结果归属正确；关闭一个tab不取消另一tab；旧响应不能覆盖新请求；取消后仍允许新查询；元数据缓存失效准确；保存SQL/历史不因拆分丢失；现有driver/dialect测试通过。真实DB功能按既有测试环境验证，缺平台/服务的结果明确列待验证。

## 9. AR06 · 固定数据上下文并接统一生命周期

这是与已有任务**共用的工作包**，不是重复开发新的框架。

### 9.1 上下文最小契约

Rust定义不可变 `DataContext { spaceId, generationId, location, epoch }`：location兼容旧默认布局；epoch为本次启动上下文标识，用于拒绝晚到事件/任务，不充当云同步revision。前端只取非秘密上下文标识，业务组件不拼物理路径。

默认空间身份/索引由导入导出L0/L1定义，paths和PluginDb消费同一实例。设备字段（存储根、快捷键、自启、路径绑定）与空间字段（偏好、收藏、工具数据）经settings服务按schema路由；所有桌面持久写入经Rust应用入口，前端浏览器预览走明确的独立适配器。

**禁止临时替代**：每次调用从settings.json读当前根；不同模块自行创建空间id；把AccountId等同spaceId；给所有表机械加account_id；同时保留两套有效settings写入端。

### 9.2 生命周期最小契约

唯一关闭协调入口接收 `reason=tab/exit/restart/update/space-switch`，区分prepareClose与dispose：前者可拒绝/提示未保存，后者在允许关闭后负责清理。业务协议清理由各模块提供，应用只协调结果与总超时。

唯一维护互斥负责根迁移、导入提交、空间激活和更新安装。JS“页面按钮禁用”不是锁，最终互斥在Rust服务。工具资源绑定实例id与DataContext，晚到旧上下文事件被丢弃并计入可诊断统计，不写新环境。

### 9.3 验收归属

| 实施内容 | 必须同时引用的验收 |
| --- | --- |
| 固定根/布局/上下文 | 可靠性T01–T03，导入导出L0/L1 |
| 设置权威/字段路由 | 可靠性T07，导入导出空间/设备分类 |
| key与凭证上下文 | 可靠性T04/T05/T09，导入导出跨空间隔离 |
| 关闭/维护/任务 | 可靠性T10/T11，导入导出计划失效和generation激活 |

AR06只有当消费方已接入且上述必要行为验证通过才完成。仅增加type/interface不算完成，导入导出产品向导则仍由L2–L5交付。

## 10. AR07 · 统一 HTTP owner 与编译期装配

### 10.1 API归属迁移

将 `src-tauri/src/plugins/api/{mod,models}.rs` 迁入 `http_ws/persistence/`，api_*命令继续可用，HTTP/WS前端contracts不因物理移动而改字段。注册owner统一为现有Rust `http_ws`；产品侧稳定feature id继续 `http-ws`，映射写入模块描述，不靠字符串替换猜测。

现有 `api.db` 保留，通过 `storageKey: api` 明确为历史存储名；不得为了owner统一改名或创建第二个空库。未来导入导出数据集归HTTP/WS，但逻辑格式不得泄漏物理api表名。

去掉独立api模块的装配/路由分支，只有完成调用与旧数据验收后才删除原目录。纯前端工具无需增加Rust空模块。

### 10.2 静态装配

创建一个静态模块描述宏/清单，为每模块记录Rust模块路径、featureId/owner、register入口与handler。由它生成业务register链和owner路由，移除validate_routing内第二份手写owner枚举。

模块命令描述同时记录实现路径、IPC名称、中文用途；由一个局部声明生成handler和入库元数据，先迁框架与http_ws验证，再迁其余owner。保留一个应用总handler和现有官方插件装配顺序，不能把所有插件Builder hook塞进不可读泛型容器。

普通命令由同一函数标识符生成handler引用与 `stringify!` 注册名，不重复手写字符串。确需兼容别名时必须显式声明IPC字符串到实现的映射，不要求两者同名。保证边界如下：

| 条件 | 保证方式与验收 |
| --- | --- |
| 实现路径不存在、签名不被handler支持 | Rust编译失败；编译负例验证 |
| 普通命令注册名与handler名一致 | 同一标识符生成，消除独立编辑来源；宏展开/契约测试验证生成逻辑，不能泛称编译器会校验任意字符串 |
| 兼容别名或显式IPC字符串映射错误 | 调用契约测试比较已发布命令表、元数据与实际路由；构造错误映射负例，不能声称编译期保证 |
| 全局命令重复 | 注册表启动fail-fast与重复注册单测；不是编译期保证 |
| 未知owner | 路由运行时明确报错与负例测试，不允许默认吞掉 |
| 全部实际IPC入库且均能路由 | 注册/handler生成清单对照、契约测试及入口扫描守卫；手写绕过入口须被守卫发现，不宣称仅靠编译就证明完备性 |

生成宏内的候选由编译检查和调用契约测试补足，不能只依赖AR02源扫描；测试应明确失败阶段，禁止将上述运行期/测试约束写成编译期验收。

**验收**：已有API收藏数据库原样可读写；http/ws/api命令对照表一致；没有为目录同构增加假模块；新增测试用模块只修改清单及自身实现即可路由；权限/装配变动执行双平台构建与冷启动。
