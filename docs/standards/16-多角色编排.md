# 16 · 多角色并行编排（冲突规避 · 角色分工 · 交接协议）

> 本文原为 AI 助手侧技能库中的项目知识，2026-09-13 迁入仓库，作为项目自有开发手册的一部分。正文未改写（仅同步文档路径与目录规范）。

为「多个 agent / 多个会话并行开发同一仓库」设计的方法论。核心认知：**agent 间不直接对话，通信载体 = 仓库文件 + Git 提交**。协作设计 = 一套产出物协议：每个角色只读上阶段产物、只写自己产物、用文件交接。

## 冲突规避（三层，从根上消灭）

1. **架构层（根除 90%）**：按模块/插件目录隔离——每个 agent 只允许写自己的模块目录（如 `src/plugins/<id>/` + 后端同名目录），文件零重叠 → git 自动合并零冲突。
2. **提交前规则**：
   - 每个 agent 一个分支 + 一个 **git worktree**（`git worktree add ../repo-<agent> feature/xxx`）：独立工作目录、共享历史、文件系统隔离
   - **禁止碰共享/装配文件**（lib.rs、plugins/index.ts、插件清单、框架契约、eslint/tsconfig/CI 配置）——注册行由集成者统一收尾追加（追加不同行自动合并，但同文件格式化/重排会冲突，所以收口给一人）
   - **format 只跑自己目录**：仓库级 `prettier --write .` / `cargo fmt` 全量格式化是多 agent 冲突源——agent 只 format 自己模块（`npx prettier --write src/plugins/<id> src-tauri/src/plugins/<id>`），全量 format 由集成者合入前统一跑。rustfmt/prettier 对已格式化文件幂等，所以「改完 → 格式化 → 提交」可保持文件始终格式化态
   - 小提交、单主题
3. **合入流程**：集成者**串行合入**（一次只合一个分支 → 全量验证 → 绿才继续）；冲突只可能发生在「合入中的分支 vs main」，解决成本几行。每个合入后跑全量验证（clippy -D warnings / lint / test / 注释检查器），不合规当场打回不积压。

## 角色分工（复杂插件 3 角色协议）

| 角色 | 输入 | 产出（全部落盘） | 验收 |
|---|---|---|---|
| **设计**（需求+UI） | 用户需求、参考产品 | `docs/plugins/<id>/需求.md` + `界面设计.md` + **契约草案**（contracts.ts 出入参形状 + 命令清单含中文说明 + models.rs 形状）+ manifest | 用户确认 → **契约冻结**（提交，全流程最重要里程碑） |
| **开发** | 冻结契约 + 文档 | 前后端完整实现 + 单测 | 全量验证绿；**不改契约**（发现缺陷写交接单由集成者裁决） |
| **测试**（按需求+UI 测） | 需求/UI/契约（不是代码） | 基于契约**先写用例**（RED）+ 需求覆盖矩阵 + 跑测 + `测试报告.md` | 覆盖矩阵全绿 + UI 走查（对照 界面设计.md 逐项：布局/深色模式/空态/错误反馈） |

时序：设计（串行）→ **开发 ‖ 测试并行**（契约冻结是发令枪）→ 集成（单人收口：装配 + 联调 + 全量验证 + 合入）。测试 agent 与开发并行先写用例（测试先行），不是最后把关。

### 角色分工变体：「设计 + 前端一体化」（用户确认 2026-08-09）

复杂插件建议拆成 **4 角色**：agent1 = 设计 + 前端开发（UI 侧全包）、agent2 = 后端 Rust、agent3 = 测试、集成者 = 主会话。理由：**前端是与设计耦合最高的环节**（布局/交互/组件/tokens 都是设计阶段的产出），设计者自己做前端 = 零交接失真（界面设计.md 是文字，第三方实现容易理解偏差）；后端是独立领域，照契约执行即可不必是设计者。操作：设计完成后给 agent1 发前端开发任务书（角色切换：按 界面设计.md + contracts.ts 实现 `src/plugins/<id>/`，含 useXxx.ts 纯函数 + 测试；组件 ≤300 行；语义 token；复用 core/ui；不碰共享文件）。注意上下文管理：设计+开发同一会话历史会很长，可让设计会话提交后**开新会话（同模型）执行前端任务书**，任务书 + 设计产物即全部上下文，延续性不丢。

## 文件通信协议

- **任务书**（每阶段一份，落盘 `docs/batches/<批次号>/<角色>任务书.md`）：输入（规则文档路径+用户需求原话）、产出清单、约束（中文注释/serde 规范/不碰共享文件/提交规范）、验收标准。子 agent 无对话记忆——任务书必须自包含
- 任务书模板（三角色全套，复制改占位符即用）：`docs/standards/templates/设计任务书.md`（设计/调研，6 产出物）、`docs/standards/templates/后端任务书.md`（后端：技术选型已定死、目录结构给定、**装配片段由 agent 产出文档不由 agent 改装配文件**、质量门槛含注释检查器）、`docs/standards/templates/测试任务书.md`（测试：按需求+UI 测、两阶段 A 前端用例/B 契约一致性核对、不修实现只写问题清单）
- **交接单**（HANDOFF.md）：每阶段完成写——产物在哪、做了什么决定、遗留问题、下阶段注意
- **契约冻结 = 唯一接口**：冻结后任何一方想改 → 写交接单，不自己改
- 提交信息即通信日志（统一 conventional commits 带模块作用域）

## delegate 编排实操（Hermes）

- **设计阶段任务书模板**：`docs/standards/templates/设计任务书.md`（6 产出物/调研要求/验收标准/红线，基于 SSH 工具实战泛化）——新插件设计阶段直接复制改占位符，交给单独开的强模型会话执行- 方式 A（推荐）：主会话当集成者——`delegate_task` 单任务派设计 → batch（≤3 个）派开发+测试并行 → 结果自动回传 → 集成者联调/验证/合入。任务书可写在 context 参数内（简单）或落盘后 context 一行指向（复杂，可复用可审计）
- 方式 B（备选）：用户手动开多个会话，会话间靠仓库文件+提交衔接，用户当集成者
- **live transcript**：派发返回带 `cache/delegation/live/<id>/` 实时日志（子 agent 的文字+工具调用+结果全程可见）——关键节点看一次（前 10 分钟确认方向），不必全程盯；隐藏推理不保证出现，但可见输出已足够判断
- 失败处理：测试打回 → 派修复 agent（context 带测试报告路径）或集成者自己修
- **续跑模式（子 agent 工具迭代上限截断，2026-08-09 实战）**：delegate 子 agent 有工具调用上限（本环境 50 次），大任务（如 11 个 Rust 文件的后端实现）几乎必然被截断——不是失败，是正常分片。处理流程：
  1. 截断 summary 会声明「未完成 + 已完成 + 遗留待办」；中段被省略时用 `read_file` 分页读完整 summary 文件（路径在结果里）
  2. **从 summary 提取可复用结论**（API 测绘、技术决策、依赖版本锁定、遗留清单）——这是续跑的全部资本
  3. 重新 `delegate_task`，把结论**原样放进 context**（如「russh 0.62.5 用法：connect/Handler…、ssh-key 必须锁 =0.7.0-rc.11」），任务书指向不变，明确「无需再调研，直接开工」——续跑不重跑
  4. **任务书里要求 agent 的输出总结必须含「可续跑信息」**：API 结论 / 决策 / 遗留待办清单——这样截断时价值不丢（本会话后端 agent 的测绘结论+遗留清单让续跑 agent 直接跳过调研）
  5. 测试 agent 的「阶段 A/B 拆分」（A 不依赖后端、B 等后端）天然抗截断——阶段 A 产物即使未提交，集成者 review 后补提交即可
  6. 子 agent 遗留的临时目录（如 `.crate-inspect/` 源码包）会污染仓库 lint——续跑派发前清理或要求 agent 完成后自删
  7. **续跑上限与「集成者自己写」的决策（2026-08-09 两次截断后实测）**：连续两次 delegate 都被截断（每次 ~10 分钟都花在「读文档 + API 核实」上，实现未动）后，别再派第三个——**当任务核心是「迭代式编译调试」时（写 10+ 文件 + cargo check/clippy 多轮修复），delegate 的 50 次调用上限远不够（每次编译 20-60s 且错误逐类修），而主会话没有该硬上限**。集成者自己写的条件：API 结论已在手（前 agent 的测绘 summary 足够）、文件结构已定（任务书目录）、只需机械写文件 + 编译迭代——本会话集成者自写 11 个 Rust 文件 + 40 分钟编译调试一次成功。delegate 更适合：独立调研产出结论、或**分块**任务（每块 3-4 文件可独立编译验证）；「无限续跑」是最差选择（每个 agent 重新读 10+ 文档消耗预算）。

## 跨会话待办交接（用户会要求「下次打开就要能看到待办」）

会话收尾时把未完成的工作落三层，缺一不可：

1. **仓库根 `TODO.md` 总表**：四块固定——进行中（逐项：状态 / 关键决定 / 建议顺序）、待拍板（问题清单 + 前置验证项）、明确不做（用户本轮否掉的范围）、已搁置（用户说过「先不管」的，标注勿擅自开始）。完成即勾，做完的段落删掉
2. **常青规则文件的「当前待办」小节**（如仓库 AGENTS.md）：这类文件在会话打开仓库时自动注入，是「下次打开必看到」的唯一保证；小节只放短摘要 + 任务书路径，并注明「本文件唯一允许承载进行中状态的位置，清空后删除该节」——否则长期违背它「只放常青规则」的自身定位；修改共享的 AGENTS.md 前后要向用户报备（并行会话可能同时在改）
3. **任务书自带勾选式清单**：按批次列可勾步骤（装依赖 / 新建文件 / 接线 / 验收），批次状态以清单为准
4. **待决策书**（需要别人拍板时）：用户会把待确认事项转给另一个会话/人来确认——产物是落 `docs/batches/<批次号>/待决策书.md` 的**中性文档**，不是聊天里的角色提示词（用户明确否掉「你是决策 agent」写法）。每条形如：**背景事实**（附可自验的命令、文件与行数）→ 选项表（把建议项标在第一个）→ 建议理由 → **无回复时的默认动作** → 验收判据；文件头写清用途与确认方式，并附「剩余待办全景」与「不得违反的约束」。骨架见 `docs/standards/templates/待决策书.md`。**回流那一腿同样落盘**：用户只回一句「已经完成决策」，实际裁决是他交给的复核方产出的 `docs/batches/<批次号>/决策书.md`——先读它取执行顺序与「记录缺项」等口径，不要复述或再问一轮；复核方通常已自行把指针挂进 TODO 与相关文档入口，动手前用 `git log`/grep 确认它已做的记账，**不重复记账、不新建重复任务书**，直接按它给的顺序一项一验收一提交

**多批次改造另加一层：逐项执行计划书**（用户要求「一项一项的做计划书，一项一项逐个完成」）。任务书含多个批次/AR、或预计跨多次提交时，先落 `docs/batches/<批次号>/剩余项执行计划.md`：逐项写 范围 / 前置依赖 / 验收判据 / 风险与门禁底线（依赖外部条件的项只排期、不展开实现）；执行纪律写进文件头并逐项遵守——一次只做一项、一项一提交、只 `git add` 本项文件；完成即回填提交号 + 各项实际验收结论 + 「未做与理由」。它是跨会话唯一的进度事实源（TODO.md 只放指针）。

**进度汇报必须对照原任务书的判据，并把「结构完成」与「行为验收完成」分开写**（用户会追问「针对任务书说下进度，这样复核方才能全盘知道」）。汇报表逐条列：任务书要求 / 状态 / 提交证据 / 未完成与未验证及原因；再补三张对照——按批次的视角（B0–B7 之类）、验证矩阵里**没跑完的门禁行**（真机、双平台、旧数据夹具、跨层全量）、完成定义里逐条条件的达成情况。口径按任务书自己的话：结构接线完成不等于相关风险已修完；欠的验收要写成「未做 + 原因」，不许并进「已完成」一句带过。

**交接文档里的数字与结论同样是硬断言**：行数、提交号、「全仓无 X 先例」「门禁全绿」写进文档前实测一次（`wc -l` / `grep -rn` / 重跑命令），给不出实测的判据就写「未验证 + 原因」——复核方会把文档当依据，造假的代价与代码一致。**长文档的增删改原地替换、不整文件重写**：读入（保留原行尾，如 CRLF）→ 断言目标串存在（必要时 count==1）→ replace → 写回，插整段与章节重编号同理；改完跑该仓库的格式与文档检查入口。

待办条目必须自解释：写「决定 + 依赖 + 谁拍板」，不写只有标题的空条目。

**文档不按时间平铺进单一目录**（用户要求「分目录去放，多个目录下的文档按批次号为关联」）：文档按**生命周期**落位——会反复读的规格/设计、一次拍板的决策、只写不读的证据、一次性报告各归其类；跨目录靠**批次号**串起来（批次 ID 写进每篇文件头，目录名或文件名带同一 ID）；一个批次的进度只在它自己的清单里勾，不另建进度文档。插件级文档仍放 `docs/plugins/<id>/`。各层职责、批次号形式、行业对照与存量迁移步骤见 `docs/standards/17-文档组织与批次.md`——**目录方案与批次号形式未拍板前不要擅自迁移既有文档**，先提议再搬。

**规划轮次以代码为现状事实源**：写任务书前用 grep 盘点真实能力（契约 / 命令注册 / 依赖 / 设置项），插件自带的需求/设计文档不能当现状——历史文档会把后来做了的写在「明确不做」、把没做的留在 P2。规划轮次只出方案不写代码，用户会亲自划线；他否掉的项要显式进 TODO.md「明确不做」，避免下个会话重新提。

## 接手已停的并行会话（无人值守）

用户会说「监控隔壁会话，结束了就按未完成任务书继续；需要决策的先写入报告；因决策影响模块可以先不动」。执行要点：

1. **判定「已停」用客观信号，不靠感觉**：取两个信号中较新的一个——git HEAD 的提交时间、工作区源码文件的 mtime；**必须排除 `target/`、`node_modules/`、`dist/` 等构建产物**，否则编译噪音会让会话永远显示「在动」。两者同时静默约 20 分钟判停。监视器每 60 秒落一行 `[时刻] idle=Xmin | HEAD=<短哈希> | 最新文件=… | 未提交=N`，退出时打印一行结构化结论（idle 分钟数 + HEAD + 是否 dirty），便于事后回溯判定依据
2. **对方活动期间不并行动手**：不碰同一批文件，不跑会互相干扰的命令（例如 dev 实例会锁住 exe，使依赖编译的文档/规则检查器报 `os error 5`）；这段时间只做只读盘点
3. **接手第一步是回归基线**：`git log` / `git status` 确认对方留下的提交与未提交改动，再按未完成任务书排活；对方只做了「单平台/单路径」的项，补的是缺口那一半，不重做已完成部分
4. **需要拍板的一律写报告，不替用户决定**：无法自行裁决的结构性改动原地挂起，报告里写明「无回复时的默认动作」；与决策无关的模块照常推进
5. **收尾交回**：新证据回填原文档（原地替换，不整文件重写）、更新 TODO、按仓库规范只提交本会话文件

## 渐进策略（避免过度工程）

- 轻量/中小模块：**不推荐多角色**——固定开销（任务书/交接单/评审）超过开发本身，单 agent + 检查器全绿就够
- 只有复杂模块（状态机+长连接+多视图+适配器，如 SSH/DNS 三厂商/DB 三方言）值得 3 角色
- 先拿中等复杂模块试点跑通流程（摸清契约冻结摩擦点、任务书格式是否够用），再铺开到大型模块；流程章程在试点后根据真实摩擦点固化，不要未验证就写死

## 关键坑

- **子 agent 报回的「行为零变化 / N 个 key 相等 / 测试全绿」是自报，不是证据**：拆分、搬移、契约类交付必须机制化复核——用脚本在 `git show HEAD:<file>` 与工作树之间比对公开面（返回对象键集合、导出名、消费方 import 覆盖），并在**已提交树**上自己重跑门禁；报告只写自己跑出的数值。同一条目还要防「孤儿模块陷阱」：按行数红线抽出却从未接线的旧实现常有多个，接入前必须以活跃实现（谁被上层消费谁就是基线）为行为基准、把活跃侧较新的修复逐条搬过去，禁止用旧副本覆盖新修复。配方与脚本骨架见 `docs/standards/18-重构与搬移验证.md`
- **后台批次报告的失败先判时点**：进程启动于修复提交之前 → 过期，按过期处理并在报告里说明，然后用已提交树重跑它跑过的同一条命令取值；不要在已修好的代码上「复修」，也不要因一份过期报告停下进度
- 子 agent 无对话记忆：context 必须包含所有必要信息（项目路径、规则文档、需求原话、产出/验收）
- **子 agent 与 `tauri dev` watcher 共存（2026-08-16 vault 并行实测）**：子 agent 边写边存 `src-tauri/` 时，运行中的 tauri dev 会对**中间态**反复触发重编译，watch 日志报 error[E…]（如 E0277）是正常噪音——**不要中断子 agent，也不要去修它的半成品**（会跟它后续编辑打架）；等 delegate 返回后主会话跑 `cargo check --no-default-features --lib` 复核，绿即无碍。若 dev 因编译失败停在旧二进制，等子 agent 收尾后 watcher 会在下一次保存时自动重编译恢复，或手动重启 dev。
- **确认门禁遇上用户不在场（澄清表单超时）不要空转**：推进「不需要拍板且可回退」的那部分（现状盘点、盘点/计划书/待决策书落盘、手工核对事实），把结构性改动与需决策项原地挂起，并在文档与回复里写明默认动作——既不擅自动必须确认的改动，也不因等回复停下全部进度
- 仓库级 format 命令（`prettier --write .`）是多 agent 场景的隐藏冲突源
- 「契约先行 + 冻结」是并行能成立的前提——设计阶段不可并行
- **设计阶段角色边界**：当用户说「本次任务不是改代码，是做需求调研/UI 设计」时，即使发现任务书与仓库现状不符，也**不要当场修正任务书**——把问题整理到 `docs/batches/<批次号>/待确认.md` 由主会话转达/仲裁，设计 agent 专注产出 6 个设计文件（竞品分析/需求/UI/契约草案/待决策清单）。任务书修正属于集成者/用户职责，不是设计 agent 的产出物
- **设计阶段验证**：契约草案（contracts.ts + models.rs）落盘后必须验证语法——TS 用 `npx tsc --noEmit <file>`；Rust 若未被 mod.rs 引用，临时挂 `pub mod ssh;` + `cargo check`，验完立即 `git checkout` 撤销，保持提交干净。设计阶段也要跑全量 `pnpm test/lint/build` 确保未破坏现有代码
- **审查并行会话的提交，范围钉 commit 不钉工作区**（2026-09-06 实测）：并行 agent 随时可能 `git commit`，审查中的「未提交 diff」会半途被提交走，delegate 子代理按旧指令审 `git diff HEAD` 会颗粒无收。流程：① `git log --format='%h %ad %s'` + 文件 mtime 还原时间线，分清已提交/未提交/进行中；② 已提交的用 `git show <hash>` 审；③ delegate 审查任务书写死 commit 范围（如 `git show 61c8037`），产出限定「只报有证据的 bug：文件:行号+触发场景+修法」；④ 大重写审查先跑门禁（cargo check/vue-tsc/test）拿客观证据再按模块并行 delegate
- **他人提交里的「已验证」声明要打折**：提交/文档宣称 RC 验证完成 ≠ 覆盖 dev 冷启动——真实案例：注册 updater 插件缺基座配置段导致 `pnpm tauri dev` 启动 panic 两周无人发现（CI 只 build 不启动）。审查涉及 tauri.conf.json/插件注册的提交时，冷启动冒烟是唯一证据
- **契约评审必查「事件通道」缺口**（2026-08-09 SSH 设计评审真实缺口）：仓库里只有轮询型插件（http-ws 用 `ws_recv` 300ms 轮询）时，设计 agent 容易把契约写成纯命令（请求-响应 invoke），漏掉 Rust→前端**主动推送**的事件定义（Tauri `app.emit` + `listen`）。交互式终端（输入延迟 <50ms）、文件传输进度、连接状态变化三类数据**必须走事件**，轮询不现实。契约要显式定义：事件名（如 `ssh://terminal-data`）+ 负载类型。集成者 review 契约时逐类检查「哪些数据是推送型」：终端数据/进度/状态变化 → 事件；用户主动查询 → 命令
- **用户「不做 / 我自己测」的裁决要落盘为已关闭项，且不得把未验证改写成已通过**：用户表态「这项测试我手动做」「这个平台现阶段不管」时，动作是——把裁决原文与日期写进决策文档、该条从「待决策」移到「已裁决」、同步 TODO，此后它不再是阻塞项，不要复述也不要再问一轮。同时**验收结论只写实际观察到的状态**：没有条件验证的平台或场景保持「空白 / 未验证」表述（可补一句「长期环境缺项，不追求补齐」），禁止顺手写成「已通过」——文档是下个会话的事实源，一个假绿的格子比空白更有害

## 模型分工模式（用户认可的编排）

**「强模型单会话做设计 → 普通模型多 agent 做开发测试」**（2026-08-09 用户方案，无需改配置）：设计质量由好模型保证（契约是后续一切的地基），开发/测试是执行型工作普通模型够用。操作：设计任务书落盘（`docs/batches/<批次号>/设计任务书.md`，自包含：需求原话/必读文档路径/产出清单/验收标准/红线）→ 用户新开强模型会话粘贴执行 → 产物提交（独立分支）→ 主会话集成者 review 契约（含事件通道检查）→ 拿待决策清单给用户一次性拍板 → 冻结 → delegate 开发+测试。子 agent 模型不可逐角色配置（继承父会话或 config.yaml 全局 pin delegation.model）——想按角色分模型只能用「单会话 + delegate」混合编排

## git 误提交事故处理（2026-08-09 真实事故）

场景：全仓库 `pnpm format`（prettier --write .）把其他会话的未提交改动格式化了，随后 `git add -A` 把它们一起提交。**误提交后的正确流程**：

```
git reset --soft HEAD~1          # 撤销提交，全部改动保留在 staging
git reset HEAD src/plugins/ ...  # 只取消他人文件暂存（unstage）
git add <自己的文件>              # 显式只 add 自己的
git commit ...
```

🔴 **绝不在误提交后跑 `git reset --hard`**——soft reset 后工作树改动仍在（staged），`--hard` 会把**所有未提交改动（包括自己刚写的功能 + 其他会话的工作）全部销毁**，只能重做。本事故中 `reset --soft` 已正确执行，随后误加 `reset --hard HEAD` 把已暂存的功能改动一起清了，全部重写。

预防（提交前 3 秒检查）：
- `git status --short` 确认工作树**只有自己的文件**再 `git add -A`；并行会话场景一律显式 `git add <路径>`
- 仓库级 format 只由集成者在合入时跑一次，agent 只 format 自己目录（见冲突规避 §2）
- 任何 `git reset --hard / checkout -- . / clean -fd` 前先 `git status` + `git stash list` 确认无未提交工作
