# 21 · Git提交规范

> 用户2026-09-13确认：只约束新提交，不整理或重写历史提交。本文是提交信息的唯一规范来源。
> 何时读：准备提交、拆分提交或评审提交信息时。

## 标题说明结果

格式：`类型(scope): 中文变化描述`。标题必须独立可读，说明本次解决的问题、增加的能力或完成的结构调整，不依赖任务书、清单、会话或评审编号。

- 标题突出一个核心结果；相关变化放正文，不相关变化拆提交。
- **任务号、批次号、issue号和评审编号不得出现在标题任何位置，包括scope**，即使标题已有完整变化描述也不能附带，如 `rel-202609-001`、`AR06`、`P3`。需要追溯时只放正文末尾的辅助关联项。真实技术标识符不属此禁令，如HTTP状态码、协议版本、错误码；仅在解释本次问题确有必要时保留。
- 禁止用“完成整改、更新清单、处理评审问题、落实任务书、补充若干内容”等笼统过程描述代替实际变化。
- 标题描述部分不用括号、`--`、破折号补充说明，也不用 `+`、`/`、`&` 串联多件事。Conventional Commits格式中的scope括号保留；必要技术标识符按原名书写，不机械删除其字符。
- 标题描述建议15—40个汉字左右，仅衡量中文表达的简洁程度，不按中英混合字符机械折算，不设字数门禁；不能为凑长度省略核心变化，也不能借长度建议允许任务编号进入标题。
- scope取实际受影响模块，如ssh、database；框架与工程基建用core，不用任务编号充当scope。

## 类型按改动实质选择

| 类型 | 用途 |
| --- | --- |
| feat | 增加用户或开发者可用的新能力 |
| fix | 修复错误行为或实际隐患 |
| refactor | 调整结构，保持外部行为 |
| test | 增加或修正测试 |
| docs | 修改文档、规范与设计决策 |
| build | 修改依赖、构建或打包 |
| ci | 修改持续集成流程 |
| chore | 无法归入以上类型的日常维护，谨慎使用 |

纯搬移不能写成修复，规划文档不能写成已新增功能，部分验证不能写成全部通过。每次提交尽量对应一个可解释、可验证、可回退的变化。

## 正文说明具体变化

简单改动可以只有标题。复杂改动用短句或列表说明原问题、改动机制、必要的兼容影响、实际验证和局限，不复述操作流水。

正文采用现有的 `- ` 列表标记分条说明，每项写清一个具体变化或验证结果。标题对横杠和符号拼接的限制不适用于正文列表标记。正文允许必要的技术标识符与路径，关键解释写成完整短句，避免塞进括号。任务号、批次号、issue号和评审编号只能放在**正文末尾**的辅助关联项，例如 `- 关联批次：rel-202609-001`，不能代替变化描述；不需要追溯时省略。

```text
fix(ssh): 防止取消连接后重新打开会话页签

- 增加请求有效性检查，防止取消后的成功响应创建会话页签。
- 释放迟到响应创建的连接资源，避免连接泄漏。
- 新增取消后成功返回和卸载后返回的回归用例。
- 相关测试、类型检查与构建通过。
```

示例中的验证只有实际执行通过后才可写入。

## 文档和验收提交也写清内容

| 不采用 | 采用 |
| --- | --- |
| fix(ssh): 完成任务书整改清单 P3 | fix(ssh): 防止取消连接后重新打开会话页签 |
| docs(core): 更新任务书和清单 | docs(core): 明确数据导入的隔离与合并策略 |
| docs(core): 落实评审意见 | docs(core): 统一开发任务的分级与验收要求 |
| docs(core): 明确存储迁移策略 rel-202609-001 | docs(core): 明确存储迁移的校验与恢复策略 |
| docs(ssh): 补充验收记录 | docs(ssh): 记录连接取消与重连的验收结果 |

文档提交描述规则、设计或证据发生的变化，不暗示业务代码已经实现对应能力。

## 提交前自查

1. 只读标题能否知道改了什么，且与暂存差异一致？
2. 类型和scope是否反映改动实质，标题是否只突出一个结果？
3. 标题是否含任务号、批次号、issue号或评审编号？正文是否用任务书、清单或编号代替了具体内容？
4. 标题是否借括号、破折号或符号拼接多个主题？正文的 `- ` 分条标记不受此限制。
5. 验证和兼容声明是否有实际依据？

提交操作继续遵守AGENTS的署名、明确路径暂存、隔离他人改动和只commit不push要求。历史提交保持原样，不执行rebase、amend或其他历史重写来追溯套用本规范。

## 本地门禁

标题条款由 `.githooks/commit-msg` 在提交落盘前执行：违规即中止本次提交，标题不进历史。判定逻辑在 [`scripts/check_commit_msg.py`](../../scripts/check_commit_msg.py)（纯函数可单测），钩子本身只是入口。

每个克隆启用一次（`.git/hooks` 不进版本库）：

```bash
git config --local core.hooksPath .githooks
```

路径保持相对形式：写成 Git Bash 的 `/g/...` 时 git 找不到钩子会**静默放行**，比没有门禁更危险。检查器只判机械条款（编号、格式、括号与破折号、笼统描述），「标题是否真说清变化」仍靠提交前自查；规范判断确实有误时用 `git commit --no-verify` 跳过，并在当次说明理由。

验证：`python -m unittest discover -s scripts -p test_check_commit_msg.py`

## 提交边界

咨询不产生提交；已授权实施默认只 commit 不 push。相关代码、测试与说明可同提交，不强制实现与回填分离，不要求每次提交对应验收文档。小修验证写正文或最终回复；大任务在阶段与交接时维护必要状态。

## 单人项目的提交粒度

一个提交对应一个完整、可解释、可回退的变化，不与每条消息或每份文档一一对应。相关代码、测试、API 说明放一起；跨多步但尚未形成完整行为时不为了计数拆提交。

不创建基线空提交、逐次回填 hash、例行完成状态或收尾报告提交。独立 docs 提交应改变当前规则、设计或使用说明；新增测试随实现提交，复用测试源码入库，输出和一次性脚本留本地。已有历史不重新整理。

默认直接在当前分支处理已授权改动；不强制 PR、审阅人或每任务 worktree。并行写入确有需要时才隔离。署名配置已明确时直接复用，不每次要求用户重新确认身份。
