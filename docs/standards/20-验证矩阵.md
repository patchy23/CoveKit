# 20 · 验证矩阵

> 验证按改动风险选择，不按文件数量或会话次数。通过相关检查后，只有新改动、失败或未解决疑点才扩大或重复检查。测试取舍见[15](15-测试与走查.md)。

## 按变更选择

| 变更 | 本地执行 | CI 或用户执行 |
| --- | --- | --- |
| 文档 | 修改文件的链接和差异；入口改变再查预算 | 全仓文档链接 |
| Python 检查器、提交钩子、CI 分类 | 相关隔离夹具、语法与失败传播核对 | 工程工具测试、实际工作流 |
| 小范围前端逻辑/UI | 本次文件 lint/格式与相关轻量单测 | 类型检查/构建；需要时实际交互和视觉 |
| 公共前端能力、依赖或测试配置 | 前端 check、相关单测、依赖守卫 | 完整前端 test/build 与平台集成 |
| Rust | 源码、契约和 diff 核对；本地不调用 Cargo | fmt、clippy、相关行为及 AST 规范检查 |
| 持久化、密钥、取消与生命周期 | 可隔离的相关前端单测与契约核对 | Rust 故障、事务、并发与恢复用例；必要真实环境 |
| 发布与最终集成 | 配置审查 | 完整构建、平台冒烟与真实链路 |

## 本地与CI的分工

2026-09-17 用户裁决：允许助手本地运行与本次修改直接相关的轻量单测；完整构建、Cargo、真机和联网测试仍交给用户或 CI。这替代 2026-09-15 的“本地不跑产品行为测试”，保留“不执行 Cargo”。不得通过 Python wrapper、提交钩子或其它入口间接运行 Cargo。

轻量单测应离线、使用隔离数据、无真实凭证或服务操作。调用命令不是授权边界的例外；单测中若实际启动外部服务或访问真实数据，仍按真实操作处理。

未推送时 CI 不会自动替本地提交验证。最终回复须区别：本地通过、CI 实际通过、未执行；不能因为写了测试就声称功能已验证。Windows/macOS 构建门禁继续保留，它们补充本地没有执行的编译验证；无需团队审批流程。

## 命令入口

以下按需选择，不是每次全跑；尖括号为需替换的路径。

```bash
python scripts/check_markdown.py <本次文档路径>
python scripts/check_doc_budget.py
python -m unittest discover -s scripts -p 'test_pre_commit.py'
python -m unittest discover -s scripts -p 'test_ci_changes.py'
python -m unittest discover -s scripts -p 'test_doc_checks.py'
python -m unittest discover -s scripts -p 'test_check_commit_msg.py'
pnpm exec eslint <本次前端路径> --max-warnings 0
pnpm exec prettier --check <本次文件路径>
pnpm exec vitest run <相关测试路径>
pnpm run check
pnpm check:deps
git diff --check
```

工程工具共同改动时可一次执行 `python -m unittest discover -s scripts -p 'test_*.py'`。文档检查不带路径时查全仓已跟踪 Markdown；新文件传显式路径。删除文件或标题时查引用方，普通文档大小提示不触发强制拆分。

CI/用户的 Rust 入口：

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --locked --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --locked --no-default-features --lib
cargo test --manifest-path src-tauri/Cargo.toml --locked --no-default-features --test source_rules -- --nocapture
```

`scripts/check_docs.py` 检查 Rust 注释，`scripts/check_rust_rules.py` 检查 Rust 规则；两者都调用 Cargo source_rules，**不是本地无编译检查器，也不检查 Markdown**。CI 跑整个 source_rules 后不重复跑 wrapper。无默认 features 不等于不编译依赖。

## 提交前门禁（本地）

[pre-commit](../../.githooks/pre-commit) 调用 [pre_commit.py](../../scripts/pre_commit.py)：按暂存路径运行 Markdown 链接和 Prettier；入口变化时查预算；删除 Markdown 时扩大链接检查。不运行 Cargo、安装依赖、测试或产品构建。标题由 [commit-msg](../../.githooks/commit-msg) 校验。

钩子使用 NUL 分隔路径，支持中文和空格。检查的是工作树内容，**不是隔离的索引快照**；被查文件存在未暂存修改时会停止，避免拿另一个版本宣称暂存内容通过。不会自动暂存、撤销或整理用户改动。

工具缺失会明确报告未执行，不冒充通过；CI 仍是完整检查入口。已有准确的等价检查或钩子误判时可以说明原因使用 `--no-verify`，不能用它掩盖已知产品失败。新克隆按需设置 `git config --local core.hooksPath .githooks`。

## CI 分流与证据

已知纯文档、Python 文档/提交检查器与钩子变更走工程检查；产品代码、构建/依赖配置、工作流及未知路径保守跑产品检查。工程工具测试包含提交标题和钩子回归，避免本地生效的规则无人验证。CI 结果汇总保持失败传播；发布工作流独立验证配置和平台产物。

生成输出放本地忽略目录或 CI artifact。本地人工清单只收录确需用户、设备或现场凭证的事项，不跟踪到 Git；自动测试待 CI 不逐项追加人工任务。macOS 无环境不做实测，但正常实现并公开差异，见[09](09-平台能力矩阵.md)。

## 入口行为验收

咨询零写入；小改无任务文档；必要方案一份且不重复申请已有授权；既有改动受保护；测试有独立价值；提交能解释变化与验证局限。命令全绿不能替代这些行为。
