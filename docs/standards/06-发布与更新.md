# 06 · 发布与更新

## 发布模式

### CoveKit 命名与旧安装接续

产品名和仓库名为 `CoveKit`，工程包名为 `covekit`，应用标识为 `com.patchyx.covekit`；GitHub 所有者仍为 `patchy23`，与域名 `patchyx.com` 不要求同名。

新标识首次启动且尚无 `settings.json` 时，接续旧标识 `com.patchy23.patchybox` 的自举配置，并把旧默认数据根显式写成存储位置；已有自定义根原样保留。旧目录与配置不移动、不删除，新配置存在时不覆盖。若希望数据目录也使用新名称，通过设置中的存储位置迁移入口处理，不手工删除仍在使用的旧目录。不要同时运行共享同一数据根的旧、新版本。

新建凭证使用新 keyring service；只有新 service 的同空间条目明确不存在才只读回落到旧 service。拒绝访问、损坏等错误不当作缺省处理；读取兼容不重生成密钥、不改动旧条目。`.pbdata` 容器魔数与加密 AAD 保持兼容。新建暂存目录统一使用 `.covekit-staging-`；旧前缀集中定义在 `brand_compat`，仅处理升级前的残留和中断计划。同一迁移计划同时存在新旧暂存目录时停止并保留现场。默认导出文件名前缀使用 `covekit-`。

安装标识与可执行文件名均已改变，发布前须在 Windows/macOS 验证安装、更新、数据接续和凭证解锁；仅修改源码或 Rust 格式检查不能代替这些验证。

普通开发和 CI 构建继续读取 `src-tauri/tauri.conf.json`，不要求更新签名私钥。推送 `v*` 标签后，Release 工作流会生成一份不入库的 `src-tauri/tauri.release.conf.json`，打包 Windows NSIS、macOS DMG 和带签名的更新产物，然后创建 GitHub 草稿版本。

更新器固定读取：

`https://github.com/patchy23/CoveKit/releases/latest/download/latest.json`

## 构建平台

应用只发布 Windows NSIS 和 macOS DMG。CI 的 Rust 检查及 Release 发布门禁使用 Windows，安装包在各自目标系统构建；文档和前端检查使用 Ubuntu 执行器不代表支持 Linux 桌面。

## GitHub 配置

必需的 Actions 配置：

- Repository variable `TAURI_UPDATER_PUBLIC_KEY`：Tauri 更新签名公钥。
- Secret `TAURI_SIGNING_PRIVATE_KEY`：Tauri 更新签名私钥，绝不入库。
- Secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：私钥口令；无口令时留空。

macOS 签名和公证另需 `APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_SIGNING_IDENTITY`、`APPLE_ID`、`APPLE_PASSWORD`、`APPLE_TEAM_ID`。Windows Authenticode 需另行配置可用的代码签名证书；更新签名不等同于操作系统代码签名。

## 密钥和安全

首次发布前按 Tauri 官方流程离线生成更新密钥对，将私钥放入 GitHub Actions secret，并在安全位置备份。丢失私钥后，已安装的应用无法验证新更新。不要在本项目、日志、聊天或发布产物中传播私钥。

## 发布步骤

1. 确认 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 与发布标签的版本一致。
2. 按[验证矩阵](20-验证矩阵.md)完成发布检查，将 `CHANGELOG.md` 中已完成且准备发布的未发布条目归入目标版本。
3. 创建并推送同版本标签，例如 `v0.1.0`。
4. 检查 Release 工作流产物、`latest.json` 及签名，在实机验证升级。
5. 确认 Windows/macOS 代码签名和 macOS 公证后再发布草稿。
