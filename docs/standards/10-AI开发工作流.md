# 10 · AI 开发工作流（四档流程与质量门禁）

> **常青文档**（2026-09-13 从 AI 助手技能库迁入仓库，正文未改）。
> 定档判据、各档确认门禁、通用规则、返修上限、任务书模板。**动任何功能前先读本文定档。**
>
> 维护：改了本文件描述的行为，就改这里——不要只改 AI 助手侧的副本。

## 核心原则

核心原则：**流程轻重与风险成正比**。动手前先定档，按档执行；执行中发现范围超档必须升级，不得用低档流程绕过。本文只管定档、门禁、验证三件事；插件 UI 规范见 `docs/standards/11-插件UI开发约定.md`，多角色编排与测试执行规范见 `docs/standards/16-多角色编排.md` 与 `docs/standards/15-测试与走查.md`（待从 AI 助手侧迁入）。

## When to Use（何时使用）

- **仅适用 patchyBox 仓库**（`G:\workspace\patchyBox`）的功能开发、修复、框架改动、UI 调整
- 不适用：纯问答、单字符 typo 修正（直接改直接提交）
- **其他项目禁用**：本 skill 内含 patchyBox 专有路径、插件架构与提交规范，在任何其他仓库一律不得加载套用
- **加载后自检**：定档前先确认当前工作目录是 patchyBox（存在 AGENTS.md 且含「patchyBox · 项目简报」）；不是则立即停止套用本流程，按通用工程规范执行并向用户说明

## 定档

档位数字越大流程越重（S1 最轻 → S4 最重）：

| 档 | 场景 | 判定信号 |
|---|---|---|
| S1 小改 | UI 优化、小 BUG 调整 | 单插件内、不动公共契约、可一次提交 |
| S2 大修复 | 功能无法使用、涉及大量改动 | 需要根因分析；跨多文件/前后端修复 |
| S3 框架级 | 框架/公共层优化 | 动 `src/core/`、`src-tauri/src/framework/`、框架契约、装配文件（lib.rs / plugins/index.ts / mod.rs） |
| S4 新工具/重做 | 完整工具或模块新增、整体重做 | 新增 `src/plugins/<id>/` 或 `src-tauri/src/plugins/<id>/`；新建契约 |

兜底规则：

- 动 `src/core/` 或 `src-tauri/src/framework/` 的公共契约 → 至少是 S3
- 新增 `src/plugins/<id>/` 目录 → 自动 S4
- 拿不准就往更高一档（数字更大、流程更重），往下降档需用户明确同意
- **升级机制**：执行中发现实际范围超档（如小 BUG 查出根因在框架）→ 停下升级，补齐新档位的确认门禁后再继续

### S3 / S4 的硬性前置：先出两份文档（用户 2026-09-13 定）

**大任务必须先制定任务书和实现方案；小任务直接改。**

| | 任务书 —— 做什么 | 实现方案 —— 怎么做 |
| --- | --- | --- |
| 内容 | 范围、产出清单、验收标准、明确不做什么、约束与红线 | 技术路线与取舍、改动面（逐文件 / 逐模块）、实施步骤与批次划分、风险与回退 |
| 落盘 | `docs/batches/<批次号>/任务书.md` | `docs/batches/<批次号>/实现方案.md`（沿用旧名 `执行计划.md` 亦可） |
| 门禁 | **两份都经用户确认后才允许动代码**（S4 的契约冻结即此门禁的产物） | |

适用档位：**S3 框架级 / S4 新工具必做**；**S1 小改直接改**；S2 大修复先出根因分析（`10b-修复分析模板.md`），改动跨模块或多文件时按本节升级为任务书 + 实现方案。

**进度唯一视图是 [`docs/进度台账.md`](../进度台账.md)**：每份任务书一行，含状态与提交证据。开工前查台账，收尾时连同提交一并更新；`python scripts/check_progress.py` 校验台账与实际文件一致。

## 通用规则（全档适用）

1. **验证诚实**：验证状态只有 通过/失败/受阻 三种。没实际跑的命令不得声称已验证；环境或依赖缺失记「受阻」并说明解除条件，禁止标「跳过」伪装通过
2. pnpm 前置（Windows git-bash）：`export PATH="/c/Users/patchy/AppData/Roaming/npm:$PATH"`
3. 提交：conventional commits 带模块 scope（框架用 core）；只显式 `git add` 本会话文件，禁 `git add -A`；验证绿才提交；只 commit 不 push
4. **返修上限**：修复 → 验证失败 → 再修，最多 3 轮；第 3 轮仍失败立即停手，把失败证据（命令、输出、改动点）列给用户转人工，不得继续自动返修
5. 仓库红线（Rust 注释标准、字体语义 token、UI 组件契约等）见 AGENTS.md 与 `docs/standards/11-插件UI开发约定.md`，各档都必须遵守。**规模判定已改为语义判断（2026-09-12 起）**：约 300/400 行、8/15 个业务文件是评审信号而非自动失败条件（超线在提交说明写职责与拆分依据）；注释按语义强制（docs/05 §9）；clone 与锁按所有权、是否跨 await 判断，不数数量
6. **Rust 门禁**：凡动 `src-tauri/` 的改动，任何档位都必须 `cargo fmt` + `cargo clippy -- -D warnings` + 相关测试绿；本批收尾跑全量 `cargo test` 与两个规范入口（`python scripts/check_rust_rules.py`、`python scripts/check_docs.py`；AR02 落地后统一为 `cargo test --test source_rules`）（pnpm 四件不覆盖 Rust 侧）
7. **UI 门禁**：动任何 `.vue` / CSS 前必须先 `读 `docs/standards/11-插件UI开发约定.md`` 加载 UI 规范（本会话已加载过可豁免）；提交前按该 skill 的红线与公共组件契约逐项自查，自查结果写入完成报告；派 delegate 做 UI 任务时，任务书必须写明「开工先加载 docs/standards/11-插件UI开发约定.md」并内联最关键红线（原生控件禁令 / 字体语义 token 与 font-mono 边界 / 公共 Select·ContextMenu / 危险操作确认 + toast 反馈），子 agent 无对话记忆、不会自动加载 skill，不带红线等于裸奔

## S1 小改

- 无产物、无确认门禁、不派子代理，主 agent 直接改
- 验证：单插件改动至少 `pnpm lint` + `pnpm test`；动 `src/core/ui` 公共组件必须加 `pnpm build`；动 Rust 按通用规则 6 补 Rust 门禁；UI 改动按通用规则 7 走 UI 门禁。**本地只格式化本次改动的文件**（`npx prettier --write <文件>`），全仓用只读 `pnpm format:check` 检查，不跑全仓 `pnpm format` 改别人文件
- 验证绿 → 立即提交，改动说明写 commit body

## S2 大修复

1. **先诊断**：复现问题，定位根因（不是症状）；根因 + 修复方案按 `docs/standards/10b-修复分析模板.md` 落盘（`docs/batches/<批次号>/fix-<slug>.md`，小体量可直接把模板内容写进给用户的确认消息）
2. **根因确认门禁**：把根因与方案给用户确认后才动手；用户已明确说「直接修」时豁免
3. **修一类不是修一处**：根因确定后检查所有同类调用路径是否有同样缺陷，一并修复
4. 验证：全量 `pnpm test` / `lint` / `build` + Rust 门禁（动 Rust 时）+ 该功能回归走查（不能只看改动点）；走查方法见 `docs/standards/15-测试与走查.md`
5. 验证失败 → 返修，受 3 轮上限约束

## S3 框架级

1. **影响面盘点**：改公共契约前用 `search_files` 找出全部消费方插件，清单列入方案
2. **方案确认门禁**：按 §S3/S4 硬性前置落「任务书 + 实现方案」两份文档，经用户确认后才动代码；涉及 AGENTS.md 架构铁律（模块 owner 边界、兼容边界、IPC 注册与数据分区、公共组件契约）的权衡只能用户拍板
3. **验证最严**：按变更风险分层（矩阵见《架构重构与工程规范调整任务书》§12）——相关测试 + `pnpm lint` + `pnpm build`（含 typecheck）+ Rust 门禁（动 Rust 时）+ 受影响插件的功能走查；发布与跨层合入再跑全量 `test` / `lint` / `build` / `format:check`
4. **AGENTS.md 同步**：框架规则变化当场更新 AGENTS.md——它是跨会话事实源，框架改了它不更新，下个会话就按旧规则写代码；公共契约改动同时检查 `docs/standards/02-架构.md` 是否需同步

## S4 新工具/重做

多角色编排见 `docs/standards/16-多角色编排.md`，本文只定门禁：

1. **设计先行**：任务书 + 实现方案落盘 `docs/batches/<批次号>/`；用户对设计确认 = **契约冻结**（全流程最重要里程碑）
2. **用例先行**：测试任务书随设计一并产出一并确认，不许开发完再补用例（补的用例天然迁就实现）；测试执行按 `docs/standards/15-测试与走查.md`（待迁入）
3. **契约冻结硬化**：冻结后任何偏离契约的需要（命令名、出入参、UI 结构）必须回用户重新确认，开发 agent 不得自行调整
4. **开发/测试分离**：开发 delegate 只实现，禁止跑验收、禁止自称已验证；测试 delegate 独立按测试任务书验收
5. 开工前记录起始 HEAD（工作区干净时不造空基线提交）；复杂模块按阶段提交；进行中进度只在 `docs/进度台账.md` 与 `TODO.md` 维护（AGENTS.md 只放常青规则，不含状态清单）
6. 测试打回 → 返修，受 3 轮上限约束；仍不过 → 列出失败证据转人工

## 坑（Pitfalls）

- **运行中的应用会锁住 exe，让文档检查器失败**（2026-09-13）：dev 实例或应用还在跑时，`python scripts/check_docs.py` 会先 cargo 编译并尝试替换 `src-tauri/target/debug/patchybox.exe`，报 `failed to remove file … 拒绝访问 (os error 5)`、`cargo 退出码 101`。这不是规则命中，别去改文档；先关掉实例（`Get-Process patchybox | Stop-Process -Force`）再重跑
- **冷启动冒烟前先查 1420 端口残留**（2026-09-13）：上次会话遗留的 vite dev server 会让 `pnpm tauri dev` 的 `beforeDevCommand` 直接报 `Port 1420 is already in use`，看起来像启动崩溃。查 `netstat -ano | grep :1420` 取 PID 后关掉；git-bash 里 `taskkill //PID x //F` 参数会被吞（报「无效参数/选项」），用 `powershell -NoProfile -Command "Stop-Process -Id <pid> -Force"`

## 成长规则（本文档如何演进）

- **踩坑自动追加**：开发中踩到坑（烧 token、返工、险些丢代码的一次即记；普通摩擦同一类重复出现才记），直接写进本文的坑节或 `docs/standards/12-reka-ui坑.md` 等对应文档，带日期带证据，完成时向用户报告。坑放对器官：流程问题归本文，框架与渲染层坑归 `12-`，UI 约定归 `11-`
- **结构性改动先确认**：新增/修改门禁、档位规则、通用规则 → 提议给用户，拍板后才改
- **防淤积**：每条新增必须是可检查的行为规则（禁「要小心」式废话）；添加规则时删除被它取代的旧措辞；里程碑时回顾修剪

## 验证（流程本身是否被正确执行）

- 定档有依据，能说清为什么是这个档
- 该档的确认门禁均已通过，或被用户显式豁免
- 所有声称的验证都有真实命令执行记录，失败/受阻如实报告
- 提交只含本会话负责的文件
