# 10 · AI开发工作流

> 何时读：实施任务、判断任务规模或接手大任务时。咨询按需读取，不进入开发闭环。命令唯一来源是[验证矩阵](20-验证矩阵.md)。

## 请求分流与定档

| 请求 | 判据 | 执行与产物 |
| --- | --- | --- |
| 只读咨询 | 解释、分析、评审、建议，未要求实施 | 回答及必要证据；不自动改文档、跑门禁或提交 |
| S1 小改 | 明确的局部修正，保持既有契约 | 直接实施、相关验证、提交；无额外任务材料 |
| S2 修复 | 需要根因分析，恢复既有契约 | 分析可在会话中；已授权则继续，按需用[修复提纲](10b-修复分析模板.md) |
| S3 公共改造 | 改公共行为、数据格式、安全边界或重要工程机制 | 任务书与实现方案，关键取舍确认后实施 |
| S4 新能力或整体重做 | 完整新能力或替换，存在重要范围与设计决策 | 同上，验收必须包含用户可观察结果 |

文件数、目录位置和行数不决定档位。明确且低风险的工程小修不因触碰公共文件自动升级。只读分析即使讨论架构，也不自动成为 S3 实施。

## 大任务两份文档

[任务书](templates/任务书.md)写问题、目标、范围、不做项和验收；[实现方案](templates/实现方案.md)写当前代码、技术取舍、改动面、步骤、验证、风险与恢复。保存于 docs/batches/ 对应批次，已有任务书覆盖子阶段时沿用，不重复立项。

新大任务在代码前准备两份材料并确认。会话中已有具体方案与执行授权，可直接整理入库并执行，不重复申请；不能把沉默视为批准。当前方案与批次入口见[TODO](../../TODO.md)。

默认不另建决策书、实施记录、交接报告、补证据记录或测试报告；复杂到影响阅读时才拆专题。实现方案末尾维护简短执行状态：完成阶段、下一步、阻塞、重要偏离和必要验证结论。

## 按批准目标实施

1. 实施前查 git status、相关范围裁决与实际调用链；复杂工作记录起始 HEAD，不造空基线提交。
2. 以验收项明确现状与预期；并发、迁移、取消、资源释放建立行为或故障用例。
3. 按已批准方案持续推进，完成接线和必要清理；常规命名、测试替身、内部拆分由执行者负责。
4. 范围、用户行为、已发布数据兼容、安全边界或重要技术取舍变化，先说明偏离与影响并确认；仅暂停依赖未定决策的部分。未发布且无实际消费方的内部名字不强制兼容别名。
5. 按影响选择验证，如实报告通过、失败、未执行与局限。连续三轮失败没有新证据则重新审查假设，不盲修。
6. 对照原定验收交付，不通过事后改任务书掩盖未完成。按可解释的改动提交；相关说明可同提交，不强制实现后再补一次记录提交。

一个交付项只有一个归属，其他批次引用结果。阶段完成、重要决策、交接或任务结束才更新方案状态；TODO只维护活动入口，不复制证据。小修结果放提交正文与最终回复即可。

## 自测、交接与证据

开发者负责相关自测；独立验收补充需求视角，不为角色形式强制创建 agent。委派需任务或适用环境授权，见[16](16-多角色编排.md)。接手核对当前代码与活动方案，不复演旧会话。

历史测试结果始终属于执行时的提交与环境；后续改动是否需要重跑按影响判断。补写文档不自动使产品测试失效。需人工或真机执行的项目见[待人工验证清单](../待人工验证清单.md)，不阻塞任务书收口，也不能写成已通过。

## 环境与规则维护

只清理由本任务启动且确认归属的进程；用户实例正常关闭，未知实例先核对。端口占用先查归属，不按名称强杀，不为文档检查停止应用。不得 stash、reset 或覆盖他人改动。

可重复的工程风险优先用类型、测试和守卫约束。长期规则需有明确触发条件；临时排查留会话或 .work/，不把每次工具失败写成永久规则。修改流程时同步仍适用的模板和工具，历史指令不覆盖现行流程。
