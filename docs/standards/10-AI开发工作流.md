# 10 · AI 开发工作流

> 项目由一人维护，agent 是开发助手。目标是准确交付，流程只服务于范围澄清、验证和必要接续。验证入口见[20](20-验证矩阵.md)。

## 按请求进入

| 请求 | 执行方式 | 任务材料 |
| --- | --- | --- |
| 咨询、解释、只读审查 | 阅读相关源码和约束后回答 | 不自动改文件或提交 |
| 明确的小改、既有行为修复 | 查调用链、实施、相关验证、提交 | 不建任务文档；复杂根因按需用[修复提纲](10b-修复分析模板.md) |
| 有重要取舍或需跨会话接续的改造 | 先明确目标、当前实现、影响和验收，再持续实施 | 默认一份[方案](templates/实现方案.md)，已有方案覆盖则沿用 |
| 长期复杂工程 | 按可独立验证的阶段推进 | 仅当范围与技术细节确需独立维护时拆[任务书](templates/任务书.md)和方案 |

文件数量、修改公共文件、请求条数不决定是否立项。一次会话可完成且取舍明确的公共组件修改，也可以不建任务文档；必要 API 和设计说明仍随实现更新。不为每条消息新建批次。

## 授权与范围

用户已明确目标并要求实施时直接推进。写方案是整理工作，不是再设一道批准关卡。只有未覆盖的重大范围变化、用户行为变化、数据兼容或安全边界取舍才澄清；先完成不依赖答案的工作，不能把沉默当批准。

没有证据表明要扩展的功能不顺手开发；也不为未来假想需求增加抽象、适配层或配置。普通命名、内部拆分、mock 和夹具由 agent 决定。没有新的错误或不确定性时，不重复全量读取、检查和汇报。

## 实施闭环

1. 查 Git 状态、TODO 相关入口和实际消费方，区分用户已有改动；复杂工作在方案中记起始 HEAD。
2. 明确触发条件与预期结果。沿调用链确认状态归属、错误、持久化、取消及释放责任。
3. 实施完整接线和必要清理。仅处理本次直接涉及的问题，不能因为看到长文件就扩大重构。
4. 选择能发现此次错误的验证。测试按[15](15-测试与走查.md)取舍，命令按[20](20-验证矩阵.md)执行。受执行限制或环境限制时明确标为未验证。
5. 按一个可解释、可回退的变化提交代码、测试和相关说明，遵守[21](21-Git提交规范.md)；默认只 commit、不 push。
6. 最终说明改了什么、验证结果和剩余事项。实现完成与验证完成分别表述，不事后降低验收标准。

## 接续与收口

方案只在重要决策、阶段完成、跨会话接续或结束时更新。只留目标、必要设计依据、尚未完成事项和验证局限，不维护操作流水、逐次 hash 或重复统计。

TODO 只作活动入口。普通小修验证写提交正文或最终回复；只有确需用户或特定环境执行的事项才放[人工验证清单](../待人工验证清单.md)。待 CI 自动执行的单测不逐项变成人工待办。已完成方案冻结，不为每次后续小修重开或补记。

临时计划、分析和输出放 `.work/`。跨会话继续同一目标可沿用一份方案；不强制角色评审、交接报告、覆盖矩阵或独立文档提交。历史批次只作证据，不能覆盖当前用户裁决与源码。
