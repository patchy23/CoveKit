# 09 · 平台能力矩阵

> **常青文档**。项目要求「产品能力必须覆盖 Windows 与 macOS，unsupported 必须可见」（AGENTS.md 已定技术决策）。
> 本文是那张表：每个能力在两端的真实状态与依据。**空白不等于通过**——没实测的就写「未实测」，禁止用推测填成「可用」。
> **macOS 差异点集中登记在 §3**：跨平台分支代码一律登记在此，不再散落在各批次文档里。

## 状态口径

| 状态 | 含义 |

## 3. macOS 差异登记

> **本节是两端必然不同的代码点清单**，扫描范围 `src-tauri/src`、`src`、`Cargo.toml`、`tauri.conf.json`。
> macOS 列一律 `⏸ 未实测（无平台环境，用户已裁决不追求补齐）`；**不得把它当作「已通过」**，也不得因为没测就不写实现。
> **维护规则**：新增或改变用户可观察的平台能力、限制或验证结论时更新对应能力行；同一能力的内部条件编译调整不逐处分配新行。

## 4. 已知平台差异的处理原则

1. **接口契约两端一致**：平台差异不体现在 IPC 契约上，只在实现层分派。
2. **unsupported 必须可见**：不支持的能力要在界面上显式禁用或给出说明，不得静默失败。
3. **不靠移除平台目标规避问题**：Windows 专属调用必须加条件编译或非 Windows 明确 no-op。
4. **平台专用依赖**：新增时按 `standards/05-Rust代码规范.md` 评审并记录 target 条件。
5. **差异必须登记**：§3 是唯一登记处，改代码与改表在同一次提交内完成。

## 5. 长期环境缺项

- **macOS 构建、冷启动与平台实测**：无 macOS 环境，用户 2026-09-13 裁决不追求补齐。相关结论保持**空白**表述，**不得改写为「已通过」**。macOS 侧代码照常实现，差异点全部登记在 §3。
- **真实数据库驱动矩阵**：只有 SQLite 实测；MySQL/PG/Redis 与国产库需要实例或远端 agent。
- **桌面交互取证**：后台合成点击不可用（`effect: unverifiable`），部分走查需人工，或用 CDP 驱动正式版 exe 取证。
