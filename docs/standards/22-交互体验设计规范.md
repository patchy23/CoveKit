# 22 · 交互体验设计规范

> 公共 UI 设计依据，适用于基础控件、工具页面和工作区。新建或调整交互时先读必读摘要，再按相关主题阅读；纯文案修正无需通读。
> 本文规定设计原则与行为约束，不是已实现能力清单。具体功能范围以[产品裁决](07-产品需求.md#当前有效范围裁决)为准，多窗口、持续观察区等能力不因本文提及而自动进入实施范围。

## 必读摘要

- **围绕完整任务设计**：先说明用户要完成什么、需要同时看什么、什么状态必须保留，再选择组件和布局。
- **操作容易找到，后果能够预测**：高频动作直接可见；动作靠近对象；相同概念保持命名和行为一致；拖拽有菜单等替代入口。
- **工作保持连续**：切换、折叠和布局调整保留工作现场；移动视图不能隐式重连、重发请求或重跑任务。
- **反馈真实且就地可见**：加载、旧结果、空结果、失败和不支持分别表达；失败保留可恢复内容；更新不抢焦点。
- **按影响决定打断程度**：普通反馈留在内容附近，可能丢失数据或结束重要任务时明确说明影响；持续工作避免被模态界面阻断。
- **统一交互，保留工具独立性**：工具拥有自己的业务和资源，框架协调展示与生命周期；禁止跨工具内部访问。
- **复用现有设计体系**：视觉 tokens 只见 [DESIGN](../../DESIGN.md)，控件走公共组件；不以缩小字号、隐藏全部操作或复制组件换取表面简洁。

## 1. 文档职责与使用方式

本文维护跨工具的设计思路和通用行为。开发者应能仅凭仓库理解约束，不依赖会话、助手配置或本地方案。

| 工具布局、编辑器、浮层的具体实现约定 | [11 UI 开发约定](11-插件UI开发约定.md)、[13 表单](13-表单排版约定.md) |

| 测试取舍与验证命令 | [15 测试与走查](15-测试与走查.md)、[20 验证矩阵](20-验证矩阵.md) |

“必须、不得”是适用场景中的行为约束；“建议”是设计默认方向。新增和修改的交互按本文设计，既有界面按任务范围逐步校准，不据此扩大为全仓改版。本文不证明现有控件已经满足所有要求，使用前仍需核对实际组件和调用链。

现行产品行为和专题约定继续有效。改变主按钮数量、快捷键作用范围、关闭按钮语义等既有规则时，必须明确行为变化并同步其权威说明，不在工具内部形成隐含例外。

## 2. 借鉴苹果的体验设计原则

Apple 的人机界面经验用于帮助判断交互质量。下表右侧是 CoveKit 对原则的应用，不是 Apple 对本项目的具体要求。保留现有明净、内容优先的视觉方向；Windows 和 macOS 分别遵守平台习惯。

| 原则及官方依据 | 在 CoveKit 中如何运用 |
| --- | --- |
| 一致性帮助用户预测结果，[Essential Design Principles](https://developer.apple.com/videos/play/wwdc2017/802/) | 同类操作使用相同名称、控件和反馈；连接、请求、查询仍保留各自业务语义 |
| 反馈与信息重要性相称，[Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) | 复制成功轻量反馈；字段错误就地呈现；可能丢失工作时说明影响并让用户决定 |
| 模态应有明确收益，[Modality](https://developer.apple.com/design/human-interface-guidelines/modality) | 短配置和必要确认可以用弹窗；持续观察、终端操作等工作优先使用非模态内容 |
| 拖拽应明确移动或复制并提供替代入口，[Drag and drop](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop) | 提供落点预览、取消与菜单动作；移动视图不隐式复制业务会话 |
| 窗口行为符合平台认知，[Windows](https://developer.apple.com/design/human-interface-guidelines/windows) | 需要跨屏工作的内容适合系统窗口；支持时应考虑排列、缩放、窗口定位与找回 |
| 无障碍贯穿交互，[Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) | 保留键盘路径、可见焦点、文本状态和减少动效；操作不只依赖颜色、悬停或精确拖动 |

界面简洁以完成任务的负担衡量：减少记忆、来回寻找和重复输入，同时保留关键操作的可发现性。借鉴原则时不直接套用移动端密度、专用素材或视觉效果。

## 3. 从工作过程选择布局

设计前明确四件事：主要任务、操作对象、需要同时观察的内容、必须保留的状态。简单变更可直接在实现判断中完成，不要求额外撰写方案。

| 用户需要 | 适合的呈现方式 | 设计注意点 |
| --- | --- | --- |
| 执行当前任务，例如发送请求、执行查询 | 有足够空间的主要内容区 | 主动作与输入、结果相邻；执行目标清楚 |
| 持续观察，例如多个服务日志 | 非模态区域；具备能力时支持并排或独立窗口 | 切换其他工作不应夺走用户明确固定的观察内容 |
| 查看辅助信息或调整选项 | 可收起侧栏、详情区或按需展开区域 | 收起后保留恢复入口及已填值 |
| 完成短而集中的配置或确认 | 简短弹窗或局部编辑 | 完成或取消后回到来源，不层层堆叠弹窗 |
| 偶尔处理报文等内容 | 独立工具中的短操作路径 | 保留来源工作现场，遵守跨工具协作范围 |

复杂工具沿用现有朴素分栏、局部 header 和内容优先的布局，具体要求见 [11 的布局约定](11-插件UI开发约定.md#复杂工具页布局风格2026-08-15-用户纠偏红线)。首页的工具发现与工具内部的业务操作分别组织；不重复套应用外壳或全局工具栏。

高频操作直接可见，次要动作进入局部菜单，高级配置按需展开。配置折叠的前提是默认值足以完成常用任务；折叠区域有错误时显示摘要并允许定位。统一规则不要求所有工具拥有相同栏数、字段顺序或页面模板。

布局适应内容与可用空间。主要阅读/编辑区优先获得空间，密度使用公共组件档位；不可通过无限缩小字号和命中区域挤进更多内容。分栏不是必选项，只在比较、观察或操作确需并行时使用。

## 4. 基础组件行为

下表说明行为目标，实际组件选型与参数仍见 04 和 11a。同类缺陷优先修公共组件并核对消费方，不逐页复制一套实现。

| 控件或区域 | 行为约束 |
| --- | --- |
| 按钮 | 名称表达动作及必要对象；开始执行立即反馈，避免重复提交；图标按钮有可访问名称，Tooltip 仅作补充 |
| 禁用状态 | 用户能在邻近说明、字段错误或可聚焦说明入口中理解原因，不只依赖禁用按钮的悬停提示 |
| 输入与字段 | 标签持久可见并关联输入；placeholder 仅示例；字段错误靠近字段；失败保留输入；输入未完成时避免持续报错 |
| 表单提交 | 显示执行状态；失败时引导到首个需处理的问题；折叠区内错误可定位；保存和执行的含义不得混淆 |
| 选择控件 | 开关表示启停，单选表示互斥选择，页签表示内容切换；遵循公共组件的键盘语义 |
| 列表与树 | 选择、展开、执行有清楚的作用范围；同类对象单击/双击行为一致；刷新保留仍有效的选择和展开状态 |
| 数据表格 | 文本选择与行操作互不劫持；刷新不使点击目标漂移；排序、分页和数据来源可辨认 |
| 页签 | 激活与关闭互不误触；可键盘到达；溢出时当前项可定位；关闭后焦点回到合理相邻项或首页；提供移动时明确结果 |
| 菜单 | 同类动作顺序一致，危险操作分组；Esc 关闭并回到触发点；必要功能具有右键之外的入口 |
| Tooltip | 只放简短说明，不承载唯一错误原因、交互按钮或可复制正文 |
| 编辑器 | 使用公共 CodeMirror 基座；切换或折叠保留正文、光标、选区和滚动；不抢占已经约定的终端/编辑器快捷键 |
| 日志与持续输出 | 可选择复制；阅读历史不被新内容拉走；来源、接收状态与更新信息明确；暂停显示和停止采集分别命名 |
| 可调整分隔条 | 有最小可用尺寸与恢复方式；提供键盘或预设布局等拖动替代，不把内容压成无法操作的窄条 |

应用输入、表格、结果、日志与终端的文本选择边界沿用 DESIGN。不得全局拦截鼠标、键盘或复制事件来维持界面整齐。

## 5. 反馈、错误与控制权

1. **状态表达真实。** 区分未开始、加载中、成功、有旧结果、无结果、失败和平台不支持。未连接不显示“没有日志”，获取失败不显示“没有数据”。
2. **反馈紧邻对象。** 字段问题放在字段旁，业务错误放在所属内容区；需要处理的错误持续可见并给出重试或下一步。普通成功用轻量反馈。
3. **刷新不抹掉工作。** 更新已有数据时保留可阅读结果并标明刷新状态；首次加载才按需要用骨架或占位。无确定总量不显示虚假百分比。
4. **更新含义清楚。** “上次成功读取”和“最近一条记录”分别表达；没有新增与采集失败可区分。失败时保留旧结果但标明它不是新的成功结果。
5. **减少重复打断。** 同一错误不同时堆叠多个弹窗、toast 和横幅；诊断日志与用户反馈分别履行职责。持续工作不依赖必须先关闭的模态层。
6. **取消有真实结果。** 取消不伪装成功或普通失败；无法取消的阶段明确提示，不提供无效取消按钮。
7. **焦点归用户。** 后台完成、日志更新和轮询失败不自动激活窗口或抢走输入焦点；主动操作需要确认时，反馈回到发起位置。
8. **危险操作说明对象和后果。** 例如说明断开服务器会结束哪些会话；能可靠撤销的低风险动作优先提供恢复途径，不滥用“确定吗”。
9. **布局动作可恢复。** 筛选、折叠与位置调整不额外确认；重置布局不清空正文。请求、命令、SQL 等操作不因显示恢复而自动重复。

## 6. 连续工作与工具独立性

### 6.1 状态保持与资源边界

同次运行中的切换、折叠和布局调整必须保护草稿、选择、滚动位置与任务现场。展示变化和业务结束是不同动作；页面不可见不等于连接应断开。资源范围由原 owner 的契约定义，不能由基础控件的卸载事件推断。

业务视图、会话、工具、窗口和应用退出分别说明关闭影响，使用已有协商入口。主窗口隐藏到托盘等已确认行为继续由产品规范定义；新增窗口类型必须明确自己的关闭语义，不能自行复制主窗策略。

界面恢复只恢复已允许的布局与安全草稿，不自动恢复外部连接或执行操作。布局持久化只记录位置、尺寸和安全标识，业务正文与凭证不进入布局文件、窗口 URL 或诊断日志。业务草稿仍按所属工具的存储规则管理。

### 6.2 统一体验的分工

| 层级 | 责任 |
| --- | --- |
| DESIGN 与基础 UI | 视觉语义、通用控件、焦点、交互状态和可访问性；不依赖业务 Store、凭证或业务 IPC |
| 工作区与平台 | 工具装载、导航、展示位置、可见性、窗口及关闭协调；使用公开契约，不解释业务正文 |
| 工具 owner | 完整业务入口、数据与草稿、连接、任务、结果、业务错误和清理规则 |

每个工具单独打开仍应完成自身工作，其他工具未打开或出错不得成为其正常使用的前置条件。共享能力走公开契约，禁止直接 import 其他 owner 的内部组件、状态或数据表。

需要协作时，优先判断是否只需同时显示两个独立工具。只有业务确需传递数据且范围已允许时，才定义显式的数据契约；不能用统一 UI 的名义建立跨工具可写业务状态中心。框架不得为摆放界面要求纯前端工具新增后端模块。

### 6.3 支持分离视图时的设计要求

本节约束未来或已获授权的视图分离能力，不声明 CoveKit 当前已经提供多窗口、观察区或拖出页签。具体实现和默认关闭策略仍需按产品范围确定。

- 移动保持同一个逻辑工作，复制明确命名；移动视图不触发重连、重发请求或重新执行查询。
- 提供菜单等拖拽替代、合法落点预览、取消和移回入口；目标创建失败时保留原位置的可用工作。
- 用户明确固定的观察内容保持可见，切换主要工具不替换它；空间不足时给出调整排列、收起或移窗等已有可用选择。
- 焦点、可见性、最小化和隐藏分别表达；并排可见的日志不因用户在另一个窗口输入而被当作隐藏。持续采集与展示刷新由 owner 分别管理。
- 关闭观察视图只释放其订阅；结束它依赖的会话时，由 owner 明确依赖影响并同步派生视图状态。
- 多窗口退出需要汇总所有相关阻断后统一决定；取消时不能已经清理部分工作。继续沿用唯一关闭协调，不新增平行退出路径。
- 系统缩放、显示器移除、移回和找回窗口共同设计；状态移交失败不通过自动重跑业务操作伪装恢复。

## 7. 键盘、平台与可访问性

- 高频操作具有键盘路径；Tab 顺序符合视觉和任务顺序；焦点与选中状态分别可见，弹窗关闭后回到触发位置。
- 重要操作不只依赖悬停、颜色或精确拖动；状态同时提供文字或图标；控件名称对辅助技术可读。
- 平台快捷键遵循各自习惯并维护现有兼容性；不得全局抢占终端 Ctrl+C、编辑器查找/保存或输入法组合事件。调整快捷键范围时同步专题契约。
- 主动作的视觉强调、字体、尺寸和对比度以 DESIGN 为准；不能在业务页自行放宽其限制。
- 动效用于表达位置变化与操作结果，遵循系统减少动画设置；不加入持续装饰动画，不用过渡掩盖加载失败。
- 亮暗主题、最小可用窗口和 125%/150% 系统缩放共同考虑；更多空间应改善内容阅读，更少空间仍能找到主要操作与恢复入口。

## 8. 设计走查与维护

按本次变化选择实际流程验证，不为满足条目而补实现镜像测试或无关功能。执行方式只见 [20 验证矩阵](20-验证矩阵.md)；不把 DOM 单测通过写成桌面交互或视觉已经验证。

| 走查维度 | 应能回答的问题 |
| --- | --- |
| 发现与操作 | 用户能否找到主要动作，知道它作用于哪个对象？仅用键盘能否完成高频流程？ |
| 反馈与失败 | 当前状态是否真实？失败保留了什么？下一步是否可执行？是否重复打断？ |
| 布局与阅读 | 操作和内容是否靠近？窄窗口和缩放下是否可用？刷新是否打断阅读？ |
| 连续性 | 返回后是否需要重复输入或定位？显示变化是否误触发执行、重连或清理？ |
| 工具边界 | 该工具能否单独使用？共享 UI 是否引入了业务依赖或跨 owner 内部访问？ |
| 关闭与恢复 | 关闭影响是否符合名称？取消是否保留工作？恢复是否重复执行了业务操作？ |

多工具流程的典型检验是：持续观察两份日志时发送 HTTP 请求、查询数据库、进入终端排查，观察内容与工作状态保持连续。仅在相关能力实施时执行这一验收，不把它当作所有 UI 小改的门禁。

长期通用规则在本文维护，具体 token、组件 API、产品裁决仍更新各自权威文档。实施方案、一次性走查记录和未定取舍留在本地，正式文档不链接这些材料。
