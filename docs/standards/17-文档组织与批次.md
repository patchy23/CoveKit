# 17 · 文档组织与批次号

> 本文原为 AI 助手侧技能库中的项目知识，2026-09-13 迁入仓库，作为项目自有开发手册的一部分。正文未改写（仅同步文档路径与目录规范）。

适用：人 + 多个 agent 长期并行开发同一仓库，`docs/` 已堆到几十篇，开始分不清哪篇是活的。

## 1. 诊断看「生命周期混层」，不是看「乱」

先把现有文档按**生命周期**归类，而不是按主题：

| 类型 | 特征 | 读法 |
|---|---|---|
| 规格 / 任务书 | 会反复读，是事实源 | 常读 |
| 决策记录 | 一次拍板后冻结 | 只查 |
| 执行计划 | 会被推翻、要回填提交号 | 半活 |
| 报告 / 评审 / 竞品 / 基线快照 | 一次性，之后只剩考古价值 | 不读 |
| 证据留档 | 只写不读，用于复核 | 按需 |
| 收尾 / 待办清单 | 活着但会被消费掉 | 常读 |

失控的判据是**「现在该干什么」需要先猜哪篇是活的**，不是文件总数。一个目录平铺十篇上下就会出现这个问题，混层比数量更致命。

## 2. 行业三条路线（对照用）

| 框架 | 目录形态 | 关键机制 |
|---|---|---|
| Kiro | `.kiro/specs/<feature>/{requirements.md, design.md, tasks.md}` | 一特性一目录三件套；进度只在 tasks 勾；执行按依赖波次 |
| spec-kit | `specs/<NNN-feature>/{spec.md, plan.md, tasks.md, research.md, contracts/}` | 特性编号自增；任务标 `[P]` 表示可并行 |
| OpenSpec | `openspec/specs/<domain>/spec.md`（真相）+ `changes/<change>/`（提案）+ `archive/` | 真相与提案分离，改动写 delta，完工合并回 spec 再归档 |
| 传统文档学 | `docs/adr/NNNN-<slug>.md`；Diátaxis 四象限 | 决策不可变、独立留痕；文档按读者需求而非时间分类 |

四条共同点，可移植：① 一个工作单元 = 一个目录，内含固定几件套；② 进度只有一个源；③ 完成即归档，活跃区与历史区分开；④ 决策独立留痕，不与执行文档混放。

## 3. 批次号 = 跨目录的关联键

- 目录名或文件头带批次 ID，形式 `<领域>-<年月>`（如 `ARCH-2026-09`）
- **已存在的子编号原样保留**（`AR01`、`T04`、`L0`–`L5` 之类），它们变成批次内的条目 ID——重命名会打断历史提交、文档与源码注释里的既有引用
- 每篇文件头写 `batch: <ID>`（可选 `batch-item: <条目ID>`），于是决策记录、插件文档、批次目录三处能被同一个 ID 串起来
- 一个批次一个进度清单；不要为批次另建「进度报告」类文档

## 4. 存量仓库的迁移成本与流程

- 迁移前先 `git grep -n '<doc 路径>'` **数引用**——引用常出现在源码注释里（框架模块、契约文件、测试文件都爱引用文档路径），只改 markdown 会留一批死链
- 这类重整通常同时动三处：文档 + 源码注释 + 仓库常青规则文件里的文档地图表；**常青规则文件（AGENTS.md 之类）一般是受保护文件**，改前必须与用户确认
- 因此它属框架级改动：先给方案（新目录 + 批次号规则 + 迁移映射 + 引用清单）→ 用户拍板 → 一次搬到位并同步改引用
- 用户的方向性要求（「分目录放，按批次号关联」）**不等于**目录方案已定；目录名与批次号形式未拍板前不要擅自迁移

## 5. 明确不做

- 不引入 OpenSpec / Kiro 工具本身：它们面向 0→1 新建，存量仓库接入成本大于收益（OpenSpec 的 delta 机制对存量友好，但目录约定要全量服从）
- 不重命名已有的编号真相层文档（`01-tech-stack.md` 这类）
- 小批次不强行凑齐 spec + design + tasks 三件套，一份索引 + 一份任务清单就够
